## 🤖 AI 分析

## 一句话概括

这个视频讲的是：长期使用 AI 做项目时，不能只依赖单次聊天上下文，而要通过类似 Claude Code 的“三层长期项目记忆系统”，把项目规则、历史决策、调试经验和关键资源沉淀成可维护的 Markdown 记忆库，让 AI 在新对话中也能接上任务，并且越用越聪明。

## 背景与主题

作者从一个常见痛点切入：很多人用 AI 时，一个对话从早用到晚，直到 AI 开始犯傻、答非所问、前后矛盾，才不得不开新对话；但新对话一开，AI 又“失忆”，用户又要重新解释自己是谁、项目是什么、技术规则是什么。作者用自己的真实项目举例：项目有 **30 多万行代码和文档、1300 多个文件**，包含客户端、服务器、小程序、官网、各类文档和其他模块，但在 Claude Code 中开一个全新对话，AI 依然能迅速接上前面的任务。作者认为，这不是因为 Claude Code 有无限上下文，而是因为它背后有一套长期项目记忆系统。视频主要是在解释这套系统的工作原理、三层架构、优缺点、正确使用方法，以及作者基于经验整理出的开源协议 **engramory / Ingramory**。

## 核心观点

### 1. AI 用久了会“犯傻”，根本原因是大模型本身无状态、上下文有限

作者首先指出，大模型本身是“无状态”的，每次回答只能看到当前对话框里的内容，而不是天然拥有连续、稳定、永久的记忆。一个对话用得越久，聊天窗口里的内容越长，模型要么会因为上下文长度限制被截断，要么会把前文压缩成摘要。作者用了一个很形象的比喻：这种压缩像表情包被不断转发，前几次还能看清，转多了以后细节越来越模糊，最后只剩一个大概轮廓。于是用户会感觉 AI 越用越跑偏，开始答非所问、前后矛盾、忘掉早期约定。开新对话虽然会让 AI 变快、变清醒，但代价是原来的项目背景、规则、上下文和历史决策都不见了。

### 2. 真正好用的 Agent 不能只靠聊天窗口，必须有窗口之外的长期记忆系统

作者强调，要解决“长对话变糊”和“新对话失忆”的矛盾，不能只依赖聊天窗口。真正好用的 Agent 应该在聊天窗口之外配备一套记忆系统，把该存的东西存下来，需要的时候再喂给大模型。这样，聊天窗口负责即时推理和当前任务，长期记忆系统负责保存稳定信息、项目背景、历史经验和可复用规则。作者的真实项目就是靠这套机制实现的：即使项目体量达到 30 多万行、1300 多个文件，新对话仍然能接上前面的任务。换句话说，AI 的“长期项目能力”不是靠一次性塞满上下文，而是靠把上下文外部化、结构化、可检索化。

### 3. 常见记忆路线有两类：RAG 向量和 Markdown 文件，各有优劣

作者把目前常见的 AI 记忆方案分为两类：第一类是 **RAG 向量检索**，第二类是 **Markdown 文件记忆**。RAG 向量的做法，是把记忆切碎，压成语义坐标，塞进数据库，用的时候根据语义相似度搜索；它的优点是能装下海量记忆，并且支持自动召回。但作者也指出，RAG 的缺点是黑盒化：用户看不见、改不动、不容易直接删除或修正，也有小概率出现检索错漏，而且还需要搭建数据库。另一条路线是纯 Markdown 文件，本质上就是一堆人能直接读懂的文本文件，加上一份目录。它的优势是透明、能看、能改、能删、能进 Git，也不需要单独搭数据库；对个人项目和中小型团队来说，这种方式已经非常够用。

### 4. Claude Code 的长期记忆可以拆成三层：即时上下文、手写项目规则、自动记忆库

作者为了方便理解，把 Claude Code 的记忆系统拆成三层。第一层是当前对话的即时上下文，也就是正在聊天窗口里发生的任务、代码、讨论和推理。第二层是用户手写的项目规划和规则文件，例如视频中提到的 **CLAUDE.md / cloud.md**、个人规则、目录规则等；它解决的是每次开新对话时，不用重新解释项目背景、技术栈、工作习惯和约束。第三层是作者认为最重要的一层：Claude 自己维护的自动记忆库。这个自动记忆库会把用户反复纠正过的内容、项目关键决策、调试经验、资源位置等整理成 Markdown 笔记，从而形成长期项目记忆。

### 5. Claude Code 的关键设计不是“把所有记忆塞进去”，而是“常驻索引，细节按需召回”

视频中最核心的技术逻辑，是 Claude Code 并不会把所有长期记忆一次性塞进上下文，而是先加载一份“主索引”。这份主索引告诉 Claude：项目里大概有哪些记忆、什么东西在哪里、什么时候应该去读哪些文件。真正需要某个细节时，Claude 再去读取对应的记忆文件，这就是作者总结的“常驻索引，细节按需召回”。作者用自己的项目举例：Claude Code 为他的项目沉淀了 **118 个记忆文件**，总共 **14000 多行笔记**，但每次加载到上下文里的主索引只有 **148 行**。也就是说，148 行目录背后挂着 14000 多行记忆，只有当用户提到相关内容，或者模型判断需要时，才会翻开其中一页或几页查看；这正是它能记住庞大项目、又不把上下文“撑死”的秘密。

### 6. 自动记忆库的第一个软肋：它很会记，但不太会忘

作者认为 Claude Code 的自动记忆库很强，但并不完美，第一个明显软肋就是“很会记，但不太会忘”。随着项目推进，记忆库里会逐渐堆积过期、重复，甚至互相矛盾的笔记。比如用户明明已经改了主意，项目方案已经变更，但 AI 可能还拿旧版本的记忆来指导自己。作者提到，社区在今年 3 月 Claude Code 源码泄漏时，曾发现过一个叫 **AutoDream** 的记忆整理模块，说明 Claude Code 内部可能探索过自动记忆整理方向。可问题是，截至作者讲述时，这个功能依然没有正式发布，官方文档里也没有把它作为可用能力提供出来。

### 7. 自动记忆库的第二个软肋：主索引会膨胀，而且超出安全线不会提醒

第二个软肋是主索引会不断膨胀，而且 Claude Code 不一定会主动提醒用户。作者提到，Claude Code 每次大概只加载主索引前 **200 行左右** 的内容，也就是说，如果索引写得太长，后面的记忆条目可能会被悄悄挤出去，不再被召回。更麻烦的是，这种情况不会报错，用户第一时间很难发现。结果就是：你以为记忆还在、AI 应该知道，但实际上它可能根本没读到索引后面的部分。这个问题非常隐蔽，因为它不是明显的功能故障，而是记忆召回质量慢慢下降，最后表现为 AI 越用越糊涂。

### 8. 自动记忆库的第三个软肋：没有强制记忆规则，记忆治理要靠用户主动维护

第三个问题是 Claude Code 虽然提供了很强的记忆架构，但没有强制给用户一套完整的记忆管理规则。什么内容该记、怎么分类、什么时候合并、什么时候删除，很多时候都要靠 AI 临场发挥，也要靠用户自己主动维护。作者认为，这就是“记忆架构”和“记忆治理”的区别：Claude Code 给了你长期记忆的能力，但没有完全替你管好记忆库。没有治理规则时，记忆会越来越乱，旧信息会堆积，新旧决策可能冲突，索引也可能失控增长。最终决定 AI 是越用越聪明，还是越用越糊涂的，并不是记忆数量本身，而是记忆是否被持续整理和约束。

### 9. 作者提出的实践重点是：少写入口规则、及时结束对话、主动同步记忆、定期整理

在“怎么用才对”这一部分，作者总结了几条非常具体的使用经验。第一，**CLAUDE.md 一定要精简**，不要把所有东西都往里塞，稳定、重要的规则应控制在 **200 行以内**，否则 AI 抓不住重点，也不容易照做。第二，对话要在被反复压缩之前结束，作者自己的习惯是在上下文用到一半时就准备收尾，避免既丢失原始上下文，又浪费 token。第三，重要内容要主动要求 AI 记下来，因为自动记忆库只是软约束，不能保证每个关键内容都会自动保存；收尾时可以明确说：“我要结束这段对话，请你把对话里的重要内容同步到记忆中。”第四，记忆要定期整理，让 AI 删除过期内容、合并重复内容、把索引压回安全线以内；作者强调，这一步 **90% 的人都会忽略**，但它决定 AI 的长期质量。

### 10. engramory / Ingramory 的意义：给 AI 长期记忆加一套轻量、跨 Agent 的管理规矩

视频最后，作者介绍了自己整理出的开源协议 **engramory / Ingramory**，并把它放到了 GitHub 上。它要解决的问题不是再造一个复杂数据库，而是给 AI 的 Markdown 记忆加一套规矩：让记忆分类更清楚，索引不乱长，旧信息能被及时清理，并且可以跨不同 Agent 使用。作者认为，Claude Code 内部曾探索过 AutoDream，说明自动记忆整理确实是一个重要方向；而 engramory 更像一个现在就能用的轻量实践版。它不需要数据库，不需要起服务器，也不挑具体工具，只要你的 Agent 能够读写 Markdown 文件，就能按照这套方式管理长期记忆。作者建议，具体使用时可以让自己的 Agent 去 GitHub 读取 engramory 的 README，让它一步一步教你配置。

## 值得记住的点 / 行动建议

### 1. 不要把一个对话无限用下去，要在上下文压缩前主动收尾

作者最实用的建议之一，是不要等 AI 已经明显变笨、开始答非所问之后才开新对话。长对话会不断消耗上下文窗口，过长后系统会压缩历史内容，而压缩后的信息会丢失大量细节。作者自己的习惯是在上下文大约用到一半时就准备收尾，而不是等它反复压缩。这样做的好处是，关键内容还保留在原始上下文中，可以被更完整地总结进长期记忆。如果等到上下文已经多次压缩，很多原始细节已经模糊，再让 AI 写记忆就晚了。

### 2. CLAUDE.md / 项目规则文件要短、稳、关键，不要写成百科全书

很多人一开始使用 Claude Code，会把项目里的所有背景、规则、偏好、目录说明都塞进 CLAUDE.md 或类似规则文件，作者认为这会适得其反。入口规则文件的作用不是存放全部项目知识，而是告诉 AI 最稳定、最重要、最必须遵守的规则。作者建议这类文件最好控制在 **200 行以内**，因为 Claude Code 主索引也有加载长度限制，写太长反而容易让 AI 抓不住重点。正确做法是：把通用工作习惯、关键技术栈、不可违反的项目约束写进去，而把细节、历史决策、调试经验放到独立记忆文件里。入口文件应该像“导航图”和“宪法”，不是项目的全部档案馆。

### 3. 重要结论不要指望 AI 自动记住，要在对话结束前明确要求同步记忆

作者强调，自动记忆库只是“软约束”，你不能保证 AI 一定会把你认为重要的内容保存下来。所以在每次对话收尾时，最好主动告诉 AI：“我要结束这段对话，请你把对话里的重要内容同步到记忆中。”这句话的作用是让 AI 在上下文还没有被压缩到失真之前，把关键决策、修复方案、踩坑经验、资源位置、规则变化等写入长期记忆。尤其是项目方向改变、接口约定变化、架构决策调整、bug 定位结论这类内容，如果不写进记忆，新对话很可能会回到旧思路。长期来看，这个收尾动作会决定 AI 是否能真正积累项目经验。

### 4. 定期做“记忆管理员”，删除过期、合并重复、修正冲突

作者认为，很多人只关心怎么让 AI 多记，却忽略了怎么让 AI 正确地忘。项目推进过程中，旧方案会废弃，规则会调整，目录会迁移，接口会重构，早期调试结论也可能不再成立。如果不定期整理，记忆库就会出现过期、重复、冲突的信息，AI 可能拿着旧版本指导新任务。作者建议用户定期要求 AI 清理记忆：删除过期内容、合并重复笔记、修正互相矛盾的信息，并把主索引压回安全线以内。视频中特别强调，这一步 **90% 的人都会忽略**，但它恰恰决定 AI 是越用越聪明，还是越用越糊涂。

### 5. 使用“主索引 + 分文件记忆”的结构，不要把所有细节堆进上下文

Claude Code 能处理大型项目的秘密，不是把 14000 多行记忆一次性塞给模型，而是用 148 行主索引挂载 118 个记忆文件。这个结构非常值得普通用户和团队借鉴：主索引只负责告诉 AI 有哪些类别、哪些主题、哪些文件，具体细节放在分文件笔记里。这样既能保留大量长期知识，又不会把上下文窗口撑爆。用户自己设计 Agent 记忆系统时，也应避免“所有记忆写进一个大文件”的做法。更合理的结构是：入口规则短小稳定，索引文件清晰可控，细节文件按模块、主题、决策、调试经验拆分。

### 6. 不要把密码、密钥、Token 写进记忆文件

作者最后特别提醒，千万不要把密码、密钥、Token 直接写进 AI 的记忆文件。因为记忆文件会被 Agent 读取、整理、迁移，甚至可能进入 Git 或被其他工具访问，一旦把敏感信息写进去，就会形成长期安全隐患。如果确实需要让 AI 知道某个密钥相关信息，最多只记“它放在哪里”，例如环境变量、密钥管理系统、配置文件路径，而不要记录密钥本身。这个建议尤其适合多人项目、开源项目、企业项目。长期记忆的目标是保存项目知识，不是保存敏感凭据。

### 7. 中小项目优先考虑 Markdown 记忆，不必一上来就搭复杂 RAG 数据库

作者并没有否定 RAG 向量方案，但他认为对个人项目和中小型团队来说，Markdown 文件路线已经足够好用。Markdown 的最大优势是透明，用户能直接看、直接改、直接删，也能用 Git 管理版本。相比之下，RAG 虽然能承载海量记忆和自动召回，但黑盒、难维护、需要数据库，对小团队来说运维成本更高。如果一个项目的核心问题是“新对话能不能接上任务”“项目规则能不能稳定继承”“历史踩坑能不能复用”，Markdown 记忆往往已经能解决大部分问题。等项目规模、自动检索需求、多人协作复杂度进一步上升，再考虑引入 RAG 也不迟。

### 8. 想给自己的 Agent 做长期记忆，可以参考 engramory / Ingramory 的轻量协议

作者把自己一年多使用 Claude Code 的经验整理成开源协议 engramory / Ingramory，目的就是给 AI 记忆加一套可执行的管理规矩。它不依赖数据库，不需要服务器，也不限定具体工具，只要求 Agent 能读写 Markdown 文件。对于想自己搭 Agent、写自动化助手、做项目级 AI 工作流的人来说，这种协议的价值在于提供了一套记忆分类、索引控制、旧信息清理、跨 Agent 复用的实践框架。作者建议可以让 Agent 直接去 GitHub 读取该项目的 README，再一步一步指导配置。它的定位不是复杂平台，而是一个现在就能用、成本很低的轻量实践版记忆治理方案。

## 我的点评

这个视频的核心判断很有道理：大模型长对话变糊、新对话失忆，并不是单纯靠更大上下文就能彻底解决的问题，长期项目一定需要外部化、结构化的记忆系统。作者把 Claude Code 的记忆拆成“即时上下文、手写规则、自动记忆库”三层，非常清晰，也能解释为什么同一个项目换新对话后还能接续工作。最值得普通用户借鉴的，不是某个工具本身，而是“常驻索引，细节按需召回”和“记忆需要治理”这两个原则。

需要注意的是，视频里关于 Claude Code 内部实现、AutoDream、源码泄漏等说法带有一定社区观察和作者经验判断，具体细节如果用于正式引用最好再查证。另一个可能的片面之处是，Markdown 方案虽然透明轻量，但当记忆规模极大、团队成员很多、自动检索需求复杂时，单纯 Markdown 也会遇到维护压力。普通人最实用的做法是：先把项目规则文件写短、把关键决策写进记忆、定期让 AI 清理旧笔记；不要急着追求复杂系统，先建立“对话收尾同步记忆”的习惯，效果就会明显提升。
