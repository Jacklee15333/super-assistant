## 背景与主题

这期视频围绕 OpenAI 的 **Codex** 展开，作者把它设计成“通关教程”：从安装入口、账号模型接入、任务执行逻辑、权限控制，到 Skills / MCP / Plugins，再到 PPT 生成和本地 LLM Wiki 知识库实战。作者的角度很明确：Codex 不只是程序员写代码的终端工具，而是普通人也能使用的本地 AI Agent。

视频里有不少语音识别误差，我按上下文做了校正：文中的 “Scale” 大概率指 **Skill**，“Glan / 可乐端” 指 **CLI / 终端**，“DeepStick” 指 **DeepSeek**，“RHG” 指 **RAG**，“LLM VK” 指 **LLM Wiki**，“卡帕西 / 卡巴西” 指 **Andrej Karpathy**。

整期的主线是：先让 Codex 跑起来，再让它接上模型，再理解它怎么执行任务，最后把它扩展到真实工作场景里，比如 C 盘清理清单、PPT 生成、Obsidian 本地知识库。

## 核心观点

### 1. Codex 的定位不只是“AI 编程工具”，而是本地 AI Agent

作者一开始就强调，Codex 虽然由 OpenAI 开发，常被理解为 AI 编程智能体，但官方定位远不止编程。它本质上是一个可以在本地电脑里读取信息、修改文件、调用工具、执行命令，并自主完成任务的 AI Agent。这个定位非常关键，因为它把 Codex 从“代码助手”升级成了“电脑工作代理”。

视频举了多个扩展场景：用 PPT Skill 生成演示文稿，用 Draw MCP 画架构图，用 Hyperframes 插件做动画视频，结合 Obsidian 整理知识库。这说明 Codex 真正的价值不是单次问答，而是进入真实文件系统和工作流。作者想传达的是：普通用户不需要先成为程序员，也可以通过桌面端、插件和 Skill，把 Codex 用在内容整理、资料生成、知识库维护等任务里。

### 2. 新手优先选择桌面 App，开发者再考虑 CLI 或 IDE 插件

视频把 Codex 的入口分成三类：**桌面 App、CLI 终端、IDE 插件**。作者建议新手优先选择桌面 App，因为它像普通电脑软件一样，有可视化界面，可以看到对话、项目、任务过程、插件和权限，对初学者更友好。

如果用户本来就是开发者，习惯在终端里查看项目、执行命令，那么 CLI 更直接、轻量，也更适合放进真实开发流程。如果每天都在 VS Code 里写代码，则 IDE 插件更顺手，因为不用离开编辑器就能打开 Codex 对话窗口，还能直观看到它改了哪些文件。作者总结说，这三种方式基本满足 99% 的个人使用场景；至于云端使用、GitHub 接入、Codex SDK、MCP 等高级玩法，可以先留个印象，后面再学。

### 3. Codex 只是 Agent 外壳，真正的大脑是背后的模型接入

第二关的重点是账号、模型和工作目录。作者用一个很直白的比喻：Codex 是装在电脑上的 Agent，模型才是它背后负责思考、判断和生成内容的大脑。所以要真正让 Codex 干活，第一步不是疯狂下命令，而是把模型接好。

接入方式大致有两条路：第一是官方账号订阅，适合新手，因为登录、订阅、用量、模型、插件都在官方体系里处理，省心但有额度限制；第二是第三方 API 接入，适合不方便使用官方订阅、希望使用国产模型，或者团队已经准备好 API 方案的人。作者特别提到 Free 方案现在从周额度变成月额度，适合入门验证，但不能当主力；Plus 能做基础体验，但高强度使用会很快碰到 5 小时限额；如果长期高频使用，需要认真评估 Pro。

### 4. 作者认为 Pro 20X 可能比 Plus 和 Pro 5X 更适合高频用户

视频里对官方订阅方案做了比较。Free 方案只适合跑几次简单对话，主要用于验证 Codex 能不能用；Plus 是很多人已经习惯的方案，日常对话和轻度任务够用，但如果让 Codex 连续读项目、改文件、跑任务，5 小时限额会很快耗尽。

作者还提到最近很多开发者感觉 OpenAI 在逐步收紧 Plus 的可用额度，所以他不认为 Plus 是最具性价比的 Codex 主力方案。再往上是 Pro，常见有 5X 和 20X 两种额度方案，可以简单理解为 Plus 的 5 倍和 20 倍。作者的观点有点反直觉：虽然 5X 比 20X 便宜一倍，但他认为 20X 更有性价比，因为到了这个档位后，不用一直陷入 token 焦虑，更容易把 Codex 变成真正能撬动业务效率的生产力杠杆；如果一个人用不完，也可以找小伙伴合租。

### 5. 第三方 API 接入的关键，是让 Codex 指向兼容的模型服务商

作者解释了为什么 Codex 可以接第三方 API：因为 Codex 本地有配置文件，可以指定模型服务商、请求地址和密钥。只要第三方提供兼容的 Base URL，并支持 Codex 所需的接口形式，Codex 就能调用它完成模型处理。

视频中推荐新手可以先用 **Codex++** 这类第三方增强工具，它是面向 Codex 应用的外部启动器和管理工具，把第三方 API 接入做成图形界面。以 DeepSeek 为例，至少要配置四项：接入类型选择纯 API，填写 Base URL，填写 API Key，填写模型名称。保存后先测试连通性，测试通过再从 Codex++ 入口启动 Codex；如果模型列表不显示、配置没生效，要先检查是不是从 Codex++ 启动，以及 Codex++ 是否需要更新。

### 6. Codex 的工作方式，核心是 Project + 工作目录 + 权限边界

作者特别强调了“项目 / 工作目录”的概念。一个软件项目通常是围绕同一个目标组织起来的一组文件，里面可能包括代码、文档、配置、图片和脚本。你把一个文件夹交给 Codex，就等于告诉它：这次任务只围绕这个范围展开。

这样做有两个好处：第一是更安全，避免 Codex 一上来就在桌面、系统目录或真实项目里乱动；第二是注意力更集中，它看到的文件越明确，越容易判断哪些内容和当前任务相关。作者建议第一次实操先准备一个干净文件夹，文件夹名尽量用英文和短横线，然后在 Codex 里新建 Project，把这个文件夹作为工作目录。接着让 Codex 生成第一份 Markdown 文件，你就能感受到它已经从普通聊天窗口变成了能围绕本地目录搜资料、整理内容、写入文件的 Agent。

### 7. 看懂 Codex 执行任务的五个动作，才能真正控制 Agent

第三关讲的是 Codex 接到任务后的执行过程。作者把一次任务拆成五个动作：第一，理解目标，判断你是要写资料、写文件、做 PPT、操纵网页，还是整理知识库；第二，读取上下文，包括 Project 绑定的文件夹、手动添加的文件、截图、网页资料，或前面对话内容。

第三，选择工具；如果只是普通文本问题，可以直接回答，涉及网页就可能调用浏览器能力，涉及本地文件就访问工作目录，涉及 Skill 就先读取对应操作说明。第四，执行并等待确认；只要没有完全放开权限，Codex 遇到联网、写文件、执行命令等动作时会停下来请求批准。第五，输出结果；结果可能在聊天窗口里，也可能是一份 Markdown 文件、一组代码脚本、一份 PPT，或者一段需要你复核的任务摘要。这个拆解的意义是：用户不应该把 Agent 当黑箱，而要知道它每一步在做什么，什么时候该放手，什么时候该介入。

### 8. 任务排队、插队和并行，是使用 Codex 的重要操作习惯

作者提醒，新手很容易把多个任务塞进同一个对话里，导致任务排队。Codex 默认会按顺序处理同一对话里的多个任务，这本身没问题，但如果你想让新要求影响正在执行的任务，就要用任务旁边的引导或追加功能，把补充要求塞进正在运行的任务里。

如果你想同时开展另一个方向，就不要硬塞进当前对话，而是新建一个对话。同一个 Project 下面可以有多个对话并行推进，它们都围绕同一个工作目录，但每条对话最好只负责一个清晰的任务边界。这个建议非常实用，因为 Agent 的上下文会影响判断；如果一个对话里混入太多不同目标，很容易导致执行混乱。作者本质上是在教一种 Agent 项目管理方法：同目录、多线程、单对话单任务。

### 9. 权限控制是 Codex 真正进入本地电脑前必须理解的安全门槛

视频里把权限模式讲得比较细。新手阶段建议保持默认权限，Codex 可以在当前工作区里处理文档、代码和常规本地任务，但一旦要求访问工作区外文件、联网或调用更敏感的命令，就会请求用户批准。这个工作区边界就是“沙盒”，相当于先给 Codex 圈一块活动范围，让它默认只在当前项目里行动。

自动审核适合步骤很多、频繁弹窗影响效率的任务，低风险操作可以自动放行，高风险操作仍回到用户这里确认。完全访问是最高权限，只适合在任务边界清晰、风险可控、结果可回滚时临时打开；打开前最好让 Codex 说清楚它准备运行哪些命令、修改哪些文件、访问哪些外部资源，并确认项目有 Git 或备份。自定义权限属于进阶能力，可以把目录、网络访问、命令审批等规则固定下来。

### 10. Skills、MCP、Plugins 是 Codex 扩展生产力的三件套

第四关开始讲 Codex 的扩展体系。作者把 **Skill** 解释成给 Codex 看的操作手册，核心文件通常是 `SKILL.md`，里面写技能名称、适用场景和具体指令，复杂的还会配可执行脚本、参考资料和模板。比如生成 PPT，如果每次都从零告诉 Codex 如何分析主题、拆页面结构、生成文件、检查页面比例和文字溢出，会非常繁琐；有了 PPT Skill，这些固定流程就可以提前沉淀进说明书。

**MCP** 全称是 **Model Context Protocol**，是 Anthropic 提出的开放协议，用来统一连接 AI 模型和外部工具。放到 Codex 里，可以理解为给 Agent 接浏览器、数据库、GitHub 等工具和上下文的标准接口。**Plugin** 则更像可安装的能力包，一个 Plugin 里可能包含多个 Skills，也可能包含 MCP Service。作者总结得很清楚：Skill 负责沉淀流程，MCP 负责把工具和数据接近 Agent，Plugin 负责把这些能力打包安装。

### 11. PPT Master 案例说明：Agent 可以把一句话需求变成可编辑 PPTX

视频第二个实战副本是用 Codex 调用 PPT Skill 生成演示文稿。作者选了 GitHub 上已经有 3 万多 Star 的开源 Skill：**PPT Master**。选择它的原因很直接：真正的 PPT 不能只是图片或不可编辑文件，如果不能在 PowerPoint 里打开、不能编辑，就不应该叫 PPT。

实操过程是把 PPT Master 的 GitHub 主页丢给 Codex，让它先帮忙安装 Skill；安装完成后，在聊天窗口用斜杠调出 PPT Master 技能，如果没有显示，可以重启 Codex。正式任务中，作者让 PPT Master 参考一张 PPT 风格图，把一份文档内容制作成 PPT；如果需要图片，就调用 ImageGen 图像生成技能。Agent 会先读取 PPT Master 和 ImageGen 的技能说明，再分析文档内容、提炼标题、拆分页面、判断哪里需要图表或配图，并在正式生成前给出设计方案确认清单，包括画布格式、页面结构、目标受众、视觉风格、色彩方案等。

### 12. LLM Wiki 案例是整期视频最有价值的部分：让 Codex 维护持久知识库

最后一个实战副本来自 Andrej Karpathy 的 **LLM Wiki** 思路。作者说，现在很多知识库使用 **RAG / Retrieval-Augmented Generation（检索增强生成）**，但 Karpathy 认为 RAG 的问题在于：每次提问，模型都要从零开始重新发现知识。比如一个问题需要综合 5 篇文档，RAG 会检索、拼接、生成；第二天你再问类似问题，它又重复一遍。

LLM Wiki 的思路是把知识库分成三层：第一层是原始资料层，负责收集论文、文章、文案等素材，大模型可以读取，但不要改写；第二层是 Wiki 层，由大模型维护，可以整理目标、生成摘要、提取实体和概念、做比较分析和综合，也可以创建页面、更新页面、维护页面之间的交叉引用；第三层是 Schema / 规范层，可以理解为整套知识库的操作规范，放在 Codex 里就可以是 `agents.md`。作者用 Codex 参考 Karpathy 的 GitHub Gist，在 Obsidian 里搭建本地 LLM Wiki，把不可变资料放进 `raw`，把 Agent 维护的持久知识页放进 `wiki`，再用 `agents.md` 规定后续 Agent 的操作准则。这个案例真正体现了 Agent 的长期价值：不是一次性回答，而是持续维护一套可复用知识资产。

- LLM Wiki 思路来自 AI 研究者 **Andrej Karpathy**。
- Karpathy 批评传统 RAG 的问题：每次提问都要重新检索、拼接、生成，相当于重复发现知识。
- LLM Wiki 分三层：原始资料层、Wiki 层、Schema / 规范层。
- 原始资料层负责存放论文、文章、文案等不可变素材。
- Wiki 层由大模型维护，负责摘要、实体提取、概念整理、比较分析、页面创建和交叉引用。
- Schema / 规范层负责定义知识库操作规则，在 Codex 里可体现为 `agents.md`。
- 作者用目录结构落地：`raw` 放不可变资源，`wiki` 放 Agent 维护的持久知识页，`agents.md` 作为后续 Agent 操作准则。
- Codex 可用 `/init` 初始化 `agents.md`。
- 最终知识库可以在 Obsidian 里看到 Markdown 页面形成知识图谱。

## 值得记住的点 / 行动建议

### 1. 新手不要一上来折腾终端，先用桌面 App 跑通闭环

如果你是零基础，最优路线不是 CLI，也不是 VS Code 插件，而是先安装 Codex 桌面 App。桌面端能直观看到对话、项目、任务过程、插件和权限，最适合建立对 Agent 工作方式的整体感知。

第一阶段的目标很简单：能打开软件，能看到登录入口，能完成登录，能问一句“用一句话解释 Codex 是什么”，并得到正常回复。做到这里就已经完成了“可用性验证”。不要一开始就陷入环境变量、Node、NPM、Git、终端命令这些细节，否则很容易还没开始用 Agent，就先被工程环境劝退。

### 2. 先准备干净工作目录，不要直接把真实桌面或重要项目交给 Codex

第一次让 Codex 处理本地文件时，最好新建一个空文件夹，名字用英文和短横线，例如 `codex-demo`、`ai-workspace`、`llm-wiki-test`。这个文件夹就是 Codex 的活动范围，也就是它默认读取、写入、修改文件的边界。

这么做的价值很大：一方面可以防止 Codex 误动真实项目、桌面文件或系统目录；另一方面也能让 Codex 的注意力集中在当前任务上。Agent 看到的文件越少、上下文越清晰，它越容易做出正确判断。等你熟悉它的行为模式后，再逐步把它接入真实项目。

### 3. 模型方案要按使用强度选，不要只看月费

如果只是体验 Codex，Free 可以验证能不能跑通；如果是轻度使用，Plus 能做一些基础任务；但如果你真想让 Codex 连续读项目、改文件、生成文档、跑命令、调工具，Plus 很快会遇到额度和 5 小时窗口限制。

作者的判断是，高频使用者要认真评估 Pro，尤其是 20X 方案。这个观点背后的逻辑是：Agent 的价值来自连续工作和复杂任务拆解，如果你总是在 token 和额度上焦虑，它就很难成为生产力杠杆。对于团队或几个朋友共用的场景，20X 合租可能比每个人单独买 Plus 更划算。

### 4. 第三方 API 接入要先确认兼容性，再考虑长期使用

如果你不方便使用官方订阅，或者想接国产模型，可以用第三方 API。新手可以先用 Codex++ 这种图形化工具，避免一开始就手动编辑配置文件。配置时核心是四项：Base URL、API Key、模型名称、接入类型。

但要注意，Codex++ 属于第三方增强工具，不是 OpenAI 官方主体功能。Codex App 更新后，Codex++ 可能需要等待适配，出现菜单不显示、配置不生效、模型列表不出来，都不一定是你的 API 错了。排查顺序应该是：是否从 Codex++ 入口启动、配置是否保存、连通性测试是否通过、Codex++ 是否需要更新。

### 5. 权限默认保守，等任务边界清楚后再放权

涉及本地文件、系统目录、命令执行、联网访问时，权限控制必须认真对待。新手阶段建议用默认权限或请求批准权限，让 Codex 在关键动作前停下来确认。尤其像 C 盘清理、系统目录排查、软件缓存处理这类任务，绝不能直接完全放开。

如果要开完全访问，至少满足几个条件：任务目标明确、工作目录安全、项目有 Git 或备份、Codex 先说明准备执行哪些命令、修改哪些文件、访问哪些资源。完全访问不是不能用，而是要在可回滚、可审计、范围明确的情况下用。否则 Agent 的效率优势，可能会变成误操作风险。

### 6. 复杂任务先用计划模式，不要直接让 Codex 开干

当任务还比较模糊，或者步骤很多时，最好先进入计划模式。计划模式的作用是让 Codex 在执行前先理解上下文、提出澄清问题、拆解步骤，并生成一份可审阅的执行计划。你可以把它理解成“施工图”：先看它准备怎么做，再决定是否开工。

这对 C 盘清理、项目迁移、PPT 生成、知识库搭建尤其重要。因为这些任务不是单一问答，而是包含多步骤、多文件、多权限判断。计划先行可以显著降低误操作，也能让用户更容易在关键节点介入。

### 7. 同一个 Project 可以多对话并行，但每条对话只做一个清晰任务

如果你在同一对话里连续发很多任务，Codex 通常会排队处理。这个机制并不坏，但如果任务之间目标不同，就容易污染上下文。更好的做法是：同一个 Project 下可以开多个对话并行推进，但每条对话只负责一个明确任务。

例如，同一个知识库项目里，一条对话负责整理论文摘要，一条对话负责生成索引，一条对话负责更新 `agents.md`，一条对话负责制作 PPT。它们都共享同一个工作目录，但各自任务边界清晰。这样既能并行利用 Agent，又能避免上下文混乱。

### 8. Skills 的价值在于把重复流程沉淀成 SOP

PPT 生成案例说明，真正提高效率的不是每次写更长 prompt，而是把稳定流程沉淀成 Skill。比如做 PPT 的固定流程包括：分析主题、拆结构、规划页面、确定视觉风格、生成文件、检查文字溢出、保证 PowerPoint 可编辑。

如果每次都靠人工把这些步骤重新说一遍，效率很低，也容易漏步骤。把它们写进 `SKILL.md` 后，Codex 就能按说明自动推进。对个人和小团队来说，值得沉淀的 Skill 包括：竞品分析、日报生成、文档转 PPT、文章入库、项目初始化、代码审查、视频文稿整理等。

### 9. MCP 和 Plugin 不要死记概念，要从“接工具”和“打包能力”理解

MCP 的本质是让 AI Agent 能以统一方式连接外部工具和上下文，比如浏览器、数据库、GitHub、文件系统、企业知识库等。Plugin 则是把一组能力打包安装，里面可以包含多个 Skills，也可以包含 MCP Service。

所以理解这三者的最好方式是：Skill 是流程说明书，MCP 是工具接口标准，Plugin 是能力包。这个理解非常实用，因为未来 Agent 的竞争力不会只来自模型本身，而是来自它能接多少工具、能否按稳定流程工作、能否被安全地安装和管理。

### 10. 最值得普通人实践的是 LLM Wiki：把 AI 从一次性问答变成长期知识资产

LLM Wiki 案例是整期视频最值得深入做的部分。传统 RAG 的问题是每次提问都重新检索、重新拼接、重新生成，知识没有真正沉淀下来。LLM Wiki 的思路是让大模型持续维护一层 Wiki，把摘要、实体、概念、关联、比较分析都变成可长期复用的页面。

这很适合用在个人知识库、自媒体素材库、行业情报库、竞品监控库、研究笔记库。具体做法是：`raw` 放原始资料，保持不可变；`wiki` 放 Agent 生成和维护的知识页；`agents.md` 写清楚操作规范，规定 Agent 怎么入库、怎么摘要、怎么交叉引用、怎么保留来源。这样 AI 不只是回答问题，而是在帮你持续建设一套可复用的认知资产。

## 我的点评

这期视频的价值在于，它没有把 Codex 只讲成“更强的代码助手”，而是把它放在本地 Agent、工作目录、权限控制、Skill 扩展和知识库建设的框架里，这个理解是对的。尤其是“工作目录 + 权限边界 + 计划模式 + Skills”的组合，基本就是普通人安全使用 Agent 的核心方法。

需要注意的是，视频里有些订阅档位、额度变化、第三方工具兼容性属于动态信息，具体价格和限制要以 OpenAI 官方当前页面为准，不能完全按视频里的说法长期记。第三方 API、Codex++、PPT Master、ImageGen 等工具链也存在更新断裂、权限风险和适配成本，真正用于生产前要先做小项目验证。

我认为普通人最应该立刻复制的不是“装一堆插件”，而是先建立一个干净 Project，让 Codex 生成 Markdown、整理资料、写清单，再逐步沉淀自己的 `agents.md` 和 Skill。真正长期有价值的方向，是把 Codex 从临时聊天工具变成“可审计、可回滚、可复用”的本地工作流系统。
