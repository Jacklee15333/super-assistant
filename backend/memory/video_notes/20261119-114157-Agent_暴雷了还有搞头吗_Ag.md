## 核心观点

### 1. Agent 暴雷的不是整个技术方向，而是“只会调 API”的浅层开发模式
主讲人开篇就提出一个非常明确的判断：“有一部分 Agent 已经暴雷了，就是调 API 的那帮人。” 这里的“暴雷”并不是说 Agent 技术彻底失败，而是指过去被大量包装、宣传和追捧的低门槛 Agent 开发模式，正在失去原本的市场吸引力。此前，一些工程师只需要掌握传统后端开发，再学会调用大模型 API、使用 Agent 框架，就可以开发问答机器人、客服机器人或简单业务助手，并以此进入 AI 应用开发岗位。但随着企业尝试把 Agent 部署到真正复杂的业务流程中，简单调用接口所能解决的问题越来越有限，工程师也开始面临更高的技术要求。
这一变化背后的核心逻辑是：企业购买的不是“接入了 AI”这个标签，而是 AI 系统实际解决问题的能力。 一个 Agent 能成功运行、接收用户输入并返回结果，并不意味着它能够准确、稳定、低成本地完成企业的重要业务任务。因此，低端 Agent 开发能力的价值可能被压缩，但真正能够解决企业复杂问题的 Agent 工程能力反而可能更加重要。

### 2. 企业对 AI 的最大误解，是把当前大模型当成已经实现的 AGI
主讲人举了一个具体的企业会议案例：上周，他参加了一场线上 To B 会议，对方企业的一位业务部门经理并不懂技术，却认为只要企业拥有 AI，就可以解决绝大多数业务问题。在这位经理的设想中，自己现在管理着 20 名员工，这些人未来都可以被 20 个 Agent 替代，从而实现大规模自动化和人员精简。主讲人认为，这种思维反映了一个普遍现象：许多人把现阶段的大模型神化了，误以为我们已经进入 AGI（Artificial General Intelligence，通用人工智能）时代。
但现实是，能够自然对话、生成文章、回答常识问题，并不等于具备完成复杂专业工作的可靠能力。企业员工在实际工作中不仅要理解任务，还需要掌握行业知识、处理异常情况、执行复杂流程、判断结果是否可靠，并承担相应的业务责任。现阶段的 Agent 在部分任务上可以替代人工操作或提升效率，但不意味着可以直接按照“一个员工对应一个 Agent”的比例替换整个部门。把 AI 当作无所不能的数字员工，是企业在规划 Agent 项目时容易犯下的根本性认知错误。

### 3. 2025 年企业集中接入 Agent，经过一年检验才发现落地难度被严重低估
按照主讲人的观察，许多企业从 2025 年开始，就急切地希望把 Agent 接入现有业务系统。当时企业对大模型的预期很高，希望快速完成智能客服、自动问答、知识检索、流程自动化，甚至替代部分专业岗位。但经过大约一年的实际项目检验，企业逐渐发现，很多 Agent 只能在演示环境中表现良好，一旦进入复杂、真实、多变的业务场景，就会暴露出各种问题。
主讲人认为，这些问题往往不能通过简单修改几条提示词或替换一个 API 来解决，而是需要在两个关键层面持续进行精细化调整：底层模型层面，以及 Harness（智能体运行与控制框架）层面。 前者涉及模型自身的知识、能力和对垂直领域任务的适应程度，后者涉及如何组织模型调用、工具使用、上下文、执行流程以及错误处理等。两个层面都需要专业工程师参与，而不是完全依赖非技术人员通过可视化配置就能解决。
这一现象说明，AI 项目的难点已经从“能不能把模型接进来”，逐渐转移到“接进来以后，能不能长期、稳定、可靠地创造业务价值”。

### 4. Agent 有明显的应用深度差异：浅层任务容易做，专业任务才是真正的技术门槛
主讲人并没有否认简单 Agent 的实际价值，而是明确区分了不同层次的需求。对于通用问答、基础客服、日常聊天等场景，只要使用现成的大模型 API，再搭建合适的后端服务，确实可以较快开发出能够上线、能够落地的产品。但这类产品解决的是相对浅层的问题，模型对任务的理解、准确性与执行流程往往不需要非常复杂的专业约束。
一旦 Agent 进入医疗、电力、法律等专业场景，情况就完全不同：模型不仅要理解自然语言，还要正确理解行业术语、专业规范、复杂条件以及专业推理逻辑。主讲人以自己为例，表示如果让“小朱老师”去看病历，可能连病历内容都看不懂；让他处理法律文本，也可能不理解其中许多专业用词。如果普通人需要长期专业训练才能胜任某些工作，就不能简单假设通用 AI 模型天然具有可靠完成这些任务的能力。
这一例子揭示了 Agent 开发中非常重要的差异：让模型“能回答问题”，与让模型“能够可靠地处理专业业务”，是两种不同难度的工程任务。

### 5. 仅靠 Harness 架构无法解决所有问题，模型自身的能力也可能成为瓶颈
视频反复强调 Harness 的作用与能力边界。Harness 可以理解为围绕大模型构建的一套执行与控制机制，通常涉及任务编排、工具调用、状态管理、上下文处理、错误重试、结果校验以及执行过程管理等，目的是让模型能够更有效地完成复杂任务。但主讲人指出，当问题本身超出了模型的知识范围、理解能力或专业推理能力时，即使 Harness 做得再好，也不一定能够从根本上解决问题。
例如，一个通用模型如果无法准确理解某类电力工程规范，那么在外面再增加一套复杂的任务执行架构，也无法保证模型对专业概念的理解就会自动变正确。在这种情况下，问题可能已经不在执行流程，而在模型本身的能力与专业适配程度。主讲人因此强调，工程师需要知道什么时候应该优化 Harness，什么时候必须进一步调整底层模型。
这里的关键不是 Harness 没有价值，而是工程师不能把某一种技术手段当作解决所有问题的万能方案。 真正专业的 Agent 开发，首先要能识别问题到底发生在哪一层，再选择对应的解决方式。

### 6. 复杂垂直行业需要专业领域适配，不能指望通用模型天然掌握所有知识
主讲人重点提到电力、医疗和法律三个典型领域。在电力企业中，存在大量物理学、电学知识、国家标准、专业术语以及行业规范，通用模型未必能够正确理解这些知识之间的关系，更不一定能按照行业标准执行精确判断。如果要让 AI 深入电力业务，就需要使模型的能力和输出更加贴近电力行业的专业要求，而不是永远停留在普通互联网文本的知识分布上。
医疗领域同样如此：模型需要理解病历、临床术语、诊疗逻辑以及相关专业规范，不能因为它能够与患者流畅聊天，就认为它具有可靠的医疗判断能力。法律领域也存在大量特殊用语、严谨的概念边界和复杂的规则适用条件，通用模型回答得通顺，并不能证明其结论准确。主讲人将这一过程形象地描述为：让底层模型向特定垂直行业“偏”，而不是始终保持完全通用的状态。
从更完整的工程实践理解，专业适配可以涉及领域数据训练、微调、检索增强生成（RAG）、专业工具接入、规则校验及专家反馈等多种路径，并不意味着每一个垂直领域 Agent 都必须重新训练模型。视频真正强调的是：专业能力必须通过技术和业务工程建设来实现，而不是通过简单调用通用模型自动获得。

### 7. Prompt Engineering 有明确能力边界，只会写提示词不足以应对复杂项目
视频中，主讲人特别批评了一种观点：有人认为，Agent 遇到复杂专业问题时，只要把提示词（Prompt）写得更好，就能够解决。他认为，说这种话的人往往缺乏真实项目经验，因为他们没有理解提示词的能力边界。提示词确实可以帮助模型理解任务、约束输出格式、明确角色、提供示例或改善执行步骤，但它不等于能够修改模型内部所有知识和能力。
例如，当模型对一条专业规范本身就缺乏正确理解时，仅仅在提示词中要求“请严格按照专业标准回答”，并不能保证模型因此掌握该标准。同样，如果模型缺乏完成某类专业推理的能力，反复增加“请认真思考”“你是行业专家”等指令，也不一定能解决实际问题。主讲人用一句带有强烈反问意味的话表达了这种观点：“提示词要能解决，那还要这帮工程师干什么？”
从技术角度看，提示词工程仍然十分重要，但它应该与知识系统、模型适配、工具调用、评估体系和工程控制共同发挥作用。真正有价值的工程师，必须知道提示词能解决哪些问题、不能解决哪些问题，以及什么时候应该采用其他技术方案。

### 8. 后端工程师转型 Agent 开发的门槛正在提高，传统开发技能不再构成充分优势
主讲人指出，近些年传统后端开发领域的就业竞争已经非常激烈，因此不少后端工程师开始转向 Agent 开发。由于目前很多 Agent 项目以 Python、Java 后端系统为基础，工程师只需要学习相应的大模型 SDK、Agent 框架和 API 接口，就能够比较快地搭建应用。这样的转型在 Agent 应用早期阶段具有一定市场空间，因为当时企业普遍处于探索阶段，对简单接入模型的需求较多。
但随着越来越多传统后端工程师掌握同样的技能，单纯会调 API、搭建流程、封装接口的能力很容易趋于同质化。主讲人认为，如果一个工程师对 AI 的理解始终停留在 API 层面，却无法处理模型能力、评估、垂直领域适配等深层问题，那么其技术竞争力就十分有限。他甚至用夸张的说法表示，这类工程师未来找工作可能需要依靠“985 学位”等其他竞争条件才更有机会。
这里的“985 学位”是主讲人用来强调竞争激烈程度的修辞，并不是经过数据验证的招聘硬性门槛。 更值得关注的信号是：单纯把传统后端技术叠加大模型 API，可能越来越难以构成有辨识度的职业优势。

### 9. 2026—2027 年 Agent 岗位可能出现更明显的分层，真正的机会在深度工程能力
主讲人给出了一个比较明确的时间判断：从 2026 年夏天开始，以纯后端开发为主的 Agent 工程师会越来越难获得市场认可；进入 2027 年，如果工程师仍然把 AI 当作普通 API 使用，就业竞争可能更加困难。其背后的逻辑是，企业早期已经完成了大量浅层 Agent 尝试，而下一阶段需要处理的任务将更复杂、更专业，也更依赖对模型和业务流程的深入理解。
随着 Agent 在行业内部进一步发展，企业对人才的要求可能从“能够把功能做出来”，转向“能够定位失败原因、改善模型表现、构建可靠系统、解决专业问题”。主讲人还提到 DeepSeek 及其 Harness 相关架构，意在说明：当部分框架能力可以通过开源项目获得时，仅仅掌握框架本身，未必足以形成长期竞争壁垒。需要注意，文字稿未提供具体开源项目名称，因此不能据此认定 DeepSeek 已经开源了某一套完整、通用的 Agent Harness 系统。
视频最终要传递的职业判断是：Agent 方向并没有失去前途，但会使用现成框架的人与能够解决深层技术问题的人，未来的市场价值可能越来越不同。 这是一种基于主讲人项目观察作出的行业趋势预测，而不是已经得到完整就业数据验证的结论。

| 电力行业 | 物理学、电学、国家标准和大量专业术语 | 理解专业概念、技术约束和行业标准 |
| 医疗行业 | 病历、专业医学知识 | 正确处理专业信息，避免不可靠的理解和判断 |
| 法律行业 | 专业法律用语、法律文本 | 理解严谨的专业概念和文本含义 |

这三个行业的共同特征，是业务知识高度专业化，且错误结果可能带来严重后果。因此，对 Agent 的要求不能仅仅是回答流畅，还必须考虑准确性、可验证性以及任务的风险程度。

### 五、浅层 Agent 与深层 Agent 的本质区别

| 比较维度 | 浅层 Agent | 深层专业 Agent |
| --- | --- | --- |
| 典型业务 | 简单问答、通用客服、聊天助手 | 医疗、电力、法律等专业业务 |
| 模型能力要求 | 通用语言理解、基础信息处理 | 深度专业知识、复杂条件判断与推理 |
| 开发方法 | API 调用、简单 Prompt、框架封装 | 可能涉及模型适配、知识工程、复杂编排与评估 |
| 主要难点 | 快速集成、实现功能 | 准确性、稳定性、复杂任务完成率 |
| 工程师核心价值 | 把功能搭建出来 | 识别能力瓶颈并持续解决问题 |
| 长期竞争优势 | 较容易被模仿 | 更依赖综合技术能力与实际项目经验 |

这一分类是对视频观点的归纳，并非行业统一的技术分级标准。

## 金句摘录

### 1. 关于 Agent 暴雷的本质
“有一部分 Agent 已经暴雷了，就是调 API 的那帮人。”

理解： 主讲人真正批评的不是 Agent 技术，而是缺乏深层工程能力、只依靠接口封装实现功能的开发模式。

### 2. 关于 AI 被过度神化
“很多人神话了 AI，就是我只要有个大模型，我什么问题都解决了。”

理解： 大模型能够解决大量问题，但不能因此推导出它具有处理所有专业任务的能力。AI 项目最大的风险之一，是预期与现实能力之间的落差。

### 3. 关于企业对 AGI 的误解
“很多人对于 AI 的理解，就是把它想象成终结者了，到达了这个 AGI 通用人工智能的时代了。事实上没有。”

理解： 这是对企业“AI 可以直接全面替代人工”这一认知的批评。当前 Agent 仍然需要明确任务边界、专业知识支持和可靠的工程控制。

### 4. 关于通用模型的局限
“你真的以为 AI 是万能的？AI 不是万能的。你跟它聊天，那是太初级的应用了。”

理解： 自然语言交互只是大模型能力的一种体现，而真实业务场景中的专业准确性与稳定执行能力，才是更困难的工程挑战。

### 5. 关于 Prompt 的能力边界
“光靠写提示词就能把这个问题解决？一看就是没做过项目，他根本就不知道提示词的能力边界在哪。”

理解： Prompt Engineering 很重要，但它不能代替知识补充、模型能力适配、系统工程和验证机制。对技术手段边界的理解，是工程经验的重要体现。

### 6. 关于后端工程师的职业竞争
“就是同样的一批人，多调了个 API，市场就认可你了？那不可能的。”

理解： 给传统技能增加一个时髦的技术标签，不等于获得了真正的竞争优势。能够创造差异化价值的，仍然是解决复杂问题的能力。

## 值得记住的点 / 行动建议
视频主要是行业判断，并没有提出完整的学习计划。以下将其观点转化为可执行建议，其中具体技术路线和实践方案属于笔记延伸，不应理解为主讲人逐项给出的原话。

### 1. 不要再把“会调用大模型 API”当成 Agent 开发的最终目标
API 调用当然是学习 Agent 的必要起点，但它只能证明你能够接入模型，并不能证明你可以处理复杂的真实任务。
对学习者来说，最初可以通过调用大模型 API 完成基础聊天、工具调用、结构化输出和简单知识问答。但完成这些功能之后，应该进一步研究：为什么模型会答错？为什么工具调用会失败？为什么同一个问题会得到不一致的答案？为什么一个演示效果很好的 Agent，上线之后却容易出问题？
建议把学习目标从“学会某个框架的所有 API”改成“能够独立开发、调试、评估并优化一个 Agent 系统”。
可执行做法： 选择一个已经开发完成的简单 Agent，主动设计 30—50 个不同类型的测试用例，包括正常请求、模糊请求、超出知识范围的问题、错误工具参数以及多步骤任务。记录失败结果，再逐一定位问题来源，而不是只展示几次成功运行的截图。

### 2. 建立模型能力边界意识，学会定位 Agent 的错误来源
这是视频中最值得深入理解的工程思维之一。
Agent 出现问题，原因可能来自不同层次：模型不具备相关知识、检索系统没有找到正确内容、提示词存在歧义、上下文不完整、工具调用出错，或者业务流程本身设计不合理。如果无法区分这些原因，就容易陷入无效调试，例如不断修改 Prompt，却没有处理真正缺失的专业知识。
可以用一个实际排查顺序：
Agent 失败问题诊断流程
首先复现错误并记录执行过程
输入、上下文、工具调用、输出和预期结果

确认错误发生在哪一层
业务流程 / 工具 / 检索 / Prompt / 模型

流程或工具问题
优化 Harness、工具接口、异常处理和执行控制

知识或模型问题
尝试 RAG、领域数据、模型替换或微调

通过评估集验证修复是否有效
同时检查准确率、成本、延迟以及是否引入新问题

这套思路的价值在于：不再凭感觉调 Agent，而是依靠可复现的失败案例和可衡量的指标做工程优化。

### 3. 系统学习 Harness，而不是停留在现成框架的表层使用
Harness 是 Agent 工程中值得长期投入的能力方向，但学习时不应只背某个框架的代码模板。
建议重点掌握工具调用（Tool Calling）、任务编排、上下文管理（Context Management）、状态管理、异常处理、执行限制、结果校验以及可观测性（Observability）。这些机制共同决定了 Agent 能否可靠地执行一个实际任务。与此同时，还要理解工具权限、操作确认和危险任务的人工审核机制，避免 Agent 在生产环境中执行超出授权范围的动作。
例如，可以开发一个需要先查询数据、再进行计算、最后生成报告的 Agent，故意模拟数据库超时、工具返回错误、数据缺失等情况。观察系统是否能够正确重试、停止执行、提示人工处理，并保留必要的操作记录。
真正理解 Harness，意味着你不仅知道如何让 Agent 开始执行，还知道如何控制它、观察它，以及在必要时安全地终止它。

### 4. 至少选择一个垂直行业，深入理解专业知识与业务流程
主讲人多次强调医疗、法律、电力等垂直行业，是因为这些领域并不是靠通用聊天能力就能轻松解决的问题。
对于准备从事 Agent 开发的学生或工程师，可以先选择一个相对熟悉、资料容易获取的方向，比如财务报表、企业内部知识库、软件开发辅助、公开法律法规检索或工业设备手册问答。不要一开始就追求打造“万能 AI 员工”，而应该围绕具体领域中的一个真实需求设计系统。
例如，在企业设备维护场景中，可以开发一个基于设备手册和故障处理规范的助手。要求它不仅回答故障原因，还要说明依据来自哪份文档、哪一章节；如果缺少足够信息，就应明确表示无法判断，而不是编造维修方法。
这种项目比普通聊天机器人更能体现专业知识工程、检索能力、工作流设计和输出可靠性。

### 5. 理解 Prompt、RAG、微调与 Harness 分别解决什么问题
视频批评了对 Prompt 和 Harness 的过度依赖，但不能由此推导出所有 Agent 项目都必须微调模型。
实际工程中，更有价值的能力是根据问题选择最合适的技术路线。

| 技术手段 | 主要解决什么问题 | 典型使用场景 |
| --- | --- | --- |
| Prompt Engineering（提示词工程） | 明确任务、规则、输出格式和执行要求 | 调整回答风格、约束 JSON 输出 |
| RAG（检索增强生成） | 为模型提供外部知识和可追溯的信息 | 企业知识库、专业文档问答 |
| Fine-tuning（微调） | 使模型更适应特定任务、输出模式或领域数据 | 专业文本分类、固定格式任务、特定行为适配 |
| Harness（执行与控制框架） | 组织工具、状态、流程、反馈和错误处理 | 多步骤任务、业务系统自动化 |
| 专业规则与验证系统 | 检查模型输出是否满足明确约束 | 金额计算、业务规则校验、合规性检查 |
| 人工审核（Human-in-the-loop） | 对关键决策提供专业确认与责任控制 | 医疗、法律、金融等高风险业务 |

例如，如果一个法律问答 Agent 不知道最新法规，首先可以考虑提供权威、及时更新的法规检索，而不是立即微调。如果它已经获取了正确法规，但仍然无法稳定完成某类特定判断，则需要进一步研究模型能力、任务分解和专业校验是否存在问题。
选择技术的标准不是哪个名词更高级，而是哪种方法能够以合理成本解决已确认的问题。

### 6. 求职准备要从“技术栈展示”升级为“问题解决能力证明”
对于准备大学生校招或后端转 Agent 的工程师，视频最直接的提醒是：不要认为掌握几个流行框架、做过几个聊天机器人，就一定能够形成竞争优势。
简历中的项目如果只是“使用某框架调用某大模型 API，完成聊天功能”，很难体现深入的技术能力。更有价值的项目描述，应包含业务背景、技术难点、系统设计、失败案例、优化过程和可量化结果。
例如，一个知识库 Agent 项目可以记录初始测试集的正确率、引用准确率、工具调用成功率以及平均响应延迟，再比较引入检索重排、输出校验或缓存机制之后的变化。这里的数字必须来自实际测量，不应该为了简历效果编造。
面试时，候选人也应该能够说明为什么选择 RAG 而不是微调、为什么某类任务需要工作流而不是自由规划，以及系统在模型输出错误时如何处理。这些问题更有助于展现工程理解，而不是仅靠背诵 API 文档。

### 7. 不要因为“Agent 暴雷”的舆论，就直接放弃 Agent 方向
视频虽然措辞激烈，但它并没有得出“Agent 不值得学习”的结论。
它真正表达的是，Agent 市场正在从技术概念驱动转向业务价值驱动。在这一变化中，简单项目和浅层技术可能更容易被替代，但复杂业务集成、可靠性工程、模型适配、行业知识工程等方向仍然可能存在发展空间。
因此，对 Agent 感兴趣的人不必因为网络上出现“暴雷”“没前途”等说法而立即改变方向。更合理的策略是保持对 AI 应用开发的学习，同时主动提高自己的技术深度，并通过实际项目证明价值。
与其纠结 Agent 这个岗位名称会不会消失，不如思考自己是否具备设计和交付高质量 AI 系统的能力。

### 8. 用可量化指标判断 Agent 项目的价值，而不是只看演示效果
从企业角度出发，一个 Agent 是否值得部署，最终要回到投入与产出。
例如，原来一个业务流程需要人工处理 30 分钟，引入 Agent 后是否真的能够缩短时间？是否需要额外人员检查结果？错误率是多少？如果错误导致返工或产生业务风险，整体成本是否反而上升？
因此，建议至少关注任务完成率、正确率、人工接管率、单任务成本、平均延迟和异常恢复能力等指标。对于医疗、法律、电力等高风险行业，还必须根据实际用途增加专业验证与安全控制，不能只根据一般问答准确率就判断是否能够部署。
这一点也是对视频中“20 个 Agent 替代 20 名员工”案例的直接回应：企业应该评估哪些具体任务能够自动化、在什么条件下可靠、能节省多少成本，而不是简单按照 Agent 数量来推算可替代的人数。

## 我的点评
这段视频最有价值的地方，是明确指出了 “Agent 能运行”与“Agent 能可靠解决专业问题”之间存在巨大差距，这也是企业级 AI 应用必须面对的现实工程难题。主讲人强调 Prompt、API 和 Harness 的能力边界，以及专业领域知识的重要性，这些判断总体上有合理的技术依据，但其关于 2026—2027 年岗位竞争、学历门槛等具体趋势的说法，主要属于个人观察和预测，缺少系统性的招聘数据支持。需要保留的一点是，视频对“必须动底层模型”的强调略显绝对，因为许多专业场景可以通过高质量 RAG、工具集成、结构化工作流、规则校验以及人工审核取得有效成果，并非一律需要微调或重新训练模型。与此同时，传统后端工程能力也不应该被低估：安全、数据库、分布式系统、稳定性、服务治理和系统集成，仍然是企业级 Agent 成功落地的重要基础。对于普通学习者，最合理的方向不是放弃 API、Prompt 和后端开发，而是在这些能力之上继续学习模型评估、Harness、知识工程与垂直业务，逐步建立完整的 AI 系统交付能力。
最终值得记住的是：Agent 的竞争正在从“谁能最快接入大模型”，转向“谁能让大模型在真实业务中稳定、准确、可控地完成任务”。真正需要警惕的不是 Agent 技术本身，而是把低门槛的接入能力误认为长期不可替代的技术优势。
