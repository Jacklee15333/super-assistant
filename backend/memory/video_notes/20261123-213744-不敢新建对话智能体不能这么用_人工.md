## 🤖 AI 分析

## 一句话概括
使用 AI 智能体开展长期、复杂的项目时，不应该把所有任务都堆积在同一个对话中，而应该通过项目工作空间、独立任务上下文和 `AGENTS.md` 等项目说明文件，将重要信息持久化保存，实现任务解耦、上下文复用、Token 消耗控制，并降低上下文压缩导致关键信息丢失的风险。

## 背景与主题
随着 AI Agent（人工智能智能体）逐渐被应用于编程开发、办公自动化、文档处理、表格分析、公文写作和标书制作等场景，越来越多的用户开始利用 AI 完成具有连续性的复杂项目。
但很多用户存在一个使用误区：担心新建对话会导致此前提供的信息、项目背景和工作成果丢失，因此始终在同一个对话窗口中工作，甚至将一个对话当作整个项目的永久记忆载体。
作者认为，这种使用方式不仅会增加 Token（词元）消耗，还会因为上下文长度限制和自动压缩机制，导致 AI 遗忘重要信息、理解偏差和任务执行质量下降。
视频提出了一套以 Project（项目工作空间）为组织单位、以 Markdown 文件为持久化记忆载体、以独立上下文为任务执行单位 的智能体工作方法，其核心思想是将项目记忆与临时对话分离，主动管理 AI 所依赖的信息。

## 核心观点

### 1. 不敢新建对话，是使用 AI 智能体的典型误区
很多人使用智能体时，会产生一种心理依赖：此前已经向 AI 介绍了大量背景信息、交代了各种要求、完成了许多工作，一旦新建对话，这些信息似乎就会全部丢失。因此，无论是修改代码、调整目录、处理文件，还是提出新的需求，都习惯在原来的对话中继续进行。
作者直接否定了这种做法，并强调：“不要这么干，活不是这么干的朋友们。”
这种问题的根源，在于用户将 AI 的对话上下文误认为稳定、可靠的长期记忆，而实际上，对话上下文主要承担当前任务的信息传递功能，并不能保证无限期、完整地保存所有历史信息。
真正应该延续的是项目知识和工作成果，而不是某一个聊天窗口。 只有将两者分离，才能摆脱对长对话的依赖。

### 2. 应该以项目工作空间为单位组织长期工作
作者建议，使用智能体之前，首先建立一个 Project（项目）或 Workspace（工作空间），将同一个项目相关的文件、任务、说明和成果集中在统一的工作环境中。
项目的类型并不重要，视频中特别列举了以下应用场景：编程开发项目、办公项目、表格处理项目、文档处理项目、公文写作项目以及标书制作项目。
这些工作虽然性质不同，但都存在共同需求，即需要 AI 持续理解项目目标、业务规则、文件结构和此前已经完成的工作。
项目工作空间的价值在于，它使信息不再完全依附于某一次对话，而可以通过文件、目录以及项目级配置进行管理。
这种思路实际上是将 AI 从一个临时问答工具，转变为能够围绕具体项目持续工作的协作工具。

### 3. 第一次对话的重点，是建立项目的基础知识库
建立项目之后，作者建议先开启一个专门用于项目初始化的上下文，在这个对话中集中讨论项目的基本情况。
第一次对话应该明确项目是做什么的、最终要达到什么目标、涉及哪些技术细节、采用什么执行方式、有哪些目录结构，以及各个文件分别承担什么功能。
当这些内容讨论清楚之后，应当要求 AI 对整个项目进行系统性的总结，并将总结写入一个独立的 Markdown 文件，而不是仅仅停留在对话记录中。
作者认为，当项目的核心信息完成提炼并持久化之后，第一次对话就已经完成了它的主要使命，没有必要继续依赖这个对话。
初始化对话的核心产出不是聊天记录，而是一份能够指导后续工作的项目说明文件。

### 4. 利用 AGENTS.md 建立智能体的持久化项目记忆
视频提出，可以将项目的核心信息写入 `agent.md` 文件；在许多采用项目级智能体指令的开发工具中，常见的约定文件名是 `AGENTS.md`，具体名称取决于所使用的工具。
这个文件应该集中保存项目目标、执行方式、技术细节、目录结构、文件清单、文件用途以及其他需要长期遵守的工作规则。
在后续的新对话中，只要智能体能够访问并读取这份文件，就可以重新获得项目的重要背景信息，而不必依赖之前的完整聊天记录。
作者反复强调：“不都在这了吗？”其含义是，既然决定项目如何运行的信息已经被写入项目文件，那么旧对话就不再是唯一的信息来源。
这种方法可以理解为一种 External Memory（外部记忆）机制，即将重要知识从模型有限的上下文中转移到可持续保存、更新和读取的外部文件中。
需要注意的是，不同智能体对项目说明文件的自动读取机制并不完全相同，不能认为任意 AI 产品都会自动识别 `agent.md` 或 `AGENTS.md`。

### 5. 一个独立任务对应一个新的上下文
作者提出了非常明确的任务组织原则：“有一个任务新建一个，有一个任务新建一个。”
例如，在同一个软件开发项目中，修改登录功能、调整目录结构、优化用户界面、修复数据库错误，可以分别开启独立的对话，而不是全部混杂在一个长期聊天窗口中。
对于办公项目，同样可以将数据清洗、表格分析、报告撰写、文档排版等工作拆分到不同上下文中。
每一个新上下文只需要继承必要的项目背景，并围绕当前任务集中展开，从而降低其他任务的信息对当前判断产生干扰的可能性。
这种方法体现了 Task Decomposition（任务分解）和 Context Isolation（上下文隔离）的思想，有助于提高任务边界的清晰度，也方便出现问题时定位原因。

### 6. 长期使用同一个对话，会增加 Token 消耗
作者指出，将所有工作持续放在同一个上下文中，会产生 Token 消耗方面的问题，并强调：“首先第一个，它是肯定费 Token 的。”
Token 是语言模型处理文本和其他部分输入内容时使用的基本计量单位，一个长对话通常包含大量历史问题、模型回答、工具调用结果以及文件内容。
当 AI 在执行新的任务时需要重新处理较长的历史上下文，就可能增加输入 Token 数量、推理成本以及响应时间。
尤其是在使用按 Token 计费的 API（应用程序编程接口）或智能体开发工具时，重复传入大量与当前任务无关的历史信息，会造成不必要的资源消耗。
不过，实际成本还取决于上下文缓存、历史截断、检索策略以及产品的计费方式，因此作者所说的“100%费 Token”，更适合理解为对长上下文低效率问题的强调，而非适用于所有产品的绝对计费规律。

### 7. 即使不在乎费用，也无法避免上下文窗口限制
作者进一步指出，即使用户完全不在乎 Token 成本，始终在同一个对话中工作的方式仍然存在技术限制。
所有大语言模型都存在一定的 Context Window（上下文窗口）容量，即模型在一次处理过程中能够接收和利用的信息规模并不是无限的。
视频提到了“100万”的上下文长度，以此说明即使具备百万级 Token 上下文容量，随着项目不断推进，也可能遇到历史信息超过模型处理上限的问题。
当对话内容不断累积时，智能体系统可能采用上下文压缩、摘要生成、历史截断或选择性检索等方式继续处理任务。
更大的上下文窗口只是延缓了信息管理问题的出现，并没有从根本上解决长期项目的记忆问题。

### 8. 自动上下文压缩可能导致重要信息丢失
为了让超长对话能够继续进行，部分 AI 产品会采用 Context Compaction（上下文压缩）机制，将此前的详细内容转换成更短的摘要，或者删除部分历史信息。
作者以豆包为例，指出用户在长期与 AI 聊天的过程中，有时会发现之前交代的重要信息突然不再被准确记住。
问题在于，智能体系统自动判断哪些信息应该保留时，其判断标准不一定与用户的真实需求完全一致。
例如，某个特殊业务规则、之前明确禁止修改的文件、一个看似不起眼的技术参数，或者用户已经反复确认的设计要求，都有可能在摘要过程中被遗漏。
因此，即使用户曾经向 AI 明确提供过某条信息，也不能保证它在未来的每一次任务中仍然会被准确调用。

### 9. 主动提炼项目知识，比完全依赖 AI 自动压缩更加可靠
作者最后提出的解决方案，是在上下文尚未达到容量限制之前，主动将重要信息提炼出来，并保存到项目说明文件中。
这种做法使用户能够明确决定哪些信息属于长期项目知识，哪些内容只是临时讨论，哪些约束无论经过多少次新对话都必须得到保留。
即使后续对话发生了自动压缩，或者原来的聊天历史不再可用，只要这些关键信息仍然保存在项目文件中，智能体就有机会重新读取并恢复相关背景。
作者用一句反问总结这一逻辑：“所以自己手动提炼，是不是就比让它自己压要好很多？”
从更深层次看，这套方法强调的是 Context Engineering（上下文工程），即通过主动设计、组织、筛选和维护输入信息，让 AI 在执行任务时获得更加准确、相关且稳定的上下文，而不是单纯依靠模型的记忆能力。

## 金句摘录
“不要这么干，活不是这么干的朋友们，智能体我跟大家说怎么用。”

这句话直接指出了用户将智能体当作单一长期聊天工具的使用误区。
“有一个任务新建一个，有一个任务新建一个。”

这是整段视频最重要的操作原则，即按照任务而不是按照整个项目划分对话上下文。
“千万不要所有的东西都在一个上下文里聊，你跑偏了。”

强调大量不同任务混合在同一个上下文中，可能导致任务之间相互干扰。
“那它压缩，你确定它压缩压的东西，都是你不用的东西吗？”

指出自动上下文压缩的核心风险：系统认为不重要的信息，可能恰恰是用户真正需要保留的信息。
“你以为你都给它发了，它能记住吗？它不可能都记住。”

提醒用户，曾经输入过的信息并不等于 AI 永久拥有这部分记忆。
“所以自己手动提炼，是不是就比让它自己压要好很多？”

这是视频最终的结论：用户应该主动参与项目知识的筛选、提炼和保存，而不是完全依赖 AI 系统自动管理历史信息。

## 值得记住的点 / 行动建议

### 1. 建立「一个项目、多个对话、共享知识」的工作模式
不要再采用一个项目对应一个无限延长的聊天窗口的工作方式，而应该建立一个独立的项目空间，并在项目内部根据不同任务分别创建对话。
所有对话共享同一套项目背景、项目文件和执行规则，但各自只承担相对明确的工作。

这样，即使某一个对话出现理解偏差、陷入错误循环或者上下文过长，也不需要放弃整个项目，只需要重新建立当前任务的对话即可。

### 2. 为每一个长期项目准备 AGENTS.md 文件
这是视频中最值得直接实践的方法。
如果正在使用支持项目文件读取的智能体工具，可以在项目根目录下建立 `AGENTS.md`，并要求 AI 在开展新任务之前读取其中的内容。
以下是一个可以直接复制使用的通用项目说明文件模板，属于基于视频思路的实践扩展。
AGENTS.md

 复制模板

一、项目背景
项目名称、项目用途、目标用户、需要解决的问题。
二、项目目标
最终交付成果、核心功能、验收标准。
三、技术与工作环境
使用工具、技术栈、运行环境、依赖及版本。
四、项目目录结构
核心目录、文件清单、文件用途。
五、长期工作规则
必须遵守的要求、禁止执行的操作、输出格式、不得擅自修改的内容。
六、项目进度
已完成任务、当前任务、待完成任务、已知问题。
七、重要决策
已确认的方案、决策理由、关键参数。
八、智能体执行要求
任务开始前读取项目说明，明确任务范围，完成工作后更新必要信息。

这份文件不应该成为全部聊天记录的简单复制品，而应该是经过筛选和提炼后，能够直接指导智能体开展工作的项目知识集合。

### 3. 第一次使用智能体时，先完成项目初始化
在一个新项目中，不必急于让 AI 立即编写代码、制作表格或者输出完整成果，而可以先让它系统了解整个项目。
项目背景讨论完成后，可以使用下面这段提示词，要求智能体生成项目知识文件。
项目初始化提示词

请根据我们此前讨论的全部项目内容，以及当前工作空间中的实际文件，生成一份完整的 AGENTS.md 项目说明文件。
请重点整理：项目背景、最终目标、技术方案、目录结构、核心文件及用途、已经确认的需求、必须遵守的约束、已完成工作、待完成任务、已知问题和重要决策。
删除无关的闲聊、重复讨论及已经废弃的方案，保留所有会影响未来任务执行的重要信息。
请区分已确认事实、尚未确认的事项和建议方案，不要编造信息。
这份文件将作为以后每一次新建对话的项目背景和执行依据。要求结构清晰、信息准确、便于持续更新，并保存到项目根目录。

完成项目初始化之后，后续就不必反复介绍同样的项目背景和工作要求。

### 4. 新建对话时，明确要求 AI 先读取项目说明
虽然视频作者表示 AI 会自动读取项目说明文件，但不同工具的实现机制存在差异。
为了确保智能体真正掌握项目背景，可以在新建对话时使用一个固定的任务启动提示词，特别是在工具没有明确提供自动加载项目说明功能的情况下。
新任务启动提示词

开始工作前，请先读取当前项目中的 AGENTS.md、项目进度文件及与本次任务有关的文件，理解项目目标、已有成果、目录结构和长期约束。
本次任务：【填写具体任务】。
请严格限定在本次任务范围内，不重复询问项目说明中已经确认的信息，不擅自修改无关内容。
如果项目说明与实际文件存在冲突，请先识别差异，不要自行编造或覆盖重要信息。
完成任务后，请记录本次修改内容、完成状态及需要更新的项目知识。

这样做的关键不在于让 AI 重现此前的全部聊天过程，而是使它获得完成当前任务所必需的信息。

### 5. 将长期记忆进一步拆分为多个功能文件
对于较小的项目，一个 `AGENTS.md` 文件可能已经足够。
但对于需要长期开发、频繁迭代或者涉及大量文件的复杂项目，如果把所有信息都写入一个 Markdown 文件，最终也可能出现文件过长、信息重复、维护困难的问题。
因此，可以进一步采用分层项目记忆结构。
Project

AGENTS.md
智能体执行规则与项目核心约束

README.md
项目介绍、使用方法和启动流程

PROJECT.md
项目目标、需求及整体架构

PROGRESS.md
当前进度、已完成任务和待办事项

DECISIONS.md
重要决策及其理由

CHANGELOG.md
版本变化和历史修改记录

TASKS.md
任务清单、优先级和完成状态

docs/
详细技术文档、参考资料、业务规范

| 文件 | 更新时机 |
| --- | --- |
| AGENTS.md | 长期规则或核心约束变化时 |
| README.md | 使用方法、启动方式变化时 |
| PROJECT.md | 项目需求或总体架构变化时 |
| PROGRESS.md | 每次重要任务完成后 |
| DECISIONS.md | 确认重要技术或业务决策后 |
| CHANGELOG.md | 发布新版本或进行重要修改后 |
| TASKS.md | 新增任务或任务状态变化时 |

这种分层管理方式并非视频明确提出的全部内容，而是根据作者的外部记忆思想进一步延伸出的实践方案。
其优势在于，可以让智能体根据当前任务选择性读取相关文件，而不必每次都加载整个项目的历史信息。

### 6. 在结束一个任务之前，进行一次知识提炼
每完成一项重要任务，不要只是关闭对话或者立即开始下一个任务，而应该先将本轮工作的有效成果沉淀到项目文件中。
需要保存的重点包括已经确认的事实、新增功能、修改过的文件、关键技术参数、解决问题的方法、尚未解决的错误以及未来需要注意的事项。
可以让 AI 自动生成任务交接记录，但应避免将未经确认的推测和临时方案写成永久规则。
任务结束与记忆提炼提示词

请总结本次对话中所有对后续项目工作有长期价值的信息。
重点记录：本次任务目标、实际完成情况、修改的文件、已经确认的事实和技术决策、关键参数、尚未解决的问题、下一步建议。
删除重复内容、临时讨论、已废弃方案和无关信息。
请核对实际工作成果，不要将计划中的工作标记为已完成。
将需要长期遵守的新增规则更新到 AGENTS.md，将任务完成情况更新到 PROGRESS.md，将重要方案及理由更新到 DECISIONS.md。避免覆盖仍然有效的旧信息。

通过这种操作，每一次对话都会为整个项目积累有效知识，而不只是增加聊天记录的长度。

### 7. 学会判断什么时候应该新建对话
并不是所有问题都必须立即新建对话。围绕同一个具体问题进行连续追问、补充条件和错误修正时，保留当前上下文往往更有效率。
真正需要新建对话的判断标准，是当前任务是否已经发生了明显变化，或者原有上下文是否开始妨碍任务执行。

| 场景 | 建议操作 |
| --- | --- |
| 继续修复同一个错误 | 保留当前对话 |
| 对上一轮输出进行修改 | 保留当前对话 |
| 补充当前任务的必要信息 | 保留当前对话 |
| 深入讨论同一个技术问题 | 保留当前对话 |
| 开始开发新的独立功能 | 新建对话 |
| 从代码开发切换到文档制作 | 新建对话 |
| 从数据分析切换到界面设计 | 新建对话 |
| 当前任务已经完成 | 提炼知识后新建对话 |
| AI 反复犯相同错误 | 保存有效信息后尝试新建对话 |
| AI 开始混淆以前的要求 | 检查项目说明并新建对话 |
| 对话出现重要信息遗忘 | 从持久化文件恢复相关背景 |
| 上下文过长、响应效率下降 | 提炼有效信息后新建对话 |

一个项目可以有几百个独立对话，并不意味着一个项目必须拥有一个包含几百轮交流的对话。

### 8. 区分对话上下文、外部记忆和产品级记忆
用户之所以容易对长对话产生依赖，一个重要原因是没有区分 AI 系统中不同类型的信息保存机制。

| 对比维度 | 对话上下文 | 外部项目记忆 | 产品级记忆 |
| --- | --- | --- | --- |
| 主要用途 | 执行当前任务 | 保存项目知识 | 保存跨对话的用户相关信息 |
| 常见形式 | 历史消息、工具结果 | Markdown、文档、数据库 | 产品自身提供的记忆功能 |
| 生命周期 | 通常围绕当前对话 | 可持续整个项目 | 取决于产品机制和设置 |
| 信息控制 | 相对有限 | 用户可主动编辑 | 取决于产品能力 |
| 是否可能丢失细节 | 是 | 可通过版本管理降低风险 | 是 |
| 适合保存什么 | 临时讨论和当前任务 | 技术规范、业务规则、项目进度 | 用户偏好、长期背景 |
| 是否适合无限积累 | 否 | 应分类维护 | 不应视为完整项目数据库 |

不能因为某个 AI 产品具备跨对话记忆功能，就认为它必然能够准确保存一个复杂项目的所有技术细节。
长期项目应该具有独立、可检查、可维护的信息来源。

### 9. 不要把 AGENTS.md 变成另一个无限增长的上下文
虽然项目说明文件能够解决许多长对话问题，但也不应该把每一条聊天记录、每一次临时尝试和每一种废弃方案都保存进去。
如果项目说明文件不断膨胀，AI 每次启动任务时仍然需要处理大量无关内容，就可能重新产生 Token 浪费和信息干扰的问题。
比较合理的做法，是根据长期价值对信息进行分级管理。

| 信息类型 | 处理方式 |
| --- | --- |
| 项目核心目标 | 长期保留 |
| 已确认的需求 | 长期保留 |
| 必须遵守的约束 | 长期保留 |
| 重要技术决策 | 长期保留并记录理由 |
| 当前任务进度 | 定期更新 |
| 关键参数与实验结果 | 分类保存，保留来源 |
| 详细历史记录 | 单独归档 |
| 临时讨论 | 按需保留 |
| 重复信息 | 合并或删除 |
| 已废弃方案 | 标明废弃状态或归档 |
| 密码、API Key 等敏感信息 | 不应直接写入普通项目说明文件 |

优秀的项目记忆系统，不是保存的信息最多，而是能够让 AI 快速找到真正影响任务执行的信息。

### 10. 将这套方法应用到各种非编程工作中
视频特别强调，这种工作方式并不仅仅适用于程序员。
对于需要持续使用 AI 的复杂工作，都可以采用项目化管理和外部记忆机制。

| 应用场景 | 应持久化保存的信息 | 可拆分的独立任务 |
| --- | --- | --- |
| 软件开发 | 技术栈、架构、接口、功能约束 | 功能开发、测试、修复、优化 |
| 学术论文 | 研究问题、理论框架、数据来源、引用规范 | 文献综述、方法设计、结果分析 |
| 标书制作 | 招标要求、评分标准、企业资质、技术方案 | 商务部分、技术部分、报价审核 |
| 办公自动化 | 文件规则、业务流程、输出模板 | 数据清洗、汇总、报告生成 |
| 自媒体运营 | 内容定位、受众画像、表达风格 | 选题、脚本、标题、复盘 |
| 电商运营 | 商品规格、品牌规范、素材标准 | 商品文案、主图设计、详情页制作 |
| 企业管理 | 业务规则、岗位职责、审批流程 | 制度编写、流程优化、经营分析 |
| 科研实验 | 实验方案、原始数据、变量定义、技术标准 | 数据处理、绘图、实验分析 |
| 长期学习 | 学习目标、课程进度、知识薄弱点 | 章节学习、习题讲解、阶段复习 |

这些工作的共同特点是：项目持续时间较长、信息逐渐积累、任务之间存在一定的关联性，同时又可以划分为不同的执行单元。
因此，项目知识持久化与任务上下文隔离具有较强的普适价值。

### 11. 建立一套可重复使用的智能体标准工作流程
综合视频内容，可以将智能体项目协作归纳为以下完整闭环。

这套流程最重要的特点是，每一个任务的完成不仅产生实际工作成果，还会使项目知识更加完整，为下一个任务提供更准确的输入。
它将传统的线性聊天模式，转变为可迭代、可交接、可维护的项目协作模式。

## 我的点评
这段视频最有价值的地方，是指出了很多人使用 AI 时尚未意识到的根本问题：AI 的上下文容量、记忆能力和项目管理能力是三件不同的事情，不能混为一谈。
作者提出的项目工作空间、独立任务上下文和持久化知识文件相结合的方法，符合上下文工程、模块化管理和外部记忆的基本思想，尤其适合需要持续数周甚至数月的复杂项目。
不过，作者关于 Token 消耗、自动压缩以及智能体自动读取 `AGENTS.md` 的部分表述过于绝对，不同模型和产品在上下文缓存、历史检索、记忆管理和文件加载机制上存在明显差异，实际使用时应结合具体工具判断。
此外，外部项目记忆也不是天然可靠的，如果 AI 将错误的技术结论、过时的需求或者尚未确认的方案写入项目说明，就可能使错误在后续任务中不断传播，因此知识更新同样需要注意准确性、版本一致性和信息来源。
普通用户可以优先选择一个正在进行的长期项目，将过去对话中的有效信息整理成一份 `AGENTS.md`，再使用新的对话完成一个独立任务，以实际效果验证这套工作方法。
归根结底，真正成熟的 AI 使用方式，不是想办法让 AI 永远记住所有聊天内容，而是建立一套即使更换对话、模型乃至工具，也能够持续继承项目知识和工作成果的信息管理体系。
