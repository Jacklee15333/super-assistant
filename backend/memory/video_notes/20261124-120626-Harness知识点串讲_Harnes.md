## 🤖 AI 分析

## 一句话概括
Harness Engineering（驾驭工程）是大模型从聊天助手走向生产级智能体的核心工程体系，通过事前引导、事后反馈以及执行循环、上下文管理、工具编排、记忆持久化、安全治理、可观测性六层技术架构，将具有概率性和不确定性的大模型转化为可持续执行、可控制、可验证、可交付的生产力系统。

## 背景与主题
随着大语言模型（LLM）和智能体（Agent）的发展，AI 应用正在从简单的问答交互，转向能够自主操作文件、调用工具、编写代码、执行复杂任务的智能体系统。仅仅拥有一个能力强大的底层模型，并不意味着能够构建出稳定可靠的 AI 产品，因为模型自身存在幻觉、上下文遗忘、执行失控、安全风险等问题。
Harness Engineering（驾驭工程）因此成为智能体开发中的重要工程方向，其核心是通过模型之外的一整套运行机制，弥补大模型在实际执行过程中的不足。视频引用 Mitchell Hashimoto（米切尔·哈希莫托）提出的智能体公式，以及 Martin Fowler（马丁·福勒）借鉴控制论提出的工程思想，从概念、底层原理、六层技术架构和工程设计哲学四个方面系统拆解 Harness。
作者最终强调，未来 AI 产品之间的竞争，不仅取决于底层模型的智能程度，还取决于开发者能否设计出一套高效、可靠、安全的 Harness 系统。

## 核心观点

### 1. 智能体不是大模型本身，而是大模型与 Harness 的结合
Harness 这个英文单词原本指马具、缰绳、安全背带等用于驾驭或保护的装置，在传统软件工程领域也早有应用，例如 Test Harness（自动化测试支架），以及持续集成与持续交付领域的软件交付平台 Harness。进入大模型时代以后，Agent Harness（智能体运行支架）指的是包裹在大模型之外、负责组织和控制其实际运行的一整套工程系统。视频引用 Mitchell Hashimoto（米切尔·哈希莫托）提出的核心公式：Agent = Model + Harness，即智能体 = 模型 + 运行支架。 如果将大模型比作一匹聪明、强壮但难以控制的千里马，那么 Harness 就是缰绳、马鞍、眼罩和脚蹬；如果将模型比作汽车发动机，那么 Harness 就是方向盘、变速箱、仪表盘和刹车系统。模型主要决定智能体能够达到的能力上限，而 Harness 主要负责让这些能力稳定发挥，保障实际业务中的交付质量和可靠性下限。
模型提供智能，Harness 提供完整的执行与控制体系。

### 2. Harness 工程是提示词工程、上下文工程的进一步升级
普通的大模型聊天窗口主要采用“用户提问—模型回答—等待下一条指令”的交互模式，而完整的 Harness 可以通过持续运行的程序主动推动模型执行下一步操作，直到任务完成或满足停止条件。Prompt Engineering（提示词工程）主要研究如何把指令说清楚，让模型理解用户意图并生成更好的答案；Context Engineering（上下文工程）则进一步研究如何向模型提供最相关的背景资料、历史记录、文件内容和工具信息。Harness Engineering（驾驭工程）位于更外层，不仅管理输入信息和上下文，还管理工具执行、运行状态、安全拦截、错误修复和结果验证。
它与 LangChain 等智能体开发框架也存在侧重点上的区别：开发框架更像提供木板、螺丝和零部件的工具箱，需要开发者自行组装执行流程，而完整的 Harness 更像已经组装好、能够直接工作的成品系统。视频以 Claude Code 为例，说明成熟的编程智能体通常已经内置执行循环、工具集合和权限机制；在架构合理解耦的情况下，还可以适配不同厂商的底层模型。至于 Scaffolding（脚手架），视频将其理解为启动前的准备工作，例如加载系统提示词、注册工具名单，而 Harness 则贯穿整个任务运行周期，不过实际工程中这些术语的边界并非绝对统一。

| 概念 | 中文含义 | 核心职责 |
| --- | --- | --- |
| Prompt Engineering | 提示词工程 | 如何向模型提出准确的要求 |
| Context Engineering | 上下文工程 | 如何为模型提供正确的信息 |
| Harness Engineering | 驾驭工程 | 如何让模型可靠地完成实际任务 |
| Agent Framework | 智能体开发框架 | 提供构建智能体的组件和开发能力 |
| Scaffolding | 脚手架 | 初始化环境、配置及准备工作 |
| Agent Harness | 智能体运行支架 | 管理智能体完整的运行过程 |

### 3. Harness 的底层原理是事前引导与事后反馈形成的控制闭环
视频引用软件工程专家 Martin Fowler（马丁·福勒）借鉴经典控制论的思路，将 Harness 的核心机制分为 Feedforward Control（前馈控制）和 Feedback Control（反馈控制）。前馈控制也就是事前引导，在模型执行任务之前提前规定行为边界，例如在项目根目录中放置说明文档，写清目录结构、代码命名规范、禁止修改的区域、系统提示词和工具参数要求。反馈控制也就是事后传感器，在模型执行完操作之后，通过确定性的外部工具检查结果，因为大模型本质上是概率生成系统，即使事前规则足够详细，也无法保证它永远不犯错。
例如，模型修改了一段代码之后，Harness 自动触发代码语法检查工具和自动化测试脚本，如果测试失败，就将具体的报错位置、错误类型和测试结果重新提供给模型。模型根据真实的外部反馈修改代码，Harness 再次执行检查，如此反复，直到检查通过或达到设定的终止条件。这套机制的本质不是要求 AI 一次就做对，而是建立一个能够发现错误、反馈错误、修正错误的工程闭环。
Harness 核心控制闭环：引导 → 执行 → 检查 → 修正 → 交付

### 4. 第一层：执行循环与任务编排层，是整个智能体的心脏
Execution Loop（执行循环）与 Task Orchestration（任务编排）负责驱动智能体连续执行任务，因为大语言模型的一次推理调用结束后，并不会天然自动发起下一轮调用。经典的执行方式是 ReAct（推理与行动），即思考、行动、观察结果、再次思考，通过多轮循环不断接近最终目标。Harness 首先向模型发送用户目标和可用工具清单，模型决定调用哪个工具，Harness 负责实际执行，并将执行结果追加到对话历史中，再次询问模型下一步应该做什么。
如果遇到复杂的大型工程任务，这一层还会让模型生成待办任务清单，将大目标拆分成多个可执行的小任务，并随着任务完成逐项更新进度。更加复杂的系统还可以调度多个 Sub-agent（子智能体）进行协同工作，例如让不同智能体分别承担代码开发、资料检索、测试验证等职责。执行循环使 AI 从一次性的内容生成器，转变为能够连续推进任务的执行系统，但同时也需要明确任务结束条件，防止出现无休止的循环。
典型执行流程：
1

接收用户目标

2

制定计划、拆分任务

3

模型选择下一步行动

4

Harness 调用真实工具

5

收集工具返回的观察结果

6

更新任务状态、判断是否完成

未完成：返回执行循环继续推进

已完成：验证结果并交付

### 5. 第二层：上下文管理层，解决信息过载、成本和注意力问题
Context Management（上下文管理）相当于智能体的短期注意力管家，即使现代大模型已经支持几十万乃至上百万规模的上下文窗口，也不意味着把所有信息都塞给模型就是最好的方案。作者指出三个主要问题：第一，过多信息容易导致 Lost in the Middle（中间信息迷失效应），使模型忽略位于长上下文中间的重要内容；第二，历史记录不断增长，会增加模型调用的费用和延迟；第三，大量无关的工具日志会干扰模型判断，降低有效信息的占比。
Harness 因此需要进行 Dynamic Context Assembly（动态上下文组装），每轮只按需检索与当前任务最相关的文件和背景资料，而不是一次性加载全部项目内容。当上下文逐渐接近窗口限制时，可以通过 Context Compaction（上下文压缩）将早期对话浓缩成摘要，保留重要决定、任务状态和关键结论。另一项重要技术是 Observation Masking（观察遮蔽），将数轮之前冗长的工具原始输出隐藏起来，只保留仍然有价值的结果和必要的引用信息。作者认为，这些方法能够显著降低计算成本，甚至节省一半算力，同时减少无关信息对模型的干扰，但具体收益需要结合模型、任务和实际测试结果判断。

| 上下文管理技术 | 具体作用 |
| --- | --- |
| 动态上下文组装 | 每轮只加载当前任务所需信息 |
| 按需检索 | 根据任务定位相关文件和知识 |
| 上下文压缩 | 将早期历史记录浓缩为摘要 |
| 观察遮蔽 | 隐藏过时、冗长的工具输出 |
| 关键信息保留 | 保留任务目标、重要决定、约束和结论 |
| 输出截断 | 防止单次工具结果占满上下文窗口 |

### 6. 第三层：工具编排与执行环境层，决定智能体能够做什么
Tool Orchestration（工具编排）与 Execution Environment（执行环境）负责将大模型生成的文字和结构化指令转化为真实世界中的操作，例如读写本地文件、执行终端命令、操作浏览器、查询数据库，以及通过 MCP（Model Context Protocol，模型上下文协议）连接第三方软件和服务。作者强调，工具数量并非越多越好，如果向模型提供几十个功能重叠、描述模糊的工具，反而可能让模型难以正确选择；视频提到，将杂乱工具削减八成、仅保留少数职责明确且描述精准的工具，有时能够大幅提高调用准确率。
第二项关键技术是 Output Truncation and Formatting（输出截断与格式化），例如终端命令一次产生十万行日志时，Harness 应当提取日志开头、结尾、关键错误和摘要，而不是直接全部传给模型。第三项技术是 Sandbox Isolation（沙箱隔离），将代码执行和命令行操作放在容器或临时虚拟机中，以减少错误操作对宿主机和真实业务环境造成的损害。这一层不仅决定智能体的能力范围，也直接影响智能体使用工具时的准确性、成本和安全性。一个好的工具系统应当追求职责清晰、接口明确、结果可控和执行环境隔离，而不是单纯追求能够接入多少工具。

### 7. 第四层：状态与记忆持久化层，让智能体能够跨会话完成长任务
State Management（状态管理）与 Memory Persistence（记忆持久化）是解决智能体遗忘问题、实现长期任务连续执行的核心。视频将智能体记忆分为三个时间维度：Working Memory（工作记忆）负责记录当前任务的步骤和中间变量，Session Memory（会话记忆）负责记录本次会话中的用户偏好、需求和已经确定的决定，Long-term Memory（长期记忆）则通过向量数据库或本地状态文件保存跨会话的知识与经验。
针对持续几个小时甚至几天的复杂任务，作者特别介绍了一种 Handoff Pattern（交接班模式）。当旧的智能体实例即将结束工作或上下文窗口接近上限时，它需要把已经完成的内容、当前遇到的问题、尚未完成的任务和下一步计划写入本地进度文件，并提交相关代码记录。新的智能体实例启动后，通过读取交接文档、项目状态和 Git 提交历史，就能够快速了解当前进度，而不必重新理解整个项目或重复已经完成的工作。这种机制将智能体的记忆从脆弱的对话上下文转移到可持久保存、可检查的外部状态中，从而实现长任务的断点续传。

| 记忆类型 | 时间范围 | 典型记录内容 |
| --- | --- | --- |
| Working Memory（工作记忆） | 当前执行步骤 | 当前任务、中间变量、执行结果 |
| Session Memory（会话记忆） | 本次会话 | 用户要求、偏好、已确定的决策 |
| Long-term Memory（长期记忆） | 跨会话、跨任务 | 长期知识、项目经验、历史状态 |

核心启发： 不要指望一个模型实例永远记住所有事情，而要让不同模型实例能够读取同一份可信的项目状态，并顺利接续工作。

### 8. 第五层：安全护栏与权限治理层，必须使用确定性的硬规则
Guardrails（安全护栏）与 Permission Governance（权限治理）是智能体真正进入生产环境以后必须重点建设的部分，因为一个可以修改文件、执行命令、操作服务器的 AI，在提高生产效率的同时，也可能误删文件、泄露服务器密钥或修改重要业务配置。作者首先强调 Principle of Least Privilege（最小权限原则），只为智能体开放完成当前任务所必需的目录、工具和权限，对关键文件与敏感区域设置明确的访问限制。其次要建立资源限制，包括最大循环轮数、最长运行时间和最高花费金额，一旦智能体陷入重复尝试、死循环或预算超支，就需要暂停或者强制终止任务。
第三项机制是输入输出审查，识别 Prompt Injection（提示词注入攻击），并对密码、密钥和隐私数据进行脱敏，避免敏感信息通过工具调用、日志或模型输入输出发生泄露。第四项也是作者最强调的机制，是 Human-in-the-loop（人在回路）审批：读取文件、查询资料等低风险动作可以自动放行，但删除数据、修改生产配置、发送外部邮件等高风险操作，应暂停任务并请求人类确认。安全治理的根本逻辑是，不能仅仅依赖模型“自觉遵守规则”，而应该通过权限系统、执行环境和确定性的程序逻辑进行强制约束。

| 操作类型 | 参考处理方式 |
| --- | --- |
| 读取允许访问的文件 | 自动放行 |
| 查询普通资料 | 自动放行 |
| 在隔离环境中运行测试 | 按预设权限执行 |
| 修改重要项目文件 | 按风险等级设置审批 |
| 删除重要数据 | 必须确认 |
| 修改生产环境配置 | 必须确认 |
| 发送外部邮件 | 必须确认 |
| 访问未授权的敏感目录 | 直接拦截 |
| 超出时间或费用预算 | 暂停或终止任务 |

### 9. 第六层：可观测性与评估层，让智能体从黑盒变成可分析的工程系统
Observability（可观测性）与 Evaluation（评估）相当于智能体的飞机黑匣子和体检中心，负责记录任务全过程，并衡量系统性能是否真正得到改善。很多智能体在演示时看起来十分聪明，但一旦线上发生错误，开发者就无法判断究竟是提示词不准确、上下文缺失、工具调用失败，还是模型本身的能力不足。成熟的 Harness 应当具备 End-to-end Tracing（全链路追踪）能力，记录任务输入、上下文内容、工具调用、执行结果、耗时、Token 消耗、错误信息和状态变化等可获取的运行数据。
有了 Audit Logs（审计日志）和 Monitoring Dashboard（监控面板），工程师就能追溯具体故障出现在哪一轮、哪个工具或哪个验证环节，作者认为完善的记录可以帮助工程师在很短时间内定位问题。除此之外，还要建设自动化评估系统，在更新提示词、更换模型、调整工具或者改变上下文策略以后，重新运行 Benchmark（基准测试）与回归测试。AI 系统的优化不应该仅凭感觉判断，而应该通过任务成功率、工具调用准确率、执行成本、完成时间等客观指标衡量。

### 10. Harness 需要在厚与薄之间动态权衡，不能一味堆叠复杂规则
视频最后提出了 Thick Harness（厚 Harness）与 Thin Harness（薄 Harness）的架构设计哲学。厚 Harness 将大量任务规划、判断逻辑、执行步骤和检查规则写进确定性的程序中，优点是稳定、可控、对模型能力要求较低，缺点是代码复杂、维护成本较高，而且可能限制模型自主规划的能力。薄 Harness 则主要提供必要工具和安全边界，将任务规划、问题分析和决策权更多交给模型，具有结构轻巧、灵活性强的优势，但更加依赖底层模型的能力。
作者建议企业根据模型能力、业务风险和项目成熟度动态调整 Harness 的厚度，例如在项目早期或者使用较小模型时，通过较厚的 Harness 和严密的检查点保障任务质量。随着模型能力增强，开发者应当定期检查已有规则，删除那些仅仅为了弥补旧模型能力不足而添加的冗余补丁，让系统架构逐步简化。需要注意的是，可以随着模型变强而削减的是不必要的规划和纠错逻辑，而权限隔离、安全审批、结果验证等基础机制不应该因此被随意取消。
厚 Harness
程序控制较多，模型自主决策较少。
适合规则明确、风险较高、模型能力有限的任务。

薄 Harness
程序控制较少，模型自主决策较多。
适合模型能力较强、开放性和灵活性要求较高的任务。

### 四、视频涉及的典型工程案例
- 项目规范文档： 在项目根目录中放置说明文件，提前规定项目结构、代码命名要求和禁止修改的区域，属于前馈控制。
- 自动化代码检查： 模型修改代码后，自动执行语法检查和测试脚本，失败后将具体错误反馈给模型进行修复，属于反馈控制。
- 复杂任务拆分： 先生成待办清单，再按步骤执行并逐项标记完成，避免遗漏任务。
- 多智能体协作： 调度多个具有不同职责的子智能体，共同处理规模较大的任务。
- 工具数量优化： 删除职责重叠、描述模糊的工具，降低模型选择工具时的复杂度。
- 十万行日志处理： 将超长日志截断，只提取开头、结尾和关键错误摘要。
- 容器沙箱： 将代码与终端命令的执行限制在隔离环境，减少对真实环境的影响。
- 交接班模式： 旧智能体保存项目进度、卡点和下一步计划，新智能体读取状态文件与提交历史后继续工作。
- 高风险操作审批： 删除数据、修改生产配置、发送外部邮件之前，需要人类明确确认。
- 模型升级评估： 更换模型或更新提示词后运行相同的基准测试，判断系统是否真正得到改善。

## 金句摘录
**1. 关于智能体的本质**
“智能体等于模型加上 Harness。”

这是理解整个智能体工程最重要的公式。模型只是智能体的核心认知组件，并不等同于完整的智能体产品。
**2. 关于模型与工程系统的关系**
“模型本身只提供了智商和动力，它决定了智能体的能力上限。”

模型能力越强，智能体潜在能够完成的任务越复杂，但能否稳定实现这些能力，还需要外围工程系统的支持。
**3. 关于 Harness 的实际价值**
“它直接决定了智能体在真实业务场景里的交付下限。”

生产环境更重视可靠性、成功率与可重复交付，而不仅仅是某一次演示中表现得有多聪明。
**4. 关于工具设计**
“给模型的工具绝对不是越多越好。”

工具本身也会增加模型的决策负担，清晰、必要、互不重叠的工具通常比杂乱堆叠的工具更容易使用。
**5. 关于架构演进**
“工程师要学会定期给 Harness 做减法，把当年因为模型太笨而打上的那些繁琐补丁，一层层拆掉。”

随着模型能力提升，工程系统也应该重新评估旧有规则的必要性，而不是不断累积技术债务。
**6. 关于未来 AI 产品的竞争力**
“真正决定一个人工智能产品，能不能从酷炫的演示玩具变成可靠的生产力工具，核心差距就在 Harness 上。”

作者认为，智能体工程的长期价值在于将不稳定的模型能力转化为稳定的业务价值。

## 值得记住的点 / 行动建议
以下是在视频核心内容的基础上，进一步整理出的可落地工程实践。

### 11. 开发 AI 产品时，不要只研究模型和提示词
很多 AI 应用开发者容易将主要精力放在选择模型、优化提示词、比较模型排行榜上，却忽略了智能体实际运行时的工程问题。
在设计一个 AI 产品之前，应先明确用户目标如何转化为任务、模型能够调用哪些工具、任务是否需要拆分、如何判断任务完成、发生错误后如何恢复，以及哪些操作必须经过人工审批。
如果系统只能生成一份看起来很合理的执行方案，却无法自动执行、检查和修复，那么它仍然更接近聊天助手，而不是一个完整的任务执行型智能体。

### 12. 从最小可用的执行闭环开始构建 Agent
初期不必直接开发一套复杂的多智能体平台，也不需要立即接入几十个工具。可以先选择一个目标明确、结果容易验证的小任务，例如自动整理文件、修复代码错误或者生成结构化报告。
一个最小可用的 Harness 至少应包含用户目标输入、模型调用、工具执行、观察结果反馈、任务完成判断和循环终止机制。
参考伪代码：
Python
运行

while not task_finished:

 context = build_context(task_state)

 action = model.decide(context)

 if action.requires_approval:
 request_human_approval(action)

 result = execute_tool(action)

 feedback = validate(result)

 task_state.update(result, feedback)

 if exceeds_limits(task_state):
 break

这段代码仅用于说明核心流程：模型负责提出决策，Harness 负责组织执行、验证结果、更新状态和判断是否继续。

### 13. 将自然语言要求转化为可以检查的验收标准
不要只告诉模型“把代码写好”“不要出现错误”“把报告做完整”，因为这些指令没有明确的、可自动判断的完成标准。
例如，开发一个网页应用时，可以要求代码编译通过、关键接口返回正确结果、自动化测试通过、指定页面能够正常打开、已有功能没有出现回归问题，同时检查是否修改了不允许修改的文件。
这样一来，即使模型声称自己已经完成任务，Harness 也不必直接相信，而是通过外部检查确定任务是否真正完成。
重要原则：将模型对自身工作的主观评价，转化为可以独立验证的客观结果。

### 14. 为项目建立专门供智能体读取的规范文件
可以在项目根目录中设置智能体能够读取的规范文档，例如 AGENTS.md、CLAUDE.md 或其他与具体工具兼容的说明文件。
其中可以记录项目目标、目录结构、技术栈、启动方式、测试命令、代码风格、禁止修改的文件、依赖安装限制、交付标准和需要人工确认的操作。
这类文档相当于为智能体提供一份项目工作手册，使它在执行任务之前就了解业务背景和工程边界，减少开发者重复解释同样要求的次数。
不过，规范文件中的自然语言限制主要起引导作用，真正重要的权限限制仍应通过程序和运行环境强制实现。

### 15. 主动管理上下文，不要把大窗口当成无限记忆
在开发需要持续执行的 Agent 时，应当将上下文当作一种有成本、有容量限制的工程资源。
可以将信息分成必须长期保留的信息、当前步骤需要的信息、可以压缩的历史信息和能够丢弃的临时信息。

| 信息类型 | 推荐处理方式 |
| --- | --- |
| 用户最终目标 | 持续保留 |
| 安全规则与业务约束 | 持续保留 |
| 当前任务状态 | 实时更新 |
| 相关代码和文档 | 按需加载 |
| 重要历史决定 | 摘要保留 |
| 已解决的旧错误 | 压缩为结论 |
| 冗长的终端日志 | 截断、提取摘要 |
| 与当前任务无关的文件 | 暂不加载 |

不要每次调用模型都重新传输整个项目的所有文件和全部对话，而应优先根据当前任务检索最相关的信息。

### 16. 精简工具集合，提高工具的可理解性
工具开发应优先关注每个工具是否具有明确的职责、准确的描述、规范的输入参数和稳定的输出格式。
例如，如果系统中存在多个作用几乎相同的文件读取工具、搜索工具和网页查询工具，模型可能无法判断什么时候该使用哪个工具。这时应该考虑合并功能、明确调用边界或者根据任务动态开放工具。
还可以为工具调用设置超时、错误码、重试策略、最大输出长度以及所需权限。
衡量一个工具系统是否优秀的标准，不是接入了多少个 MCP 服务，而是模型能否在正确的时间选择正确的工具，并获得足够准确的结果。

### 17. 将长任务设计成能够断点续传的状态机
如果任务可能持续几十轮、几个小时甚至更长时间，就不应该只依赖模型当前的聊天历史。
可以在项目中建立以下结构作为状态管理的参考：
纯文本

每完成一个重要阶段，智能体就更新任务清单、记录已修改文件、保存测试结果，并明确下一步行动。
下一次启动时，即使使用的是不同的模型或新的智能体实例，也能够通过读取这些文件恢复上下文。
这种方式尤其适合 AI 编程、长期科研分析、大规模文档整理和自动化工作流等需要多轮推进的任务。

### 18. 建立标准化的智能体交接班模板
交接班不能只是让模型写一句“任务还没有完成”，而应要求它留下足够让下一个智能体直接开始工作的关键信息。
一个实用的交接文档可以包含：
智能体任务交接记录

任务目标： 最终需要交付什么。
当前进度： 哪些任务已经完成，哪些尚未完成。
已修改内容： 文件路径、修改原因和代码提交记录。
验证结果： 哪些检查已经通过，哪些测试仍然失败。
重要决定： 已确认的方案和不可随意改变的约束。
当前卡点： 遇到的具体问题及已经尝试的方法。
下一步行动： 新智能体启动以后应该优先完成什么。
风险提醒： 哪些文件、操作或生产环境不能直接修改。

交接班模式的价值在于将任务连续性建立在外部状态上，而不是建立在某一个模型实例永远不会遗忘的假设上。

### 19. 为每个 Agent 设置明确的安全、时间和费用预算
所有具有真实工具调用能力的智能体，都应该具备明确的执行边界。
例如，可以根据具体任务设定最大工具调用次数、最大循环轮数、最长运行时间、最大 Token 消耗、最高允许费用、连续失败次数和允许访问的文件范围。
如果模型连续多次尝试同一种错误操作，Harness 应识别这种异常行为，而不是任由模型无限重试。
对于生产数据库、服务器密钥、支付接口、外部邮件、数据删除等高风险资源，应通过权限隔离和人工审批进行保护。
这能够避免一个原本旨在节省成本的 AI 自动化系统，因为失控循环、重复调用或错误操作而产生更大的损失。

### 20. 用评估数据而不是主观感觉优化 Agent
当调整提示词、更换大模型、增加工具或修改 Harness 架构时，应当使用相同的一组任务进行前后对比。
建议长期追踪以下指标：

| 评估指标 | 衡量内容 |
| --- | --- |
| Task Success Rate（任务成功率） | 智能体真正完成任务的比例 |
| Tool Call Accuracy（工具调用准确率） | 是否正确选择和调用工具 |
| Token Consumption（Token 消耗） | 每项任务消耗的模型资源 |
| Cost per Task（单任务成本） | 完成一个任务需要的费用 |
| Execution Latency（执行延迟） | 从接收任务到完成交付的时间 |
| Retry Count（重试次数） | 完成任务所需的纠错和重试次数 |
| Human Intervention Rate（人工介入率） | 需要人工处理或协助的频率 |
| Recovery Rate（错误恢复率） | 出错后能够恢复并完成任务的比例 |
| Regression Rate（回归失败率） | 系统升级后原有能力退化的程度 |
| Safety Violation Rate（安全违规率） | 出现越权或违规操作的比例 |

这些指标可以帮助开发者回答一个非常重要的问题：系统升级以后，究竟是真的变得更聪明、更可靠了，还是仅仅在个别演示案例中表现更好。

### 21. 随着模型能力提升，定期为 Harness 做减法
早期模型能力不足时，开发者可能需要通过大量固定流程、复杂判断规则、预设分支和重复检查来保证结果质量。
但是，如果底层模型升级以后已经能够自主完成某些规划和判断，再继续保留这些复杂规则，可能会增加系统延迟、维护成本和执行限制。
可以通过基准测试、消融实验和逐步移除规则的方式，判断哪些组件仍然必要，哪些组件已经失去价值。
Harness 的演进方向不是单纯地越来越厚或者越来越薄，而是让确定性程序负责必须确定的事情，让大模型负责需要理解、判断和灵活推理的事情。
可以减少的是冗余补丁，不能减少的是必要的安全边界和验收机制。

### 22. 从模型竞争的思维转向系统工程和业务交付的思维
视频最值得创业者和 AI 产品开发者关注的一个判断，是底层模型可能逐渐成为类似电力、自来水的基础设施。
如果不同厂商的大模型在常见业务任务上的能力差距逐渐缩小，那么 AI 产品的竞争力就会更多地体现在业务数据、工具连接、任务编排、记忆管理、结果验证、运行成本、安全性和交付体验上。
因此，开发者不应该只追求“接入最强的模型”，还应该思考如何构建能够持续积累业务知识、稳定完成任务、自动处理错误的系统。
即使使用相同的大模型，不同的 Harness 设计，也可能使两个 AI 产品在任务完成率、成本和实际用户体验方面产生非常明显的差距。

## 我的点评
这期视频最有价值的地方，是将智能体开发从单纯的模型调用和提示词优化，上升到了完整的软件工程与控制系统设计层面，尤其是事前引导与事后反馈构成的闭环，能够解释为什么很多 AI 产品演示效果很好，却无法稳定进入真实生产环境。六层架构虽然不是行业唯一公认的标准，但覆盖了智能体开发中的大多数核心问题，对于 AI 编程、一人公司、自动化工作流和企业级 Agent 开发具有很强的参考价值。需要保留意见的是，工具削减八成、上下文管理节省一半算力等量化说法缺少具体实验依据，而且开发框架、脚手架与 Harness 之间的概念边界，在实际行业实践中也存在重叠。作者关于模型逐渐基础设施化的判断具有一定合理性，但模型自身的推理能力、工具调用能力、可靠性、成本和速度仍然可能长期影响 AI 产品的竞争力，不能认为 Harness 可以完全替代模型能力。对于普通开发者而言，最实用的方法不是立即搭建庞大的六层架构，而是从最小执行闭环、外部结果验证、任务状态保存和必要安全限制开始，再根据真实业务需求逐步完善。归根结底，Harness 工程的核心价值是将 AI 的概率性智能转化为可管理、可验证、可恢复、可持续优化的工程能力。

Harness工程 很多人听到就觉得，这不就是agent的运行环境吗，有啥可讲的 你要这么想 我跟你说 大错特错。Harness不仅难做 而且内容知识点也是非常非常多，不过别担心 你刷到这个视频又服了。看完这个视频 你肯定可以彻底吃透这个东西了，本期视频会从Harness概念解析。相关的核心概念 一直到底层的工作原理，最后讲到Harness六层技术架构，最后还会说一下我自己的思考和经验。废话不多说 点个赞和收藏 我们开始，想系统学习agent开发的同学可以查看橱窗的系统课哦。

在正式拆解之前，我们先花半分钟把这个词的来龙去脉立清楚，Harness这个英文单词原本的意思是马具 疆绳。或者是高空作业时的安全背带，在传统的软件工程领域它早就存在了，比如用来做自动化测试的测试支架。再比如持续集成与持续交付领域里，非常著名的那个软件交付平台 名字也叫Harness。而在今天的大模型与智能体时代，大家嘴里频繁讨论的Harness全称叫做agent harness。翻译成中文就是智能体运行支架，围绕它还诞生了一门全新的工程学科，叫做Harness工程 也就是驾驭工程。

那么到底什么是智能体的Harness呢，硅谷著名工程师米切尔·哈希默托，提出过一个在业内广为流传的核心公式。叫做智能体等于模型加上Harness，我们可以用一个非常通俗的比喻来理解，如果把大元模型比作一匹精力充沛。聪明绝顶但性格散漫的千里马，那么模型本身只提供了智商和动力，它决定了智能体的能力上限。但如果你直接骑上一匹没有马鞍，没有缰绳的野马，它跑起来是完全不可控的，甚至会把你摔下来。而Harness就是套在这匹千里马身上的全套马具，包括缰绳、马鞍、眼罩、脚灯。

如果换成汽车的比喻，它就是发动机外面的方向盘、变速箱，仪表盘和刹车系统，它包括在大元模型的外面。负责管理模型怎么感知环境，怎么调用工具、怎么记住状态，以及怎么在犯错时踩下刹车。它直接决定了智能体在真实业务场景里的交付下限，理解了这个比喻，我们就很容易分清几个经常被混淆的概念了。第一个常见疑问是，普通的大模型聊天窗口和套了Harness的智能体有什么区别。在聊天窗口里，你问一句、模型答一句，回答完它就停下来等你，而且关掉页面它就把你忘了。

所有的代码都只能跑在平台提供的临时沙箱里，而Harness是一个持续运行的程序。它装在你的电脑或者服务器上，手里握着真实的文件读写权限和外部工具，它会主动推着模型一步接一步地干活。直到把一个复杂的工程任务彻底干完，第二个常见疑问是，Harness和提示词工程、上下文工程有什么区别。其实它们三个是层层包含一步步升级的关系，提示词工程是最里层，研究的是怎么把话说明白。引导模型给出好答案，上下文工程往外扩了一圈，研究的是在模型回答之前，怎么把最精准的背景资料、历史记录塞进模型的脑子里。

而Harness工程则是最外层的完整闭环，它不仅管输入和上下文，还要管工具的执行、运行时的状态流转。安全拦截以及事后的结果验证，第三个常见疑问是，Harness和我们平时听说的智能体开发框架。比如Langchain还有脚手架又有什么不同，简单来说，开发框架就像一家卖的散装木板和螺丝钉。你买回来之后得自己写代码，自己搭循环逻辑才能拼出一件家具，而Harness是已经组装好。通上电就能直接干活的成品家电，比如大家熟悉的编程智能体工具Cloud Code。

它里面已经内置好了循环逻辑、工具集合和权限规则，你甚至可以随时把底层的模型。从一家厂商换成另一家厂商，而外面的这套Harness依然能照常运转，至于脚手架。它只负责在智能体启动之前做一次性的准备工作，比如加载系统提示词和注册工具名单。一旦智能体跑起来，真正全程接管运行时的就是Harness，搞清楚了它是什么，接下来我们来看它的核心工作原理。软件工程大师马丁·福勒借用经典控制论的思想，把Harness的所有机制归纳成了两个最好懂的核心部件。

一个叫做事前引导 也就是前溃控制，另一个叫做事后传感器 也就是反溃控制，什么叫事前引导呢。就是在模型还没有动手干活之前，先给它立好规矩、画好跑道，防止它从一开始就跑偏。比如我们在项目跟目录里放一个说明文档，里面写清楚项目的目录结构、代码命名规范。绝对不能碰得近区，再加上系统提示词和工具的参数说明，这些都属于事前引导，那什么又叫事后传感器呢。大模型的本质是概率生成，不管你事前规矩立得多细，它干活时依然有可能产生幻觉或者写出有漏洞的代码。这时候事后传感器就会在模型做完动作之后，立刻介入检查，比如模型刚改完一段代码。

Harness里的传感器就自动触发代码语法检查工具，和自动化测试脚本，如果测试没通过。传感器就会把报错信息精准地抓回来，重新谓给模型说，你刚才写的代码在第几行报错了。请重新修改，模型收到反馈后再改再测，直到所有检查全部绿灯通过，这才叫真正可靠的闭环。如果我们要从零搭建或者深入剖析一个企业级的Harness，它的内部到底包含哪些具体的技术模块呢。在目前的工程实践中，最主流的做法是把Harness拆解成六层架构，我们由内而外一层一层来串讲。

第一层是执行循环与任务编排层，这也是整个Harness的心脏，但模型本身是不会主动连续思考的。必须靠Harness用一个循环把它推着走，最经典的循环模式就是先思考再行动。接着观察结果然后再思考，在这个过程里，Harness会把用户的目标和可用工具清单发给模型。模型决定调用某个工具，Harness就去执行这个工具，拿到返回结果后追加到对话力实力。再次询问模型下一步该干什么，如此周而复始，遇到特别庞大复杂的任务，这一层还会负责先让模型列出一份代办任务清单。

每完成一小步就打一个勾，甚至调度多个不同分工的子智能体协同作战，第二层是上下文管理层。它相当于智能体的短期注意力管家，很多人会问，现在大模型的上下文窗口，都已经支持几十万甚至上百万字了。为什么还要专门管上下文呢，原因有三个，第一 信息塞得太多太杂，模型会出现中间信息迷失效应 抓不住重点。第二 历史记录越滚越长，每一次调用的花费和延迟都会成倍爆炸，第三 工具返回的大量无关日制。会形成严重的噪声干扰，所以Harness在这一层会做精细的瘦身手术，她会动态组装上下文。

每一轮只按需检索和当前步骤最相关的文件片段，当对话快要装满时，她会自动把早期的对话浓缩成简短的摘要。她还会使用观察遮蔽技术，把几轮之前那些冗长的工具原始输出隐藏掉，只保留模型当时得出的关键结论。这样既能省下一半的算力成本，又能让模型始终保持头脑清醒，第三层是工具编排与执行环境层。这一层决定了智能体的双手能伸多长，模型输出的只是文字，要让文字变成真实的动作全靠工具调用。比如读写本地文件、执行终端命令、操作浏览器，查询数据库或者通过现在业界通用的上下文协议。

去连接第三方软件，在这一层有三个极其重要的工程知识点，第一个知识点是，给模型的工具绝对不是越多越好。业界经过大量实验发现，把杂乱的几十个工具砍掉八成，只留下几个边界清晰、描述极其精准的核心工具。模型的调用准确率反而会大幅飙升，第二个知识点是输出结段与格式化，如果模型跑了一条命令。终端一下子吐出来十万行日制，Harness必须立刻在中间结段，只把开头、结尾和错误摘要传给模型。防止把模型的上下文直接撑爆，第三个知识点是环境隔离，所有的代码执行和命令行操作。

最好都关在容器沙箱或者临时虚拟机里运行，哪怕智能体不小心执行了破坏性命令，也不会伤及宿主机本身。第四层是状态与记忆持久化层，这是让智能体告别金鱼记忆，能够跨越几个小时甚至几天持续干活的关键。Harness通常会把记忆分成三个时间维度，第一个是工作记忆，记录当前任务做到哪一步了。中间变量是什么，第二个是绘画记忆，记录当前这次对话里，用户的偏好和已经拍板的决定。第三个是长期记忆，通过向量数据库或者本地的状态文件，把跨绘画的知识永久存下来。这里有一个非常巧妙的工程实践，叫做交接班模式，当一个任务特别长，单个上下文窗口装不下的时候。

前一个智能体实力在下班前会把当前的工作进展，遇到的卡点和下一步计划，写进本地的进度文件并提交代码记录。等新的智能体实力启动接班时，先去读一读前任留下的交接笔记和提交历史，马上就能找准定位接着干。实现了长任务的断点续传，第五层是安全护栏与权限治理层，也就是整套系统的安全带和刹车片。因为一旦智能体接管了真实环境，它既能帮你写代码，也能一不小心删光你的文件，或者把服务器密钥泄漏出去。所以Harness必须在这一层建立起确定性的硬性规则，首先是最小权限原则，规定哪些目录能看 哪些目录绝对不能碰。

第二是限制 设定最大循环轮述，最长运行时间和最高花费金额，一旦智能体钻进牛角尖。开始死循环 立刻强制叫停，再次是输入输出审查，拦截恶意的提示词注入攻击，对密码和隐私数据做自动脱敏。最后 也是最重要的，就是人机回还审批机制，平时查资料 读文件可以自动放行，但只要模型请求执行删除数据。修改生产配置，或者发送外部邮件这类高风险动作，Harness就会立刻挂起任务。弹窗请求人类工程师确认，人类点下同意见之后才能继续往下走，第六层是可观测性与评估层。

它相当于智能体身上的飞机黑匣子和体检中心，很多团队做出来的智能体像个黑盒，平时看着挺聪明。一旦线上出错就完全不知道它为什么抽风，一个成熟的Harness必须具备全链路追踪能力。把智能体从收到任务开始，每一轮是怎么思考的，上下文里装了什么，调用了哪个工具，耗时多久。算力，哪个传感器报了错，全都有条不稳地记录在审计日志和监控面板里，有了这层数据。工程师不仅能在一分钟内定位出故障原因，还能建立起自动化评估体系，每次升级提示词或者更换底层大模型的时候。

跑一遍基准测试，就能用客观数据看出系统到底是变聪明了还是变笨了，把这六层架构全部串起来之后。在工程落地上还有一个核心的设计哲学需要掌握，那就是Harness的厚薄权衡。什么叫厚和薄呢，如果你对模型很不放心，把每一步怎么走怎么判断，全都用死板的代码逻辑写死在Harness里。这就叫厚Harness，它的好处是极其稳定可控，坏处是代码又臭又长，而且限制了模型的自由发挥。反过来，如果你只提供基础工具和安全边界，把规划和决策的权力全都交给模型自己去想。

这就叫薄Harness，它的好处是轻巧灵活，坏处是对底层模型的智商要求极高，在真实的企业研发中。最聪明的做法是动态演进，在项目初期或者使用较小模型的时候，可以把Harness做得稍微厚一点。用严密的规则和检查点托底，但是随着底层大模型一代比一代聪明，工程师要学会定期给Harness做减法。把当年因为模型太笨而打上的那些繁琐补丁，一层层拆掉让架构保持干净纯粹，最后我们用一句话来做个总结。在大模型时代，底层的模型正在变得越来越像自来水，和电力一样的基础设施，各家模型的差距会不断缩小。

真正决定一个人工智能产品，能不能从酷炫的演示玩具，变成可靠的生产力工具，核心差距就在Harness上。通过事前引导例规矩，通过事后传感器做教验，再用执行循环、上下纹管理、工具杀箱。记忆持久化、安全护栏和可观测性这六层架构，把模型稳稳地拖住，这就是Harness工程的全部精髓。本期视频就到这里，想系统学习agent开发的同学，可以查看橱窗的系统课哦，感谢你的支持 掰了个掰。
