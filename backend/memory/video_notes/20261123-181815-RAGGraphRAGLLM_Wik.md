## 🤖 AI 分析

## 一句话概括
企业 AI 知识库建设的关键不在于选择最先进、最复杂的技术，而在于根据实际业务需求，在 RAG（检索增强生成）、GraphRAG（图谱增强检索生成）、LLM Wiki（大语言模型驱动的知识库）之间选择合适的技术路线，并通过真实业务问题验证准确性、知识关联能力、引用可靠性、更新效率及长期维护成本。

## 背景与主题
随着大语言模型逐渐从聊天问答走向企业级应用，如何让 AI 理解企业内部的制度文件、产品手册、项目经验、业务数据，已经成为大模型落地的重要问题。传统大模型虽然拥有丰富的通用知识，却不一定掌握企业内部的私有知识、专业知识和最新信息，因此需要借助外部知识库为模型补充可靠的上下文。
视频从企业实际业务需求出发，比较了普通 RAG、GraphRAG 和 LLM Wiki 三种知识库建设路线，并进一步讲解了 RAG 的底层工作原理、文档切分、向量化、语义检索、Top-K 匹配以及 Agentic RAG、多模态 RAG 等扩展技术。
作者强调，企业知识库建设并不是简单地上传文档、接入大模型，而是涉及数据解析、知识组织、信息检索、答案生成、质量评估和持续维护的一整套工程体系。
视频最终希望解决两个问题：企业应该如何选择适合自己的知识库方案，以及如何判断建成的知识库是否真正具备业务价值。

## 核心观点

### 1. 企业知识库选型应该从业务问题出发，而不是从技术先进程度出发
企业在建设 AI 知识库之前，首先应该明确知识库究竟是用来查找信息、分析业务关系，还是长期积累组织知识。如果员工的主要需求是查询公司制度、查找产品参数、核对操作手册，那么普通 RAG 往往已经能够满足要求，没有必要为了追求技术复杂度额外引入知识图谱。如果企业需要分析多个项目为何反复出现相似问题，并进一步追踪涉及的团队、设备和供应商，那么就需要更强的跨文档关系组织能力。如果企业希望将每次项目结束后的经验、复盘结果和业务知识持续整理、更新和传承，则可以考虑 LLM Wiki。作者的核心逻辑是：先明确需要回答什么问题，再选择能够解决这些问题、同时成本合理的技术路线，而不是先选技术再寻找应用场景。

### 2. 普通 RAG 的本质是让大模型先查资料，再根据资料回答问题
RAG 的正确英文全称是 Retrieval-Augmented Generation（检索增强生成），这一技术名称由 Patrick Lewis 等研究人员在 2020 年发表的相关论文中提出并推广，当时的研究团队包括 Facebook AI Research（现属 Meta）等机构。其核心机制是在大模型回答用户问题之前，先从外部文档或知识库中检索相关内容，再将检索结果作为背景信息输入大模型。这样一来，模型就不必完全依赖训练阶段获得的参数知识，而是能够在推理阶段利用企业内部知识、垂直领域知识和具有时效性的最新资料。RAG 因此可以在一定程度上减少模型幻觉、增强专业问答能力、提高答案可追溯性，也能够为 Agent（智能体）提供执行任务所需的关键知识。需要注意的是，视频中所说的“修改模型的知识和记忆体系”，更准确地理解是扩展模型当前能够访问的知识，而不是重新训练模型或直接修改模型内部参数。
例如，员工询问：“公司的差旅住宿报销标准是什么？”
普通大模型可能根据通用经验给出一个看似合理、实际上不适用于本公司的答案；接入 RAG 后，系统可以先检索企业最新版《差旅费用管理制度》，找到对应的住宿标准、适用人员、地区限制和审批要求，再根据这些资料生成回答，并提供原文出处。
RAG 的核心价值：让 AI 从凭记忆回答，转变为有资料支持地回答。

### 3. 普通 RAG 的底层流程并不复杂，核心是文档切分、向量化、相似度匹配和答案生成
企业原始文档可能只有几百字，也可能包含几千字、上万字，甚至达到上百万字，因此通常不能将所有资料一次性输入大模型，而需要先将长文档拆分成多个 Chunk（文本块）。随后使用 Embedding（向量嵌入）模型，将每个文本块转换为计算机可以处理的高维数值向量，视频举例的向量维度包括 512、1024 和 2048 维。用户提出问题之后，系统会使用相应的向量模型对问题进行编码，并计算问题向量与各个文档向量之间的相似度。接下来选择相关程度最高的 Top-K 文档片段，将这些片段及用户原始问题一起放入大模型的上下文中。最终，大模型根据检索得到的背景知识生成答案，这就是最基础、最通用的向量检索型 RAG 流程。

### 4. Embedding 和语义检索是 RAG 能够理解自然语言含义的关键
计算机进行相似度计算时，需要将自然语言转换为可计算的数值表示，因此 RAG 通常使用 Embedding（向量嵌入）技术，将单词、句子或文档片段映射到高维向量空间。这个高维空间可以通俗地理解为一个“语义空间”，含义相近的文本，其对应的向量通常也会比较接近。视频举例说，“清晨”和“早上”虽然字面表达不同，但语义非常接近，因此它们在向量空间中的距离通常较近。当用户提出问题时，系统不必只查找完全相同的关键词，而可以通过向量相似度寻找表达方式不同但含义相关的文档。视频也指出，演示图中的三维向量只是为了便于理解，真实系统往往使用数百维乃至上千维的向量，不过向量只是对文本语义的近似编码，并不意味着它能够无损保留原文的全部信息。

### 语义向量空间示意
二维概念示意，并非实际模型计算结果。语义相近的词语倾向于聚集在一起，实际 Embedding 通常具有更高维度。
向量检索与传统关键词检索的区别，可以通过下面的补充例子理解：

| 对比项目 | 关键词检索 | 语义向量检索 |
| --- | --- | --- |
| 检索依据 | 字词是否匹配 | 文本含义是否相关 |
| 用户提问 | 公司出差能报多少钱？ | 公司出差能报多少钱？ |
| 文档表述 | 差旅费用报销标准 | 差旅费用报销标准 |
| 匹配方式 | 根据关键词及其组合查找 | 根据整体语义相关性匹配 |
| 主要优势 | 精确编号、名称、型号匹配 | 同义词、自然语言、不同表达 |
| 主要不足 | 可能漏掉表达不同的内容 | 可能混淆相近概念、数字或型号 |

实际企业系统也可以采用 Hybrid Search（混合检索），结合关键词检索和向量检索的优势，而不是只能选择其中一种。

### 5. GraphRAG 适用于需要跨文档关联、实体关系分析和全局总结的复杂业务
GraphRAG（图谱增强检索生成）与普通 RAG 的主要区别在于，它不仅关注哪些文档片段与用户问题相似，还关注文档中的 Entity（实体）及实体之间的 Relationship（关系）。例如，企业希望分析多个项目为什么反复发生同类故障，涉及哪些团队、设备、供应商和业务环节，这些信息往往分散在不同项目报告、会议纪要、维修记录和供应商资料中。GraphRAG 可以从文档中提取相关实体，建立实体之间的关系，并根据关系结构进行社区划分、主题归纳或关联检索，从而帮助模型找到分散在不同文档中的证据。在视频介绍的一种典型 GraphRAG 实现中，系统可以通过匹配相关实体或社区，找到对应的原始文档片段，也可以利用 Community Report（社区报告）回答宏观问题。不过，GraphRAG 的可靠性高度依赖实体提取和关系构建的质量，如果初始关系识别错误，后续检索和分析也可能受到影响，因此建图、纠错和持续更新都需要投入额外资源。
以企业生产设备故障分析为例，假设公司拥有以下四份相互独立的资料：

| 文档 | 记录内容 |
| --- | --- |
| 项目 A 复盘报告 | 设备 X 出现过热故障 |
| 项目 B 维修记录 | 设备 X 散热模块异常 |
| 供应商采购记录 | 散热模块由供应商 C 提供 |
| 项目质量报告 | 供应商 C 的部分产品存在质量隐患 |

普通 RAG 可能找到与“设备过热”直接相关的项目报告，却没有同时找到采购记录和供应商质量报告。
GraphRAG 则可以通过实体与关系建立跨文档联系。

### GraphRAG 跨文档关系分析示意
补充案例：通过连接项目、设备、部件、故障和供应商，发现值得进一步调查的共同因素。图谱中的关联不等同于已经证实的因果关系。
这样的知识组织方式，可以帮助企业进一步回答：
- 多个项目是否使用了相同的设备？
- 反复出现的故障是否集中在某个部件？
- 是否涉及同一家供应商？
- 哪些项目、团队或业务环节可能受到影响？
- 是否存在值得进一步调查的共同风险？

普通 RAG 主要解决“相关信息在哪里”，GraphRAG 则进一步解决“这些信息之间存在什么关系”。
当然，这并不意味着普通 RAG 无法进行跨文档分析。通过多轮检索、问题拆解、重排序和长上下文处理，普通 RAG 也能完成部分复杂任务。GraphRAG 的优势在于显式组织关系，使某些关联型问题的检索过程更加系统化，但最终是否更准确，仍然需要实际测试。

### 6. LLM Wiki 更适合持续积累项目经验，让企业知识从静态资料走向动态维护
如果企业的需求已经不局限于查找现有资料，而是希望每完成一个项目，都能够将经验、问题、解决方案和复盘结论整理到知识库中，那么视频建议考虑 LLM Wiki（大语言模型驱动的维基式知识库）。它的核心思想是让大语言模型协助将分散、原始、非结构化的资料整理成具有明确主题、页面结构和相互链接的知识体系。随着新项目、新文档和新经验的不断产生，系统可以对已有知识页面进行补充、更新、归类和关联，让后续员工能够沿着专题继续学习，而不只是重新搜索原始文件。与单纯的文档问答相比，这种方式更加重视知识的组织、复用、演化和长期积累。需要注意的是，LLM Wiki 并不是一种具有唯一标准实现的检索算法，也不一定需要使用正式的知识图谱数据库，其核心是利用 LLM 维护结构化、相互链接、能够持续演进的知识内容。
例如，一个软件开发团队先后完成了三个项目：

| 项目 | 项目结束后的知识沉淀 |
| --- | --- |
| 项目 A | 数据库选型经验、部署问题、性能优化方案 |
| 项目 B | 用户权限设计、接口规范、安全漏洞修复经验 |
| 项目 C | 高并发处理、缓存设计、服务器成本优化 |

如果只把所有项目报告上传到传统知识库，员工仍然需要根据问题搜索不同文档，重新拼接所需信息。
如果采用 LLM Wiki，可以进一步整理成数据库设计、权限管理、性能优化、系统部署、故障排查、项目复盘等专题，并将新项目产生的经验持续补充到对应页面。

这种机制的长期价值在于降低企业的重复学习成本：新员工不需要从头翻阅大量历史项目文件，老员工也可以将已经验证有效的解决方案持续沉淀为组织知识。
RAG 更偏向知识检索，GraphRAG 更偏向知识关联，LLM Wiki 更偏向知识组织与长期演化。
三者并不互斥，LLM Wiki 整理出来的专题页面，同样可以作为普通 RAG 或 GraphRAG 的知识来源。

### 7. RAG 是一种入门门槛很低，但技术上限很高的工程体系
视频反复强调，基础 RAG 的原理非常容易理解，无非是将长文档切分、向量化、检索相关片段，再交给大模型生成答案，因此很多大模型应用开发课程的第一课就是 RAG。然而，真正进入企业级应用之后，每一个环节都可能存在大量技术选项和工程问题，例如原始文档格式不规范、PDF 解析错误、切分造成上下文丢失、向量模型不能准确理解行业术语等。即使系统能够正常运行，也可能出现关键条款没有检索到、表格数字被错误关联、宏观问题总结不完整、用户真实意图理解错误等问题。为了解决这些问题，开发人员需要针对不同数据类型、不同业务需求和不同准确率要求设计相应的处理流程。作者因此认为，RAG 系统开发不仅依赖合适的工具，更依赖开发人员的实际工程经验，能够搭建一个演示系统与能够交付一个可靠的企业系统之间存在明显差距。
一个完整的企业级 RAG 系统，通常需要考虑以下环节：

| 技术环节 | 主要任务 | 典型难点 |
| --- | --- | --- |
| Document Parsing（文档解析） | 提取原始文件中的内容 | PDF 乱码、扫描件、复杂排版 |
| Chunking（文本切分） | 将长文档划分为文本块 | 上下文断裂、段落不完整 |
| Embedding（向量嵌入） | 将文本转换为向量 | 行业术语识别、语义表示偏差 |
| Indexing（索引构建） | 建立高效检索结构 | 大规模文档索引、版本同步 |
| Vector Database（向量数据库） | 存储向量并支持检索 | 查询效率、数据规模 |
| Retrieval（信息检索） | 找到与问题相关的资料 | 漏检、误检、相似内容干扰 |
| Reranking（重排序） | 对候选结果重新排序 | 真正有用的证据排名过低 |
| Context Engineering（上下文工程） | 组织输入模型的背景信息 | 信息过载、关键证据被淹没 |
| Generation（答案生成） | 根据资料回答用户问题 | 幻觉、条件遗漏、错误归纳 |
| Evaluation（效果评估） | 检验检索和回答质量 | 缺乏真实业务测试标准 |
| Maintenance（持续维护） | 更新资料、权限及索引 | 新旧版本冲突、维护成本 |

其中重排序、权限控制等内容属于对视频工程思路的进一步展开，并非视频逐项详细讲解的内容。
企业真正需要优化的不是某一个孤立环节，而是整条链路最终能否稳定地产出可靠答案。

### 8. Agentic RAG 和多模态 RAG 是基础 RAG 在复杂应用场景中的重要扩展
随着大模型应用逐渐深入，传统的“每次提问都检索文本知识库”的固定流程，已经无法覆盖所有业务需求，因此出现了 Agentic RAG（智能体式检索增强生成）和 Multimodal RAG（多模态检索增强生成）等技术路线。Agentic RAG 将知识检索视为智能体可以按需调用的一项工具，让 Agent 自主判断当前问题应该查询企业知识库、使用大模型已有知识，还是调用网络搜索或其他外部工具。视频将其与 ReAct Agent（结合推理与行动的智能体）联系起来，强调它的核心变化在于检索的触发方式、决策机制和工作流程更加灵活，而底层仍然可以使用普通 RAG 的检索机制。多模态 RAG 则面向包含图片、表格、视频等非纯文本信息的资料，例如检索 PDF 中的图表、通过图片搜索相似图片、寻找相关视频内容。两种扩展技术分别解决了“什么时候检索、检索什么”和“哪些类型的信息能够被检索”的问题，反映出 RAG 正在从简单文本问答发展为面向复杂任务的知识调用体系。

不同场景下的知识调用方式可以有所区别：

| 用户问题 | 合适的知识调用方式 |
| --- | --- |
| 什么是光合作用？ | 模型已有知识 |
| 公司今年的报销标准是什么？ | 企业内部 RAG |

| 找出与这张故障图片相似的历史案例 | 多模态 RAG |
| 查询产品参数并对照行业最新标准 | 企业知识库与外部检索结合 |
| 分析多个项目发生故障的共同原因 | 多轮检索或 GraphRAG |

Agentic RAG 与普通 RAG 的区别，并不是简单地换了一种向量模型，而是将原本固定的信息检索流程升级为能够按任务需求动态选择工具的流程。

### 9. 企业 RAG 很难依靠一个通用产品解决所有问题，实际工程往往需要定制化
视频提到了 MaxKB 和 RAGFlow 等开源 RAG 项目，也提到市场上存在大量付费企业知识库产品，但作者认为很难有某一个开源框架或商业产品能够解决所有企业的 RAG 需求。原因在于，不同企业的数据结构、文档质量、行业术语、检索方式、响应要求和答案准确率标准存在明显差异。例如，制度查询主要要求条款精确和版本正确，而制造业知识库可能更重视设备型号、维修记录、技术图纸及供应商关系，财务或科研场景则可能非常依赖表格、数字和专业资料的结构化处理。视频还指出，大规模语料中的语义迷失、高价值数据的结构化信息丢失、宏观问题总结不完整以及系统效果难以评估，都是实际落地过程中可能面临的困难。正因为这些问题需要结合企业实际情况进行优化，作者认为 RAG 系统开发能力是大模型应用工程师的重要技能之一，而不仅仅是调用某个现成框架的能力。
这里需要重点理解几个企业级 RAG 的典型问题。

| 问题 | 具体表现 | 可能的影响 |
| --- | --- | --- |
| 检索精度不足 | 找到了相关主题，但不是正确条款 | 答案看似正确，实际不能执行 |
| 语义迷失 | 大量相似资料干扰真正需要的信息 | 检索结果相关但不准确 |
| 用户意图理解不足 | 不知道用户具体要查询哪个对象 | 检索方向错误 |
| 结构化信息丢失 | 表格转成纯文本后行列关系消失 | 数字与对象错误对应 |
| 宏观总结不完整 | 只检索少量局部内容 | 无法全面回答整体问题 |
| 多模态检索困难 | 图片、图纸、视频内容无法有效利用 | 关键业务信息被遗漏 |
| 新旧资料冲突 | 已废止制度仍然被检索出来 | 给出过时答案 |
| 评估体系不完善 | 没有明确标准判断回答是否可靠 | 无法持续优化系统 |

例如，一张产品参数表中包含多个型号、额定电压、额定功率、尺寸和工作温度。如果文档解析时丢失行列对应关系，AI 虽然检索到了正确的表格内容，却可能把 A 型号的功率错误地匹配给 B 型号。
这种错误不是单纯更换一个能力更强的大模型就一定能够解决的，还需要改进数据解析、结构保留、检索策略和答案验证机制。

### 10. 判断知识库是否成功，必须使用真实业务问题进行验收，而不能只看演示效果
作者给出了一个非常实用的知识库测试原则：不要只挑选容易回答的问题进行展示，而要将高频问题、复杂问题和容易出错的问题全部纳入测试集合。在测试之前，应该明确每个问题的标准答案必须包含哪些关键信息、证据来自哪份资料，以及是否存在版本、条件和适用范围限制。随后不仅要检查系统最终回答是否正确，还要检查所提供的引用是否真正支持结论，避免出现答案碰巧正确、引用却不相关的情况。企业资料更新后，也应该重新测试系统，判断知识库是否及时同步新版本、是否继续使用过期内容，以及维护和更新机制是否可靠。最后还要将响应时间、单次问答成本、知识库建设成本和长期维护成本纳入考虑，因为一个技术上表现优秀但业务上无法承担的系统，同样不是合适的企业知识库方案。
视频提出的验收思路，可以归纳为五个核心维度：

### 01

答案准确性
事实、数字、条款和适用条件是否正确，有没有遗漏关键内容？

### 02

引用可靠性
引用的文档是否真实存在，相关证据是否足以支持答案？

### 03

知识时效性
资料更新、制度修订之后，系统还能不能给出正确的新答案？

### 04

响应效率
一次检索和回答所需的时间，能否满足真实业务需求？

### 05

建设与维护成本
模型调用、数据库、图谱构建、人工审核及后续更新成本是否可以接受？

作者最终形成的知识库建设原则是：先列出业务问题，再选择技术路线，最后用真实业务问题完成验收。

### 四、视频提到的文档切分方法

| --- | --- | --- |

| 句子切分 | 根据句子边界划分 | 希望保持单句语义完整 |

| 关键词切分 | 根据关键词或特定标志划分 | 固定格式的业务文档 |

## 金句摘录
以下摘录来自原始文字稿，适当修正了语音识别错误及重复语气词。
**1. 关于知识库选型**
“选知识库，先把业务问题列清楚，再看哪条路线能满足，最后拿真实问题验收。”

这是整段视频最重要的方法论：技术选型服从业务需求，实际效果优先于技术名词。
**2. 关于普通 RAG 的评价标准**
“这种业务最看重的是条款找没找对，关键条件有没有漏，能不能回到原文核对。”

企业知识库最重要的不是回答得多么流畅，而是信息准确、条件完整、证据可查。
**3. 关于 GraphRAG 的风险**
“不过关系提错了，后面也会跟着错，所以建图和更新都得有人管。”

知识图谱并不会天然保证准确性，结构化错误同样会影响后续的知识检索和推理。
**4. 关于 RAG 的技术门槛**
“整个的 RAG 技术体系，其实是一个门槛比较低，但上限很高的技术。”

能够运行 RAG 系统与能够交付高质量 RAG 系统，是两个完全不同的能力层次。
**5. 关于知识库测试方法**
“高频问题、容易出错的问题都要放进去，别只挑好回答的。提前写清楚答案必须包含什么，依据在哪。”

企业知识库应该接受真实问题和困难问题的检验，而不是只通过经过精心挑选的案例证明自己有效。
**6. 关于通用产品的局限性**
“基本上所有的这些 RAG 系统，放到一个具体的场景里面，它或多或少都会有一些问题。”

没有一种知识库产品能够天然适应所有行业和业务环境，真正的价值来自持续优化和场景适配。

## 值得记住的点 / 行动建议

### 1. 建设知识库之前，先整理企业真实的业务问题清单
不要一开始就研究应该购买什么向量数据库、选择哪个大模型、使用哪个开源框架，而应该先找到企业中实际使用知识库的人，并明确他们最希望解决的问题。
可以将业务问题分成六类：

| 问题类型 | 示例 | 优先考虑的方案 |
| --- | --- | --- |
| 事实查询 | 公司年假申请需要哪些材料？ | 普通 RAG |
| 精确参数查询 | 产品 A 的额定功率是多少？ | RAG + 精确检索 |
| 跨文档分析 | 哪些项目反复出现相同问题？ | 多轮 RAG 或 GraphRAG |
| 关系追踪 | 哪些供应商涉及相同故障设备？ | GraphRAG |
| 经验沉淀 | 如何将历次项目复盘整理成知识？ | LLM Wiki |
| 复杂任务执行 | 查询内部制度，再结合最新外部政策回答 | Agentic RAG |

如果绝大多数问题都集中在前两类，那么优先使用普通 RAG 即可，不必一开始就建设复杂的知识图谱。
如果关系分析是企业的核心需求，再重点考虑 GraphRAG。
如果企业最大的痛点是项目经验无法传承、知识散落在员工个人文件和聊天记录中，那么应该重点考虑 LLM Wiki 所代表的知识沉淀机制。

### 2. 普通企业知识库可以先从最小可行系统开始，不要过度设计
对于刚开始建设知识库的企业，建议先搭建 MVP（Minimum Viable Product，最小可行产品），选择一个数据范围明确、业务价值明显的场景进行验证。
例如，可以先建设一个公司制度问答机器人，只接入员工手册、财务报销制度、采购管理制度、行政管理制度和常见业务流程。
第一阶段的目标不是让 AI 回答所有问题，而是确保能够稳定回答限定范围内的问题，并且支持回到原始文件核对。
可以按照以下建设顺序推进：
**1. 确定一个具体业务场景**
例如制度查询、产品手册问答或者内部客服。
**2. 收集并清洗原始资料**
去重、删除过期资料、统一名称及文件版本。
**3. 搭建基础 RAG 系统**
完成解析、切分、向量化、索引和检索。
**4. 设计真实业务测试集**
包括高频问题、难题、边界问题及无答案问题。
**5. 定位错误并优化**
判断问题究竟出在解析、检索还是生成环节。
**6. 根据业务需求扩展**
必要时再增加图谱、智能体、多模态检索和 Wiki。

这样做的好处是可以降低初期开发成本，并且尽快验证知识库是否真正有用，避免建设一个技术上复杂、业务上却没有需求的系统。

### 3. 不要把向量数据库等同于完整的企业知识库
向量数据库只是 RAG 系统中的一个技术组件，它主要负责向量存储、索引以及相似度搜索。
企业知识库是否有效，还取决于资料是否完整、数据解析是否准确、文档切分是否合理、检索策略是否有效、模型是否遵守证据，以及资料能否及时更新。
如果原始资料本身就是错误的，那么即使使用性能非常强的向量数据库，也只能更快地检索到错误资料。
如果产品手册中的表格被错误解析，使用更强的 Embedding 模型也不一定能够恢复原始表格的行列关系。
因此，遇到知识库回答错误时，应该首先判断错误发生在什么环节，而不是直接更换大模型。

| 错误表现 | 优先排查方向 |
| --- | --- |
| 完全找不到相关资料 | 数据导入、文档解析、索引 |
| 找到了相关资料，但不是正确条款 | 检索模型、关键词匹配、重排序 |
| 找到了正确条款，但遗漏重要条件 | 文档切分、上下文组织 |
| 找到了正确证据，但回答仍然错误 | 提示词、生成模型、答案约束 |
| 回答使用过期制度 | 数据版本、更新机制 |
| 产品型号与参数对应错误 | 表格结构、精确字段检索 |
| 全局性问题总结不完整 | 检索覆盖范围、问题拆解、图谱与全局总结 |

### 4. 正确理解 Top-K：检索更多资料不一定意味着答案更准确
Top-K 指的是从知识库中选出相关程度最高的 K 个候选文档片段。
例如，假设知识库中有 10,000 个文档片段，当用户提出问题后，系统通过相似度计算选出排名最靠前的若干片段。
如果 K 设置得太小，可能漏掉关键证据；如果 K 设置得太大，可能引入大量无关信息、重复内容甚至互相矛盾的资料，同时增加模型输入成本。

### 5. 只有当跨文档关系是核心需求时，才优先建设 GraphRAG
GraphRAG 虽然能够显式构建实体及关系，但其开发和维护成本通常更高，因此并不适合所有场景。
建设之前，可以重点检查企业是否需要回答以下类型的问题：
- 不同项目之间是否存在共同问题、共同设备或共同供应商？
- 一个故障可能涉及哪些部件、人员、团队和业务流程？
- 某个政策或制度变化会影响哪些业务部门？
- 某项风险是否同时出现在多个项目中？
- 企业内部的人员、产品、客户、供应商之间是否存在复杂关联？

如果这些问题具有高频率、高业务价值，并且普通 RAG 很难稳定回答，那么建设 GraphRAG 就具有更充分的理由。
同时，GraphRAG 系统应该保留每条实体关系的原始资料依据。例如，系统不能只记录“供应商 A 存在质量问题”，还应该记录该结论来自哪份报告、报告时间、适用产品以及是否经过人工确认。
图谱的价值不仅在于发现关系，更在于关系能够得到可靠证据的支持。

### 6. 将 LLM Wiki 用作企业知识资产管理系统，而不仅是另一个聊天机器人
企业真正有价值的知识，并不只是已经写好的制度和手册，还包括员工解决问题的过程、过去项目的失败经验、技术方案的取舍依据以及经过长期实践总结出的最佳做法。
建议在每次项目结束后，形成统一的知识沉淀机制，将项目原始资料交给 LLM 协助整理成专题知识页面，再由相关业务负责人进行审核。
每个项目至少可以沉淀以下内容：

| 知识模块 | 需要记录的信息 |
| --- | --- |
| 项目背景 | 项目目标、业务需求、限制条件 |
| 技术方案 | 使用的技术、选择依据 |
| 实际问题 | 遇到的故障、风险和困难 |
| 解决方案 | 已验证的方法及操作流程 |
| 失败经验 | 尝试过但没有达到目标的方法 |
| 决策依据 | 为什么选择某种方案而放弃其他方案 |
| 可复用资产 | 模板、代码、文档、工具 |
| 适用边界 | 哪些经验可以推广，哪些不能照搬 |
| 原始证据 | 原始报告、会议记录、测试结果 |
| 维护信息 | 更新时间、版本、责任人 |

当新项目结束后，不必再建立一套完全孤立的知识资料，而是判断哪些内容应该新增为专题页面，哪些应该补充到已有页面，哪些旧结论需要修正。
这会让知识库从一个静态文件仓库逐渐转变为企业能够长期积累和复用的知识资产。

### 7. 根据数据类型选择检索方式，尤其重视表格、图片和技术文档
并不是所有企业资料都适合直接转换成纯文本，然后使用普通向量检索。
制度文件通常以自然语言为主，普通文本 RAG 可以很好地发挥作用；产品参数表则高度依赖结构化字段、型号和数字对应关系；技术图纸、维修图片和视频资料还涉及视觉信息。
可以根据不同数据类型采取不同处理方式：

| 数据类型 | 推荐处理方式 |
| --- | --- |
| Word 制度文件 | 文本解析、段落切分 |
| 普通文本 PDF | 版面解析、文本检索 |
| 扫描版 PDF | OCR 文字识别与版面分析 |
| Excel 参数表 | 保留表格结构、字段过滤或结构化查询 |
| 产品图片 | 图像向量与多模态检索 |
| 工程图纸 | 视觉理解、专业数据提取 |
| 视频资料 | 语音转录、关键帧分析、多模态检索 |
| 结构化数据库 | SQL 查询或数据查询工具 |
| 项目关系资料 | 实体提取、关系组织、GraphRAG |
| 经验总结与操作流程 | LLM Wiki 专题组织 |

实际企业知识库可以同时采用多种方式，避免将所有数据强行压缩到同一种表示形式中。

### 8. 建立真实业务测试集，形成可量化的知识库验收标准
视频中最值得直接落地的建议，就是提前准备一套真实业务问题进行验收。
作为实践补充，初期可以整理 50～100 个有代表性的问题，并随着系统运行不断扩展测试集。这个数量属于实施建议，并非视频给出的固定标准。
测试集不应该只包含有明确答案的简单问题，还应该包括模糊提问、多条件问题、跨文档问题、过期资料问题，以及知识库中根本不存在答案的问题。
下面是一份可以直接参考的企业知识库测试表结构：

| 编号 | 测试问题 | 预期结果 | 测试重点 |
| --- | --- | --- | --- |
| Q01 | 公司年假如何申请？ | 给出正确流程和制度出处 | 基础准确率 |
| Q02 | 上海出差住宿标准是多少？ | 包含适用条件和具体标准 | 条款完整性 |
| Q03 | 产品 X 的额定电压是多少？ | 正确型号、数值和单位 | 精确参数 |
| Q04 | 哪些项目出现了同类故障？ | 找出相关项目及原始记录 | 跨文档召回 |
| Q05 | 多个项目故障有何共同因素？ | 归纳相关关系并提供证据 | 关联分析 |
| Q06 | 最新制度修改了什么？ | 区分新旧版本及生效时间 | 知识时效性 |
| Q07 | 某项制度没有明确规定怎么办？ | 说明资料不足，不编造 | 拒答能力 |
| Q08 | 这张设备故障图对应什么问题？ | 找到相似案例及相关资料 | 多模态能力 |
| Q09 | 哪些团队可以查看财务资料？ | 遵守实际访问权限 | 数据安全 |
| Q10 | 项目复盘后能否更新经验页面？ | 正确补充知识并保留版本 | 持续维护 |

建议进一步将验收结果转化成可量化指标：

| 指标 | 衡量内容 |
| --- | --- |
| Answer Accuracy | 答案准确率 |
| Recall@K | 前 K 个检索结果覆盖相关证据的程度 |
| Precision@K | 前 K 个检索结果中相关内容所占比例 |
| Citation Accuracy | 引用资料是否正确支持答案 |
| Completeness | 回答是否包含必要信息和限制条件 |
| Faithfulness | 回答是否忠实于提供的资料 |
| Abstention Accuracy | 资料不足时是否能够合理拒答 |
| Latency | 单次回答的响应时间 |
| Cost per Query | 单次问答成本 |
| Update Delay | 资料更新到知识库生效之间的延迟 |

具体指标阈值应该由业务风险和实际使用要求确定，而不是所有企业统一规定一个准确率目标。

### 9. 同时核算知识库的使用成本和长期维护成本
企业知识库的成本不能只看第一次搭建需要多少钱，还要考虑以后每个月使用、更新、纠错和管理需要多少资源。
普通 RAG 主要涉及文档解析、Embedding 调用、向量数据库以及大模型推理费用；GraphRAG 在此基础上可能增加实体关系抽取、图谱构建、社区总结和图谱更新成本；LLM Wiki 则可能增加页面生成、知识归并、版本管理和人工审核成本。

### 10. 三种知识库路线可以组合使用，不必强行三选一
对于规模较大、业务类型复杂的企业，RAG、GraphRAG 和 LLM Wiki 更适合理解为可以相互补充的能力，而不是三个彼此排斥的产品。
企业可以使用普通 RAG 提供高频日常查询服务，使用 GraphRAG 分析复杂项目关系，再使用 LLM Wiki 持续整理项目经验。Agentic RAG 则可以在上层负责识别用户需求，根据实际问题选择合适的知识来源和工具。

这种混合方案的关键不是所有技术都必须使用，而是让不同技术负责自己擅长的任务，避免用一种检索机制强行解决所有业务问题。

### 11. 如果希望学习 AI 应用开发或从事大模型工程，应该系统掌握 RAG 的完整技术链路
视频指出，RAG 是大模型应用工程师非常重要的技术能力之一，其原因在于企业往往需要基于自己的数据和业务需求构建定制化知识库，而不是简单调用通用大模型接口。
学习时不应该只满足于使用 MaxKB、RAGFlow 等现成平台成功上传文档、创建聊天机器人，更应该理解系统为什么能够检索到正确资料，以及发生错误时应该如何解决。
建议按照以下路径学习：
**1. 第一阶段：基础原理**
掌握 LLM、Token、Embedding、向量相似度、语义检索和 RAG 基本流程。
**2. 第二阶段：搭建基础系统**
学习文档解析、Chunking、向量数据库、Top-K 检索及提示词设计。
**3. 第三阶段：检索质量优化**
学习混合检索、重排序、问题改写、元数据过滤和上下文组织。
**4. 第四阶段：复杂数据处理**
学习 PDF 版面解析、表格处理、OCR、图片及多模态检索。
**5. 第五阶段：高级 RAG**
学习 GraphRAG、Agentic RAG、多轮检索以及工具调用。
**6. 第六阶段：知识管理**
学习 LLM Wiki、知识分类、自动更新、版本控制和人工审核。
**7. 第七阶段：企业级工程化**
掌握权限管理、系统评估、日志追踪、响应优化、成本控制和持续迭代。

最终应该具备的不只是搭建知识库的能力，还包括需求分析、技术选型、效果优化、问题排查和企业级交付能力。

### 12. 牢记企业知识库建设的五个认知转变

| 容易产生的误区 | 更准确的理解 |
| --- | --- |
| 上传文档就是建设知识库 | 知识库还需要解析、组织、检索、维护与评估 |
| 模型越强，知识库效果越好 | 数据质量和检索质量同样关键 |
| GraphRAG 一定比普通 RAG 先进且准确 | 两者适用场景不同，必须进行真实业务测试 |
| AI 自动整理知识就不需要人工 | 关系错误、总结错误、版本冲突仍然需要审核 |
| 知识库建成之后工作就结束了 | 知识库是一项持续更新和优化的长期工程 |

## 我的点评
这段视频最有价值的地方，是将企业知识库技术选型重新拉回业务需求、实际效果和长期维护成本，而不是单纯追逐 GraphRAG、Agentic RAG 等技术概念。普通 RAG、GraphRAG、LLM Wiki 的区分有助于建立整体认知，但三者并非完全平行的技术类别，其中 RAG 和 GraphRAG 更偏向检索与生成机制，LLM Wiki 更偏向知识组织和持续维护机制，因此实际工程中完全可以组合使用。视频对 RAG 基础流程、Embedding、语义检索及工程复杂度的解释比较直观，但“普通 RAG 能够完美解决简单查询”“GraphRAG 能够提高关联分析准确度”等表述仍然需要结合具体数据质量和测试结果理解，不能视为必然成立。知识库建设还有一些视频没有充分展开的重要问题，例如企业数据权限、商业机密保护、不同版本资料冲突、知识过期和模型在证据不足时的拒答机制，这些往往也是企业正式部署时不可忽视的风险。对于普通开发者或企业管理者，最值得采用的策略是先从低成本、范围明确的 RAG 系统开始，建立一套真实业务测试集，再根据实际遇到的困难引入图谱、智能体或知识沉淀机制。归根结底，成熟的企业 AI 知识库不是一个能够与文件聊天的机器人，而是一套能够可靠获取、组织、验证、更新和复用组织知识的基础设施。
