## 🤖 AI 分析

## 一句话概括

这个视频用一条“AI 从聊天工具走向真实工作系统”的主线，把 Token、Prompt、RAG、Tool Calling、MCP、Context Engineering、Skill、Computer Use、Agent、Harness Engineering、Workflow、Workspace Agent 等 AI 热词串成了一张清晰的演进地图。

## 背景与主题

这期视频的出发点是：很多人感觉 AI 圈的新词越来越多，像“黑话制造机”，刚搞懂 Prompt，又出现 RAG；刚听懂 RAG，又出现 Agent、MCP、Skill、Context Engine、Workspace Agent。作者并不是逐个堆定义，而是试图解释这些概念“为什么出现、解决了什么问题、彼此之间是什么关系”。视频的核心立场是：AI 热词不是为了制造焦虑，而是因为 AI 每往真实工作场景靠近一步，就会遇到一个新问题，于是产生一个新概念或工程方法。整期内容按技术演进路径展开，从 AI 一次能看多少信息，到如何理解任务、查资料、调用工具、连接外部系统、复用能力、操作电脑、循环执行任务，最后进入企业工作流和团队工作空间。

## 核心观点

### 1. Token 和 Context Window 决定了 AI 一次能“看见”多少信息

视频首先强调，AI 并不是像人一样直接阅读整篇文章，而是会把输入内容拆成一个个更小的信息单位，这些单位叫 **Token**。例如你输入“我喜欢人工智能”，模型眼里它可能不是一句完整的话，而是被拆成“我 / 喜欢 / 人工智能”等片段；不同模型的拆法不同，有时一个中文词会被拆成多个 Token，一个英文单词也可能被拆成几段。Token 重要，是因为它影响三件事：AI 一次能读多少内容、调用 AI 的成本是多少、以及为什么 AI 有时会忘记前面聊过的内容。比如一个模型最多能处理 8000 个 Token，那么你的问题、历史对话、系统提示词、文件内容、工具返回结果加起来都不能超过这个范围；一旦超出，前面的内容就可能被“挤出去”。作者用了一个形象比喻：你的桌面只能摊开十张纸，新的资料不断放上来，最早的资料就会被拿走；模型一次最多能看到多少 Token，就是 **Context Window，上下文窗口**。

### 2. 上下文窗口越大，不代表 AI 一定越聪明

视频特别提醒，不要把“长上下文”误解成“更聪明”。现在很多产品会宣传 128K 上下文、百万 Token 长上下文模型、按 Token 计费，本质上说的都是“这个 AI 一次最多能处理多少信息，以及你给它喂了多少信息”。但上下文窗口大只是容量变大，并不等于判断力、理解力或任务执行能力自动提升。信息太少，AI 可能答不出来；信息太多，AI 反而会被无关内容干扰，甚至抓不住重点。因此，真正好用的 AI 不只是“能看多少”，而是系统是否把任务交代清楚、是否把正确的信息放到模型面前。这个问题直接引出了第一个出圈热词：**Prompt**，也就是如何把任务说明白。

### 3. Prompt Engineering 的本质不是“咒语”，而是给 AI 写工作说明书

作者指出，早期用户发现，同一个问题用不同问法，AI 输出质量差别非常大。比如随口说“帮我写个方案”，AI 可能会写出一堆很空泛的话，比如“提升效率、优化体验、扩大影响力、增强用户粘性”，看起来完整但没什么用。相反，如果你明确说：“你是一名资深产品经理，请针对一个面向开发者的 AI 工具写一份产品方案，要求包含目标用户、核心痛点、功能模块、商业模式和落地路径，用表格输出”，结果就会更具体、更有结构，也更接近用户想要的东西。因此，Prompt Engineering 本质不是写“神级咒语”，而是给 AI 写一份清晰的工作说明书：告诉它角色、任务、背景、输出格式、不要写什么、什么结果算好，最好还能给几个例子。早期那些“万能提示词”“神级 Prompt”“学会 10 个提示词效率提升 10 倍”之所以火，是因为它确实解决了早期 AI 使用中最直接的问题：怎样让 AI 更准确理解我的任务。

### 4. RAG 解决的是“模型不知道的东西不能靠猜”的问题

Prompt 再强，也只能解决“任务怎么说清楚”，无法解决“模型没见过你的资料”这个问题。你让 AI 总结公司内部文档，它如果没看过文档就不知道；你让它分析项目代码，它如果没读过代码就不知道；你让它回答昨天才发生的事情，它训练时可能根本没有。此时如果硬让 AI 回答，它就可能“很会组织语言地胡说八道”，也就是一本正经编答案。RAG 的思路就是：不要让 AI 只凭记忆回答，而是先让它查资料，再让它基于资料回答。RAG 全称是 **Retrieval Augmented Generation**，中文一般叫“检索增强生成”，逻辑很简单：先检索，再生成；比如问“请假要提前几天申请”，系统先从员工手册里搜索“请假申请提前”的相关条款，再让 AI 回答“根据员工手册，年假需要提前三个工作日申请，病假需要提交证明”，这就不是瞎编，而是基于资料回答。

### 5. Embedding、向量数据库和知识库，是 RAG 能“查相似语义”的基础

RAG 背后带出了几个重要概念：**embedding、vector database、knowledge base**。Embedding 简单说就是把文字变成一串数字，因为计算机不懂“意思”，但可以比较数字之间的距离。比如“怎么申请退款”和“订单取消后钱怎么退”这两句话，字面关键词并不完全一样，但语义很接近；如果只用关键词搜索，可能匹配不准，但如果把它们变成向量，系统就能判断两句话在语义上相似。向量数据库就是专门存这些向量，并且能快速找出相似内容的地方。RAG 的意义在于，它让 AI 从“只靠脑子回答”变成“可以翻资料回答”，这也是 AI 第一次比较系统地具备接入外部知识的能力。不过普通 RAG 像一次搜索，复杂问题往往查一次不够，于是出现了 **Agentic RAG**：它会判断资料是否足够、不够就换关键词继续查，问题太大就拆成子问题，多个来源冲突时还要交叉对比。

### 6. Tool Calling 让 AI 从“给建议”变成“能执行动作”

RAG 给 AI 一个“资料室”，但 AI 仍然不能真正做事。它可以告诉你怎么发邮件，但不能真的发；可以告诉你怎么查订单，但不能真的查；可以告诉你代码怎么改，但不能真的改你的项目。**Tool Calling / Function Calling** 解决的就是这个问题：AI 可以调用外部工具，从生成文字走向执行动作。比如你问“我今天下午有空吗”，没有日历工具时，AI 只能建议你“可以查看日历”；接入日历工具后，它可以直接查询日历并告诉你“下午 2 点到 3 点有会，4 点以后比较空”。这一步的关键变化是，AI 不再只是输出建议，而是可以通过订单系统、代码执行环境、日历、数据库等工具完成一部分动作；但工具一多，就会出现接口混乱、权限难管、参数难传、结果难返回的问题，于是又引出了 MCP。

### 7. MCP 的价值不是让模型更聪明，而是统一 AI 连接外部世界的方式

作者把 **MCP** 比喻成 AI 世界里的 **USB-C**，这个比喻非常关键。过去每个 AI 应用接工具都像“自己焊电线”：接 GitHub 要写一套，接数据库要写一套，接文件系统又要写一套，接企业内部系统还要再写一套，开发和维护成本都很高。MCP 想解决的是：工具怎么暴露给 AI，AI 怎么知道自己可以调用哪些能力，工具需要哪些参数，调用结果怎么返回，资源怎么提供，权限和安全边界怎么控制。也就是说，MCP 不是一个普通工具，而是 AI 接入工具生态的连接层。它的出现说明 AI 已经不只是一个聊天框，而是开始变成一个可以接插件、接数据源、接工具系统的工作平台。

### 8. Context Engineering 关注的不是一句 Prompt，而是 AI 每次任务到底该看到什么

视频强调，Prompt Engineering 不是过时了，而是不够了。早期问题是“这一句话怎么写得更好”，但 AI 应用复杂后，真正的问题变成了：这次任务系统应该给 AI 准备哪些信息？它要不要看到历史对话、用户资料、数据库结果、上一次任务状态、公司规范、工具调用结果？这就是 **Context Engineering**：Prompt Engineering 是写一条好指令，Context Engineering 是设计整个信息流。比如让 AI 帮你回复客户，一个简单 Prompt 只能根据当前输入写回复；真正好用的客户助手还要知道客户是谁、之前买过什么、投诉过什么、公司退款政策是什么、是否需要升级人工处理。上下文不是越多越好，太少会答不准，太多会被干扰，信息过期会导致错误判断，权限没管好还可能泄露敏感数据；所以 Context Engineering 的核心不是给 AI 更多信息，而是给它“刚好需要的信息”。

### 9. Skill 把一次性指令沉淀成可复用 SOP

**Skill** 解决的是一个普通人非常容易理解的问题：我不想每次都重新教 AI 一遍。比如你每周写工作周报，每次都要重新交代“这周做了哪些事、哪些项目有进展、哪些问题没解决、下周计划怎么写、语气正式但不要空、不要流水账、要突出成果”，说少了 AI 写得不像，说多了又像每次重新培训新人。Skill 的价值就是把这套要求保存下来，以后只要说“按我的周报格式来写”，AI 就知道要先整理本周事项、提炼成果和问题、按固定格式输出，再调整成适合公司汇报的语气。作者总结得很清楚：Prompt 更像一次性指令，Skill 更像长期 SOP。写周报、分析代码仓库、处理财务表格都可以是 Skill；个人可以沉淀自己的工作风格，团队可以沉淀标准流程，企业可以把岗位经验变成可复用的 AI 能力。

### 10. Agent 不是更会聊天，而是能围绕目标循环执行任务

视频对 **Agent** 做了一个很重要的澄清：Agent 不是“更聪明的聊天机器人”，关键不在聊天，而在于它能围绕一个目标自己拆步骤、选工具、观察结果，再继续调整。普通聊天机器人是你问一句它答一句，Tool Calling 是你让它做一个动作它调用一个工具，而 Agent 更像你给它一个目标，它自己想办法推进。例如你说“帮我分析这个项目最近为什么启动失败”，普通 AI 可能只是建议你检查配置、依赖、端口、环境变量；而一个编程 Agent 会真的开始看错误日志、读配置文件、检查依赖版本、搜索代码调用、运行测试，如果出现新报错再继续定位，最后给出修改方案甚至直接改代码。Agent 的核心循环是：计划、行动、观察结果、根据结果调整下一步。这也是为什么 Agent 最先在编程领域爆发，因为代码项目有明确文件、具体报错、测试反馈、版本控制和可验证结果，Cursor、Claude Code、Codex、Gemini CLI 等 AI IDE / Coding Agent 都是在往这个方向发展。

## 关键事实与数据

- **Token**：AI 处理输入内容的基本信息单位，输入文本会先被拆成 Token，再由模型处理。
- **Context Window / 上下文窗口**：模型一次最多能看到多少 Token。视频举例说，如果一个模型最多处理 **8000 个 Token**，那么问题、历史对话、系统提示词、文件内容、工具返回结果加起来都不能超过这个范围。
- **长上下文模型**：视频提到常见宣传词包括 **128K 上下文**、**百万 Token 长上下文模型**、**按 Token 计费**。
- **Prompt Engineering**：核心是给 AI 写工作说明书，包括角色、任务、背景、输出格式、限制条件、评价标准和示例。
- **Prompt 示例**：从“帮我写个方案”升级为“你是一名资深产品经理，请针对一个面向开发者的 AI 工具写一份产品方案，要求包含目标用户、核心痛点、功能模块、商业模式和落地路径，用表格输出”。
- **RAG**：全称 **Retrieval Augmented Generation**，中文通常叫“检索增强生成”，逻辑是“先检索，再生成”。
- **RAG 示例**：问“请假要提前几天申请”，系统先从员工手册检索相关条款，再回答“年假需要提前三个工作日申请，病假需要提交证明”。
- **Embedding**：把文字变成一串数字，使系统可以比较语义相似度。
- **Vector Database / 向量数据库**：存储文本向量，并快速检索相似内容的数据库。
- **Knowledge Base / 知识库**：公司文档、产品手册、项目代码、课程资料、客户记录等资料集合。
- **Agentic RAG**：普通 RAG 的升级版，会拆问题、换关键词继续查、判断资料是否足够，并对多个来源做交叉对比。
- **Tool Calling / Function Calling**：AI 调用外部工具执行动作，例如查订单、跑 Python、查日历。
- **MCP**：被作者比喻成 AI 世界里的 **USB-C**，用于统一 AI 连接外部工具和数据源的方式。
- **Context Engineering**：设计 AI 每次执行任务时应该看到哪些信息，而不只是写一句 Prompt。
- **Context Engine**：更产品化的系统，自动组装上下文，例如查资料、带历史记录、过滤敏感信息、压缩长内容、把重要信息放前面。
- **Skill**：把重复任务的做法沉淀成长期可复用能力，类似 SOP。
- **Skill 示例**：写周报、分析代码仓库、处理财务表格。
- **Computer Use**：AI 像人一样看屏幕、用鼠标键盘操作电脑，适合没有 API 或 API 难接的旧系统。
- **Computer Use 示例**：打开报销系统、找到新增报销入口、识别发票金额、填写表单、上传文件、提交申请。
- **相关概念**：AI Browser、Browser Agent、Operator。
- **Agent**：围绕目标进行计划、行动、观察、调整的循环执行系统。
- **编程 Agent 示例**：看错误日志、读配置文件、检查依赖版本、搜索相关调用、运行测试、根据报错继续修改、生成提交说明甚至提交 PR。
- **AI Coding Agent / AI IDE 名称**：Cursor、Claude Code、Codex、Gemini CLI。
- **Vibe Coding**：从“人写代码、AI 辅助”转向“人描述目标、AI 生成实现，人负责验收和调整”。
- **Harness Engineering**：给 Agent 加安全带、方向盘、仪表盘和刹车系统，包括权限控制、工具白名单、沙箱执行、日志追踪、错误重试、输出验证、人工审批、成本控制、安全边界、回滚机制、评测系统。
- **Workflow 工具**：视频提到 n8n、Dify、Zapier、Make、LangGraph 等，用于把 AI、API、数据库、消息系统、人工审批、定时任务和条件判断串起来。
- **Workflow 示例**：客户提交咨询表单后，系统读取表单、判断客户类型、查询 CRM、生成跟进建议、分配销售、发送邮件、通知群聊、等待人工确认、写入数据库、生成日报并持续跟进。
- **Workspace Agent**：长期待在团队工作空间里的岗位助手，理解项目、文档、成员分工、客户历史、权限、流程和协作关系。
- **Workspace Agent 示例**：自动整理项目周报，结合任务系统、代码提交、会议纪要、文档更新、成员分工和上周周报，判断本周完成事项、延期任务、风险模块和下周推进重点。

## 值得记住的点 / 行动建议

### 1. 遇到 AI 新词，先问它解决了哪个具体问题

作者最后给出的判断方法非常实用：不要一看到新概念就焦虑，也不要急着背定义，而是问“它到底是在解决 AI 走向真实工作时的哪个问题”。比如 Prompt 解决的是任务说不清的问题，RAG 解决的是模型不知道资料的问题，Tool Calling 解决的是 AI 不能执行动作的问题，MCP 解决的是工具连接混乱的问题，Context Engineering 解决的是 AI 每次该看什么信息的问题。这样看，新词就不是孤立黑话，而是按问题自然生长出来的工具。普通人学习 AI 时，也应该沿着“问题—解决方案—适用场景”的路线学，而不是只背术语。

### 2. 写 Prompt 时，不要只提需求，要给角色、背景、格式和标准

视频中的“帮我写个方案”和“你是一名资深产品经理……”的对比说明，Prompt 的质量直接决定输出质量。一个好 Prompt 至少要包含：AI 扮演什么角色、要完成什么任务、背景信息是什么、输出结构是什么、哪些内容不要写、什么结果算好。比如你要 AI 写产品方案，就不要只说“帮我写方案”，而要明确目标用户、核心痛点、功能模块、商业模式、落地路径，并要求用表格输出。这样做的本质不是“调教 AI”，而是像给同事布置工作一样，把任务边界和交付标准讲清楚。越是复杂任务，越不能依赖一句模糊指令。

### 3. 需要准确资料时，不要让 AI 只凭记忆回答，要让它基于材料

视频反复提醒，模型不知道的东西就是不知道，强行回答就可能产生幻觉。凡是涉及公司制度、产品规则、项目代码、客户记录、课程资料、最新事件的问题，都不应该只让 AI “凭印象”回答，而应该把资料提供给它，或者使用 RAG / 知识库检索。比如问退款规则、请假制度、内部流程，最安全的方法是让 AI 先查产品手册或员工手册，再基于原文回答。普通人使用 AI 时，也可以用简化版 RAG 思路：先上传文件、粘贴资料、指定“只根据以下材料回答”，再让 AI 总结或分析。这样可以显著降低“看起来很合理但其实是编的”的风险。

### 4. 不要一股脑塞资料，关键是给 AI “刚好需要的信息”

Context Engineering 的核心提醒是：上下文不是越多越好，而是越合适越好。你让 AI 回复客户，它可能需要客户历史、购买记录、投诉记录、退款政策和当前问题，但不一定需要公司所有文档；你让 AI 写周报，它需要本周任务、项目进度、风险和下周计划，但不需要无关聊天记录。信息太少会导致回答不准，信息太多会干扰重点，信息过期会导致错误判断，敏感信息乱塞还会产生安全风险。因此，在实际使用中，要学会筛选、压缩和排序资料，把最关键、最新、最相关的信息放到前面。高质量上下文往往比超长上下文更重要。

### 5. 对重复任务，要把 Prompt 升级成 Skill 或固定流程

如果你发现自己每周、每天都在重复向 AI 解释同一类任务，就应该把这套要求沉淀下来。比如周报、日报、会议纪要、客户回复、代码审查、财务表格分析，都适合做成固定格式、固定步骤、固定语气的 Skill。你可以把常用要求整理成一份 SOP：输入需要哪些信息、AI 先做什么、再做什么、输出什么结构、哪些口吻不要用、最终如何检查。这样以后只需说“按我的周报格式”“按我们的客户回复规范”“按代码审查流程”，AI 就能复用之前的标准。对团队来说，这意味着可以把个人经验和组织流程沉淀为可复用的 AI 能力，而不是每个人各自摸索。

### 6. 用 Agent 做复杂任务时，必须有边界、验证和人工审批

Agent 的能力越强，风险也越大。它可以自己拆任务、查资料、改代码、跑测试，但也可能误删文件、乱改项目、生成不安全代码、跑偏、浪费大量 Token，甚至做出一个“看起来能跑但不敢上线”的东西。所以视频提出 Harness Engineering：要给 Agent 加权限控制、工具白名单、沙箱环境、日志追踪、输出验证、人工审批、回滚机制和评测系统。普通人使用 Agent 时，也应该采用类似原则：先让它在副本、分支、测试环境里操作，不要直接碰生产数据；重大操作前必须确认；执行后要检查结果。真正可用的 Agent 不是“越自由越好”，而是“越强越需要约束”。

### 7. 个人可以从单点工具开始，企业要关注 Workflow 和 Workspace Agent

视频后半段指出，真实业务不是一次聊天，也不是一个工具调用，而是一条持续运转的流程。比如客户提交咨询表单后，要判断客户类型、查 CRM、生成建议、分配销售、发邮件、通知群聊、等人工确认、写数据库、生成日报，这就需要 Workflow 工具把 AI、API、数据库、消息系统、人工审批和条件判断串起来。对个人来说，可以先从单点任务开始：写作、总结、代码辅助、资料问答、表格处理；对团队和企业来说，更重要的是把 AI 接进流程，让它成为业务链条的一部分。更进一步，Workspace Agent 会长期待在工作空间中，理解团队项目、权限、上下文和协作关系，像 AI 销售助理、AI 数据分析助理、AI 项目管理助理、AI 研发助理一样承担持续性工作。

## 我的点评

这期视频的优点在于没有把 AI 热词当成孤立概念讲，而是用“AI 如何进入真实工作”的主线把它们串起来，因此非常适合建立整体框架。作者对 Prompt、RAG、Tool Calling、MCP、Agent、Workflow 的解释都比较贴近日常使用场景，尤其是“资料室”“手”“USB-C”“长期 SOP”“安全带和刹车系统”等比喻，有助于普通人理解抽象概念。需要注意的是，视频为了讲清楚演进逻辑，把很多复杂技术做了简化，比如 MCP、Agentic RAG、Harness Engineering 在真实工程中还涉及更细的协议、评测、安全和组织治理问题，不能只凭概念理解就认为已经能落地。另一个值得保留的地方是，很多概念当前仍在快速演化，不同公司和社区对 Skill、Context Engine、Workspace Agent 的定义可能并不完全一致。普通人最实用的做法，是不要追着热词跑，而是把它们映射到自己的工作问题上：我现在的问题是任务说不清、资料找不到、工具不会调、流程没串起来，还是安全不可控？这样才能真正把 AI 用起来，而不是被新词带着焦虑。
