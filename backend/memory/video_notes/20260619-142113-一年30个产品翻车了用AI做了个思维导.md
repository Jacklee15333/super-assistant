## 🤖 AI 分析

## 一句话概括

这期视频借作者用 AI Coding 做“可播放思维导图 PPT”小工具的亲身经历，重新反思“一年做 30 个 AI 产品”的计划：AI Coding 最有价值的方向不是快速堆大众产品，而是围绕自己或团队的真实工作流，做高度个性化、锋利但不一定通用的小工具。

## 背景与主题

作者去年曾经设想：借助 AI Coding，一个人一年可以做 30 个产品，并且还做过相关系列视频，因此最近有不少观众追问“现在做到第几个了”“这个系列还做不做”。但过去半年高频使用 agent 之后，作者的想法发生了明显变化：AI Coding 的最佳用法，未必是给陌生用户做大众产品，而是先给自己做工具。视频中，作者用自己最近做的一个“MindMap PPT / 可播放思维导图 PPT”小工具作为案例，拆解 AI Coding 从自用工具到产品化之间的巨大差距。最后，作者借 Karpathy 等人的观点，强调未来软件会更个人化，代码会更便宜、更短命，但真正重要的是对自己工作流的理解。

## 核心观点

### 1. 作者从“一年 30 个产品”转向“先给自己做工具”，是因为 AI Coding 的真实价值发生了变化

作者开头说，去年他还觉得 AI Coding 能让自己“一年做 30 个产品”，并且为此做过一个系列的前几集；但过去半年他每周其实都在做，只是想法已经和去年完全不一样了。尤其是如果一个人高频使用 agent，就会感受到一个明显变化：现在最适合做的不是给别人做产品，而是先给自己做工具。作者还提到，像 Karpathy、“小龙虾的创始人 Peter”等人也在表达类似判断，即“80% 的软件都会消失”，因为我们正在进入一个“完全个性化工具的时代”。这背后的逻辑是：AI 让个人工作流的价值变高了，每个人真正卡住的地方都不一样，所以大众产品很难覆盖那些非常细碎、非常个性化的效率痛点。作者的转变不是否认 AI Coding，而是从“用 AI 快速造 APP”转向“用 AI 解决自己工作流里最卡的环节”。

### 2. 这次案例里的工具，是一个可以像 PPT 一样播放的思维导图演示工具

作者展示的小工具，是一个可以播放思维导图的“MindMap PPT”：演讲时可以随着讲解一个个展开节点，可以前进、后退，也有一些动画效果和参数调节按钮。它的用途非常个人化，主要服务于作者自己做讲解视频和线下讲座的场景。作者平时做视频或演讲时，需要根据文稿展示结构化内容，但传统思维导图软件更偏向静态总览，不适合按顺序演示。这个工具本身也是作者用 AI Coding 做出来的，它的核心功能不是“生成一张思维导图”，而是把本地文稿、本地素材、插图和演示流程整合起来，让它像 PPT 一样一步步播放。这个例子很好地说明了作者所谓“自用工具”的特点：它不一定大众、不一定好看、不一定标准化，但非常精准地卡住了作者自己的痛点。

### 3. XMind 这类成熟软件并不能满足作者的个性化工作流，因为它不是为 agent 和演示流程设计的

作者以前做思维导图主要用 XMind，这是一个成熟软件，也有 AI 功能，官网宣传可以“从一句话、一个文件、一个链接生成思维导图”。但作者说，他的刚需并不是“生成一张思维导图”，而是让 agent 读完本地文稿后，直接生成适合演示的结构，顺手做好插画，最后能像 PPT 一样一步步播放。XMind 的第一个问题是“agent 不够友好”：它有自己的 AI，但作者的工作流在另一个 agent 里，内容还要复制粘贴，存在人工成本。第二个问题是它不是完全按照作者的演示需求设计的，作者需要按顺序展开重点，而不是在一张大图上用鼠标拖来拖去、放大缩小、找位置。第三个问题是免费版有限制，比如 XMind 免费版的幻灯片只有 5 页，想无限播放就要买 Pro 或 Pro Plus，所以作者最终决定“干脆让 Codex 帮我写一个”。

### 4. AI Coding 的关键不是一句“帮我做个好看的思维导图”，而是把脑子里的流程拆成明确规则

作者强调，很多人被网上的说法误导，以为只要对 AI 说一句“帮我做一个好看的思维导图”就够了，但实际并不是这样。他最初的提示词虽然文档不复杂，但已经包含了非常明确的产品规则：输入格式用 Markdown，因为 Markdown 对智能体友好；无序列表里的短横线代表节点；缩进代表父节点和子节点的关系；可以通过 `@image` 插入图片；节点选中的顺序按照树的前序遍历展开。翻译成人话，就是像 PPT 一样，先根节点，再左子树，再右子树，一步一步讲解。作者认为，AI Coding 的关键是你要把自己的理解拆出来，告诉 AI 输入是什么、输出是什么、如何播放、哪些节点展示、哪些节点隐藏、切换时怎么布局。你理解得越清楚，AI 写出来的东西才越接近你真正想要的东西。

### 5. 自用工具的第一版可以很快做出来，但从“我能用”到“别人也能用”会多出大量产品化成本

作者说，这个工具的第一版大概花了两三个小时就能用：能读取 `src.js` 里的 Markdown，能画节点和连接线，能用键盘上下切换，还能用滑动条调节节点。后来又加了两行大标题、节点插图、缩放功能等；他上一期讲“怎么选 AI Coding 套餐”的视频，就是用这个工具做的演示。但这期为了把它整理成别人也能用的 skill，他又额外花了 7 到 8 个小时，这让他明显感受到自用工具和对外工具之间的差距。给自己用时，只要核心链路跑通就可以，因为文件在哪里、可能有哪些 bug、哪里不能点、出错后怎么绕开，这些上下文都在作者脑子里。给别人用时，别人没有这些上下文，不知道图片放哪里，不知道文件能不能改，也不知道 PPT 跑不起来是自己用错了还是工具 bug，所以产品化的过程，本质上就是把开发者脑子里的上下文一点点塞进工具和文档里。

### 6. 产品化的大量工作并不在“核心功能”，而在文档、边缘体验、环境兼容和用户理解成本

作者翻了自己的 git 记录后发现，后面大量时间根本不是在做核心功能，而是在写 README、中文说明、skill 文档，以及规定 agent 应该怎么读材料、怎么保留事实、怎么选插图、怎么校验结果。比如为了让大家能用，就要处理不同电脑环境的问题：最开始用 Python 开静态服务，后来改成项目自带的 server，因为不能假设每个人电脑上都有同样的 Python 环境。还要完善各种边缘体验，比如滚轮切换、移动端触屏滑动、全屏看图、调整窗口大小时会不会出 bug。对作者自己来说，这些都不是刚需，因为有 bug 他不按那个按钮就行，严重 bug 后期剪视频时剪掉也可以。但对一个要给别人用的工具来说，这些就是基本体验，说明 AI Coding 省掉了写第一版的成本，却没有自动消灭产品化、说明书、兼容性和用户支持的成本。

### 7. 作者把 AI Coding 产物分成三层：自用工具、团队内部工具、大众产品

作者提出了一个很清晰的三层分类：第一层是给自己用的小工具，第二层是给团队内部用的工作流工具，第三层是给陌生人用的大众普世产品。他认为，AI Coding 对第一层提升最大，因为自用工具只需要解决自己的问题，不需要照顾所有用户；对第二层也很有价值，因为团队内部有共享背景和使用习惯；但到了第三层，代码只是很小一部分，更大的部分是产品、运营、信任、部署、服务、隐私、登录、成本承担等。作者的 MindMap PPT 就属于第一层产品，因为它对普通人来说很奇怪：要把 Markdown 放进 `src.js`，图片还要本地 `@` 引用，再用静态网页播放。但它又正好卡在作者的视频工作流痛点上，所以“不通用但很锋利”，这正是自用工具最重要的价值。

### 8. 团队内部工具同样适合 AI Coding，因为标准不是“陌生人零学习成本”，而是“每天能不能省时间”

作者又举了第二层工具的例子：他和合伙人平时刷 AI 新闻特别多，于是几个月前自己做了一个刷 Twitter / X 的 agent。这个 agent 会读取他们平时看的 AI 研究员、AI 公司账号的推文，翻译成中文，补充背景和上下文，按重要性评分、打标签，最后生成日报。背后流程包括：先抓 X list 里的推文，再拉详情，再过滤掉一些“很水”的帖子，再用 Claude agent 做分析，最后做标签聚合和日报。作者说，如果你在他的粉丝群里收到 AI 日报，背后其实就是这套他自己写的东西。这个网站可能有很多 bug，但仅仅作为两个人日常使用完全没问题，因为内部工具的标准不是让陌生人零学习成本上手，而是能不能每天帮团队省时间。

### 9. 一旦工具要推向公众，问题就从“写代码”变成一整套产品系统工程

作者对比内部工具和大众产品时，列出了一串推向公众后必须面对的问题：用户要不要登录、怎么登录、数据库怎么部署、更快和更省时间怎么平衡、抓 Twitter 的账号权限怎么处理、用户是否需要和 agent 交互、API 成本由谁承担、新手引导界面怎么做、数据隐私怎么保证等。这些问题都不是一句提示词能简单解决的，也不是 AI Coding 自动生成一版代码就能处理好的。作者的感受是，AI Coding 确实让第一版工具的成本大大降低了，但要做一个别人都能用起来的产品，省下来的成本和精力并没有想象中那么多。尤其是大众产品要面对陌生用户，陌生用户没有开发者的上下文，也不会容忍各种奇怪流程和隐藏 bug。于是“能跑的代码”和“能被陌生人稳定使用并愿意信任的产品”之间，隔着很长的产品化距离。

### 10. “30 个产品计划”停下来的原因，是入口风险、模型内化和作者对产品价值的重新理解

作者最后解释，去年说“一年做 30 个 AI 产品”，最后其实做了 4 个就停了。一个现实原因是，当时微信机器人跑了一个多月就被腾讯全部封了；作者原本以为微信是 AI 产品很好的载体，可以围绕微信生态做很多产品，但入口被封后，原来的计划被直接打乱。更重要的原因是，他意识到 AI 产品正在变得越来越个人化，AI 让个人工作流的价值变高了，而每个人真正浪费时间的卡点都不同。作者还引用 Karpathy 的例子：Karpathy 曾用 AI Coding 写过一个识别餐厅菜单并给每道菜生成图片的小 APP，后来发现有人把菜单照片直接丢给 Gemini，Gemini 就能在原图上叠加菜品图，于是他说那个 APP 根本不应该存在。这个故事让作者意识到，今天写的 APP 明天可能被更强模型“内化掉”，所以他不再想做那种模型能力升级后就会消失的产品，而是更愿意做紧贴自己工作流、封装自己理解的小工具。

## 值得记住的点 / 行动建议

### 1. 做 AI Coding 项目时，先从自己的真实痛点下手，不要一开始就做大众产品

作者最核心的建议是：不要急着用 AI Coding 去“造大的东西”，而是盯着自己工作流或团队工作流里最卡、最影响效率的环节，做一个小工具把它解决掉。比如作者不是泛泛地做“思维导图软件”，而是解决自己做视频和线下讲座时，文稿需要被转成可演示结构、节点需要逐步展开、插图需要自动生成的问题。这个需求非常窄，但非常真实，所以工具哪怕长得奇怪、依赖本地文件、需要命令行，也能立刻给作者带来价值。普通人也可以照这个思路找场景：每天重复复制粘贴的流程、每周都要整理的资料、每次都要手工格式化的文档、团队内部反复做的日报，都比“做一个面向所有人的 AI 产品”更适合作为起点。AI Coding 的红利首先不在于创业，而在于让个人和小团队把低效环节变成自动化工具。

### 2. 写提示词之前，先把输入、输出、流程和规则想清楚

作者用 MindMap PPT 的例子说明，AI Coding 并不是一句“帮我做个好看的工具”就能得到好结果。你需要明确告诉 AI：输入是什么格式，输出是什么形态，中间怎么转换，用户怎么操作，播放顺序是什么，哪些节点出现，哪些节点隐藏，插图如何引用，布局如何变化。作者选择 Markdown 无序列表作为输入，是因为它对 agent 友好；短横线代表节点，缩进代表父子关系，`@image` 代表插图，前序遍历代表播放顺序，这些规则让 AI 有明确可执行的结构。普通人做 AI Coding 时，也应该先写一份简短但清楚的规则文档，而不是直接让 AI 自由发挥。你对流程理解越深，AI 写出来的东西越像你脑子里的产品；你越模糊，AI 就越容易写出一个“看起来有点像、但完全不贴合实际工作流”的东西。

### 3. 接受“自用工具可以不完美”，不要把第一版标准定得太高

作者强调，给自己用的工具只要核心链路跑通就行，不需要一开始就做成完美产品。比如 MindMap PPT 第一版只要能读取 `src.js`、画出节点和连接线、用键盘切换、能播放，就已经能进入作者的视频制作流程了。即使有某个按钮有 bug，作者可以不点；如果录制时出现严重问题，后期剪掉也可以。自用工具的心态更像玩 Minecraft：脑子里有个雏形，就动手搭建，边用边改，过程是放松的。对普通人来说，这意味着做内部工具时不要被“产品完整度”吓住，先让它在一个真实任务里跑起来，再根据实际使用逐步补功能。

### 4. 认清“能用”和“能给别人用”之间的巨大差距

视频里最值得警惕的一点，是作者两三个小时做出自用版本，却又花了 7 到 8 个小时才把它推进到“懂 agent、懂命令行的人也许能用”。这说明产品化不是简单地把代码发出去，而是要补齐用户缺失的上下文。别人不知道文件在哪，不知道图片怎么放，不知道报错是什么意思，不知道是自己操作错还是工具 bug，所以你必须写 README、中文文档、skill 说明、安装流程、使用示例和校验规则。还要考虑不同电脑环境，比如别人有没有 Python、server 怎么跑、移动端能不能滑动、窗口大小变化会不会崩。普通人如果想把 AI Coding 项目分享给他人，必须预留足够的文档、测试、兼容和解释成本，不要以为第一版跑通就等于产品完成。

### 5. 把 AI Coding 产物分层管理，不同层级用不同标准评价

作者提出的三层模型非常实用：第一层自用工具，第二层团队内部工作流工具，第三层大众产品。自用工具的标准是“能不能解决我的痛点”；团队工具的标准是“能不能让我们每天省时间”；大众产品的标准则复杂得多，要考虑登录、部署、权限、隐私、成本、稳定性、新手引导和用户信任。很多 AI Coding 项目失败，是因为明明只是第一层工具，却一开始按第三层产品的标准设计，导致开发者过早陷入大量产品化细节。反过来，也有人误以为第一层工具能跑，就可以直接卖给陌生用户，结果被兼容性、说明成本和用户支持拖垮。正确做法是先判断项目属于哪一层，再决定投入多少产品化成本。

### 6. 团队内部工具很值得做，因为它不需要满足所有人，只需要节省团队时间

作者做的 AI 新闻日报 agent 就是典型团队内部工具：它不一定稳定、不一定漂亮、不一定适合所有用户，但能帮作者和合伙人节省大量刷 AI 新闻、翻译、筛选、打标签、生成日报的时间。这个工具背后流程很完整：抓 X list 推文、拉详情、过滤水帖、用 Claude agent 分析、打标签、聚合成日报。对于两个人的小团队来说，只要每天能少花时间、少重复劳动，就已经足够有价值。普通团队也可以从类似场景入手，比如销售线索整理、竞品监控、客户反馈分类、会议纪要归档、日报周报生成。内部工具最大的优势是用户少、上下文共享、容错率高，因此非常适合用 AI Coding 快速搭建。

### 7. 谨慎做“模型一升级就会消失”的产品

作者引用 Karpathy 的菜单 APP 故事，是为了说明很多看似有产品价值的 AI 应用，可能很快被基础模型直接内化。Karpathy 曾经用 AI Coding 写了一个识别餐厅菜单、给每道菜生成图片的小 APP，但后来有人直接把菜单拍照丢给 Gemini，让 Gemini 在原图上叠加菜品图，于是这个 APP 的独立存在价值就被削弱了。作者因此反思，去年想一年做 30 个产品，本质上是在赌“我能多快用 AI 造 APP 并试错”；但如果模型本身进化很快，今天造的 APP 明天就可能被更强模型直接替代。普通开发者在选题时，要避免只是在模型能力外面套一层薄壳，尤其是那些没有工作流深度、没有数据积累、没有分发渠道、没有用户信任的薄应用。更稳妥的方向，是做深度嵌入自己流程或团队流程的工具，因为它封装的是理解，而不是单纯调用模型能力。

### 8. 真正重要的不是代码，而是你对工作流的理解

作者最后把视频的核心落在一句话上：“便宜的是代码，重要的是理解。”AI 让代码变得越来越便宜、短命、可塑，甚至可以为了找一个 bug 临时写一个完整 APP，用完就丢。但 AI 不能替你理解你的工作流：哪一步最浪费时间，哪一步最容易出错，哪一步值得自动化，哪些信息必须保留，哪些结果需要人工校验，这些都来自你对自己工作的长期观察。作者引用 Karpathy 的意思说，“你可以把思考外包出去，但你没有办法把理解外包出去”。所以对普通人来说，提升 AI Coding 能力的关键不是只学某个工具，而是更准确地描述自己的需求、拆解自己的流程、识别真正的卡点，并把这些理解转化成规则和工具。

## 我的点评

这期视频的价值在于，它没有继续讲“AI Coding 多神奇”，而是非常具体地拆开了自用工具、内部工具和大众产品之间的差别，这比单纯展示“几分钟做一个 APP”更接近真实世界。作者用 MindMap PPT 的开发经历说明了一个重要事实：AI 确实能大幅降低第一版代码成本，但文档、部署、兼容、用户教育、信任和运营并不会自动消失。视频对“个人化工具时代”的判断也很有启发，尤其适合内容创作者、独立开发者、小团队和知识工作者，把 AI Coding 用在自己的工作流改造上。需要保留的一点是，作者对“80% 软件会消失”的说法偏趋势判断，未必适用于所有软件形态，企业级系统、强合规行业、深数据壁垒产品仍然有长期价值。普通人最该吸收的不是“别做产品”，而是先从自己的真实流程里找到高频痛点，做小、做尖、做能立刻省时间的工具，再判断它有没有必要继续产品化。
