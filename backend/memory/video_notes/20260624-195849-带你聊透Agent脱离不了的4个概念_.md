## 🤖 AI 分析

## 一句话概括

视频从软件工程视角拆解了 Agent 体系中的 **Function Calling、Tool、MCP、Skill** 四个概念，说明它们分别负责“表达调用意图、执行具体操作、标准化接入外部能力、按需加载与分发工作流”，彼此分层协作而非相互替代。

## 背景与主题

随着 AI Agent 快速发展，Function Calling、Tool、MCP、Skill 等术语被频繁使用，尤其是 Skill，似乎出现了“万物皆可 Skill 化”的趋势，但很多人并不能清楚解释它们之间的区别。视频作者“不鲁”认为，这些概念并非凭空出现的新技术，本质上都能在传统软件工程中找到对应物，只是被重新包装并适配到了 AI 场景中。作者并不是要否定这些概念，而是希望帮助观众认清每个概念所处的技术层级、解决的问题及相互关系。其核心立场是：**旧技术“装新酒”并不是坏事，真正重要的是理解瓶子的形状，避免在系统出问题时连故障属于哪一层都判断不出来。**

## 核心观点

### 1. 四个概念并非同一个东西，而是分别处在 Agent 系统的不同层级

Function Calling、Tool、MCP、Skill 经常被混在一起讨论，但它们并不是四种相互竞争的方案，而是分别解决不同层面的问题。Function Calling负责让模型表达“我要调用什么”；Tool负责真正执行操作；MCP负责用统一协议接入外部工具；Skill则负责把一套知识、提示词或工作流按需加载进上下文。作者将它们概括为“各守一层”，因此不能简单地问哪一个更高级，或者哪一个可以取代另一个。只有先明确问题属于模型决策、工具执行、外部接入还是上下文组织，才能找到正确的解决办法。

### 2. Function Calling本质上是模型输出结构化调用意图的能力

大模型本质上只能生成内容，不能仅凭一段文字直接查询新闻、操作文件或访问第三方服务。例如，用户要求查询当天最新的国际新闻时，模型本身不能自行发送网络请求，而是输出类似“调用 `getNews` 工具，并传入相应参数”的结构化指令。外部程序解析这段指令，执行真实请求，再把新闻结果返回给模型，由模型组织成最终回答。因此，Function Calling并不是模型亲自执行函数，而是模型根据工具清单和用户需求，识别应该调用哪个工具，并生成规范的调用意图。

### 3. 完整的工具调用是一个可能反复运行多轮的执行循环

一次 Agent 任务通常不是“模型调用一次工具就结束”，而是一个持续循环：用户发送消息，模型输出调用意图，应用程序执行工具，把结果返回给模型，模型继续推理，再决定是否调用下一个工具。复杂任务中连续调用五六个工具十分正常，例如先搜索资料，再读取网页，再计算数据，最后生成总结。这个循环什么时候继续、什么时候结束，取决于模型是否认为信息已经足够，但真正负责维护消息、执行调用和回传结果的是应用层。换句话说，模型负责决策，应用程序负责调度与执行，两者不能混为一谈。

### 4. LangChain、Spring AI等框架主要负责管理执行循环和兼容性

视频提到，LangChain、Spring AI等开发框架的重要作用，是帮助工程师管理Function Calling所需的外围流程。它们可以把代码中的函数转换成模型可理解的JSON Schema，执行模型提出的调用请求，并把结果重新放回上下文中。同时，这些框架还会屏蔽不同模型厂商之间的API格式差异，例如OpenAI常使用“tools/tool calling”相关表述，而Anthropic常称为“tool use”。不过，框架并没有取代模型的决策职责：调用哪个工具、何时调用以及传入什么参数，核心判断仍然由大模型完成。

### 5. Tool才是真正执行动作的代码单元，可分为内部工具和外部工具

如果把大模型比作“只动嘴、不动手”的决策者，那么Tool就是它能够支配的手脚。工具本质上通常是一个函数、方法、脚本或服务接口，可以读取文件、写入文件、执行终端命令，也可以查询新闻、访问数据库或调用第三方平台。视频将其分为两类：第一类是内部工具，如读写本地文件、执行命令，Claude Code等编程Agent会大量使用这类能力；第二类是外部工具，即Agent自身不直接具备、需要通过外部服务接入的能力。Tool强调的是“执行什么”，至于工具通过何种协议接入，则是另一个层面的问题。

### 6. MCP是外部工具的标准化接入方式，与Tool属于平级关系

作者特别强调：“MCP和Tool是平级的关系，MCP是外部工具的一种接入方式，不是比Tool更高一层的东西。”从传统软件工程角度看，MCP依然可以理解为客户端与服务端架构：MCP Client是客户端，MCP Server是服务端，MCP协议定义双方如何握手、传输数据以及采用什么格式。它与REST API、RPC等机制在思想上有明显相似之处，并不是完全脱离既有工程体系的技术革命。MCP真正有价值的地方，是为AI应用连接外部能力建立了一套统一规范，从而减少每个客户端重复适配同一服务的成本。

### 7. MCP的核心价值是标准化复用和运行时能力发现

视频举例说，假设存在Claude Code、Codex、Cursor三个AI客户端，它们都要接入新闻查询服务，如果没有统一标准，三个团队可能需要分别完成一次新闻接口集成。采用MCP后，新闻服务只需按照规范实现一个MCP Server，所有兼容MCP的客户端理论上都可以连接并使用它。更关键的是，MCP Server具有“能力自描述”特征：启动后可以向客户端列出自己提供的工具、资源及相关参数，客户端能够在运行时动态发现这些能力。传统REST API通常要求开发者提前阅读文档并完成编码，而MCP的动态发现更适合需要临时了解“当前有哪些武器可用”的大模型。

### 8. Skill本质上是按需加载的能力包，重点在上下文管理与复用分发

当Agent拥有越来越多能力时，如果把几十套工作流、完整提示词和操作规范一次性塞入上下文，不仅Token成本会迅速上升，模型还可能因为信息过多而选错流程，甚至超过上下文窗口限制。Skill采用的核心思路，是先只向模型提供一份能力目录，每项能力只包含名称和简短说明；模型选中某项能力后，再加载该Skill的完整内容，使用结束后释放。这种按需加载并非Anthropic从零发明，许多成熟Agent系统过去已经采用类似机制，但Skill将其规范化并形成可分发格式。规范化之后，个人制作的优质工作流可以被打包、安装和复用，从“只在自己电脑上运行的散装提示词”变成能进入成千上万用户工具中的标准能力包。

## 关键事实与数据

- 视频讨论的四个核心概念是：**Function Calling、Tool、MCP、Skill**。
- 作者认为它们在传统软件工程中的对应关系大致为：

- Function Calling：函数调用或结构化调用意图。
- Tool：执行具体操作的函数、方法或服务。
- MCP：客户端、服务端及通信协议机制。
- Skill：按需加载和能力打包。
- 大模型的根本限制之一是：**模型本身输出内容或结构化指令，但实际操作需要外部程序执行。**
- Function Calling的典型流程是：用户请求→模型生成调用意图→程序执行工具→结果返回模型→模型继续推理或给出答案。
- 复杂任务中，Agent连续调用**五六个工具**属于正常情况。
- 视频提到的Agent开发框架包括：**LangChain、Spring AI**。
- 不同厂商可能采用不同术语：OpenAI体系常见“tools/tool calling”，Anthropic体系常见“tool use”。
- 内部工具的例子包括：**读取文件、写入文件、执行终端命令**。
- 视频提到的编程Agent或AI客户端包括：**Claude Code、Codex、Cursor**。
- 外部工具可以通过MCP这种标准化方式接入Agent。
- MCP架构包含：**MCP Client、MCP Server以及定义通信方式的MCP协议**。
- 作者将MCP与传统软件工程中的**REST API、RPC、客户端—服务端架构**进行类比。
- 新闻服务案例中，如果三个AI客户端分别独立适配接口，同一套集成工作可能需要重复三次；使用MCP后，服务方实现一个标准Server即可供多个兼容客户端使用。
- MCP相较于普通API调用的重要特点是：**能力自描述与运行时动态发现**。
- 普通API通常需要提前阅读文档或硬编码接口信息；MCP Server可以标准化列出工具、资源、参数和能力。
- Skill主要解决两类问题：**上下文容量有限**以及**标准工作流的打包、分发和复用**。
- Skill通常只在初始上下文中暴露名称和简短说明，被选中后才加载完整内容。

## 值得记住的点 / 行动建议

### 9. 先判断问题属于哪一层，再选择解决方案

开发Agent时，不要看到问题就笼统归因于“模型不够聪明”或“需要增加一个Skill”。如果模型没有正确选择工具，应检查工具名称、描述、参数Schema和提示词是否清晰；如果模型已经正确生成调用意图，但任务没有执行，则应检查Tool实现和应用层执行循环。如果外部服务难以在多个客户端之间复用，应考虑MCP；如果能力太多导致上下文膨胀或流程选择混乱，才更适合使用Skill。按照层级定位故障，可以显著减少盲目修改提示词和反复返工。

### 10. 不要把Function Calling误解为模型亲自执行代码

在系统设计和安全控制中，必须明确模型只是在“提出调用建议”，真正执行操作的是外围程序。应用层应对工具参数进行校验，并设置文件权限、网络权限、超时、重试、错误处理和高风险操作确认。尤其是删除文件、执行终端命令、操作数据库或调用付费服务时，不能因为请求来自模型就默认可信。模型决策与工具执行之间必须保留明确的验证边界。

### 11. 根据复用范围决定使用内部Tool还是MCP

如果某项能力只服务于单个项目、逻辑简单且不需要跨客户端共享，可以直接包装成内部Tool，减少部署和通信复杂度。例如，一个本地代码Agent读取项目配置文件，通常没有必要专门部署MCP Server。若同一能力需要同时服务Claude Code、Codex、Cursor或其他兼容客户端，或者需要由独立团队长期维护，则更适合使用MCP。选择标准不应是“MCP听起来更新”，而应是外部化、复用性、维护边界和动态发现是否真正有价值。

### 12. Skill应保留完整工作流，而不仅是换名字的短提示词

一个真正有用的Skill，应该包含清楚的适用场景、触发条件、输入输出、操作步骤、质量标准、错误处理和必要资源，而不只是把几句话放进文件后重新命名。Skill的目录描述必须简洁、准确、彼此容易区分，否则模型可能在选择阶段就调用错误。完整内容则应在被选中后按需加载，以控制Token成本并减少无关信息干扰。设计Skill时，应同时考虑“模型能否正确发现它”和“加载之后能否稳定执行”。

### 13. 把标准化看作生态价值，而不是算法创新

MCP和Skill的价值未必来自全新的底层算法，而可能来自统一格式后形成的复用网络。REST API本身并不神秘，但统一接口可以连接庞大的软件生态；同理，MCP让服务能力更容易被多个AI客户端发现和使用，Skill让个人工作流更容易安装和传播。判断一项AI技术时，不应只问它是否“以前就有”，还应考察规范化后是否降低了集成、维护和分发成本。旧思想经过标准化和场景适配后，依然可能产生显著的工程价值。

## 我的点评

视频的分层思路很有价值，尤其是把“模型决策”“工具执行”“外部接入”和“上下文组织”区分开，能够帮助初学者建立较清楚的Agent架构认知。作者强调MCP的价值主要来自标准化、复用和能力发现，而非彻底的技术革命，这种判断总体务实。不过，将MCP简单等同于REST API或RPC略有简化，因为MCP还涉及统一的工具、资源、提示等能力模型，以及面向AI客户端的交互约定。视频中“Tool与MCP平级”的说法适合作为入门理解，但更严谨地说，Tool是一种可调用能力，而MCP是暴露、发现和调用这类能力的协议，两者并不完全属于同一种概念类型。普通人在实际使用中最应掌握的不是名词热度，而是明确每一层负责什么、风险在哪里，以及当前问题究竟需要增加工具、改进工具描述、接入MCP，还是整理成可按需加载的Skill。
