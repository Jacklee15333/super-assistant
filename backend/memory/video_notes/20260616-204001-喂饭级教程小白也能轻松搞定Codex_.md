## 背景与主题
Codex 是 OpenAI 推出的 AI 编程工具，能够帮助用户理解代码、修改项目和执行编程任务，但国内部分用户在下载安装、账号登录以及模型访问方面会遇到障碍。视频作者“雷哥”针对这些问题，提出一套利用离线安装包、CC Switch 和国产大模型 API 的替代方案，声称可以绕过常见的下载及网络障碍，让普通用户也能使用 Codex。
视频以 DeepSeek 为主要演示对象，涉及 Microsoft Store（微软应用商店）、GitHub、CC Switch、API Key（API 密钥）、本地路由等工具及技术概念，并提到智谱、MiniMax、小米等其他国产模型提供方。
作者的讲解重点不是 Codex 的编程能力，而是如何完成从软件下载、模型接入、请求转发到首次对话的整个配置过程，同时强调两层路由开关、API Key 配置和重启应用的重要性。

## 核心观点

### 1. Codex 可以尝试通过第三方路由工具接入国产大模型，从而降低使用门槛
视频最核心的观点是：用户不一定必须使用 OpenAI 官方模型，借助第三方工具，可以让 Codex 的请求转发至国产大模型服务。作者开场便提出“Codex 已经支持国内所有的大模型”，并声称用户不再需要担心海外网络或账号问题。其演示方案并不是直接修改 Codex 的模型能力，而是利用 CC Switch 建立兼容接口或本地代理，让 Codex 的请求交由国内模型处理。这样，用户在 Codex 界面输入指令，后端实际响应的可能是 DeepSeek 等模型，从而将 Codex 的操作界面与具体模型服务提供方分离。需要注意的是，“支持所有国产模型”属于作者的概括性表述，实际能否使用还取决于模型接口兼容性、CC Switch 的支持情况、Codex 版本和具体功能要求，不能理解为官方已经原生支持所有模型。

### 2. 下载和安装是新手遇到的第一道障碍，离线安装包可以作为替代方案
作者指出，不少用户在安装 Codex 的第一步便会遇到下载失败、页面打不开或者无法获取安装程序等问题。视频介绍的第一种途径是通过微软官方页面访问软件下载地址，并尝试正常下载安装，但作者估计只有约 10% 的用户能够直接成功，其余用户可能需要采取其他方式。针对 Windows 用户，他演示通过第三方网页，将微软应用商店的软件下载链接转换为可下载的 MSIX 安装包，再在本地安装。针对无法访问微软页面或者使用 macOS 的用户，作者提供了自己准备好的对应系统离线安装包。其思路是把“在线商店获取安装程序”转换为“提前下载完整安装文件”，但离线包的来源、真实性、数字签名及安全性仍需单独核实，不能仅因能够安装就认为没有风险。

### 3. CC Switch 是整个方案的关键桥梁，承担模型配置和请求转发的作用
视频中最重要的辅助工具是 CC Switch，作者介绍它既可以服务于 Claude Code，也能用于 Codex 的第三方模型接入。CC Switch 在本方案中的作用，是帮助用户管理模型服务商配置、API Key，以及与 Codex 之间的本地路由关系。作者先通过 GitHub 或预先准备的离线包安装 CC Switch，再进入工具中的 OpenAI 配置区域添加新的服务商。随后选择 DeepSeek 模板，填写相应密钥并启用路由，使 Codex 能够间接调用指定的模型接口。从技术逻辑来看，这种方式利用的是客户端与后端模型服务之间的接口适配机制，CC Switch 本身不是大模型，也不是提供模型推理能力的服务器，其核心价值在于配置、管理和转发请求。

### 4. 国产模型 API Key 是替代官方登录路径的重要凭据
作者强调，如果用户无法完成 OpenAI 官方账号登录，可以尝试使用其他登录或 API Key 入口，并借助国内大模型平台提供的密钥完成模型调用配置。视频以 DeepSeek 开放平台为例，进入 API Key 管理页面，新建一个密钥，并将其命名为“Codex”。创建后复制密钥，分别填入 CC Switch 的服务商配置以及 Codex 的 API Key 输入位置，这两个位置在作者的具体方案里都需要配置。API Key 的作用相当于访问模型服务的身份凭据，模型平台会利用它验证请求并关联账户用量与费用。值得区分的是，获得 DeepSeek API Key 并不等于获得 OpenAI 账号或官方服务权限，该密钥能否通过 Codex 的特定认证流程，还取决于本地路由是否成功接管相关请求。

### 5. 配置服务商时，既要选择正确模型，也要检查接口及高级选项
CC Switch 提供多个模型服务商配置模板，作者演示进入 OpenAI 区域，点击加号创建新配置，再从列表中选择 DeepSeek。若系统没有提供目标服务商的预设模板，则可以使用自定义方式，填写 API Key、Model Name（模型名称）以及相应接口信息。选择 DeepSeek 后，软件提示当前使用的是非官方 API，作者继续选择保存，再进入编辑页面粘贴刚刚创建的 API Key。他特别强调，应检查高级选项中的本地路由配置是否开启，并利用“获取模型”功能检验当前 API 配置是否能够访问服务商。这里需要注意，成功获取模型列表只能说明至少部分接口通信正常，并不能完全证明后续 Codex 的对话、工具调用或代码修改功能一定兼容。

### 6. 本地路由需要在多个配置层面启用，漏掉总开关可能导致接入失败
视频中最容易被忽视的技术细节，是 CC Switch 的路由配置并非只有一个开关。作者在选择 DeepSeek 服务商、填写 API Key 后，要求先确认服务商配置中高级选项的本地路由已经启用，再保存配置并启动相关服务。之后还需要进入 CC Switch 的设置页面，找到“路由”或“本地路由”选项，将本地路由的总开关打开。也就是说，完成模型配置、启动代理服务和开启全局路由，是多个相互关联但不完全等价的操作，缺少其中一个步骤都可能导致 Codex 无法正确连接到模型。作者花了较大篇幅反复演示这两个层级的路由设置，说明它们是整个教程中实际操作价值最高、也最容易出错的地方之一。

### 7. 配置完成后需要保留 CC Switch 运行，并重新打开 Codex
作者在完成 CC Switch 的 API 配置和路由设置后，没有立即关闭软件，而是明确要求用户将其最小化并保留运行。如果 CC Switch 正在承担本地代理服务，直接退出程序可能导致本地监听服务停止，Codex 的后续模型请求也可能无法正常转发。随后重新打开 Codex，作者演示看到客户端进入 API Key 登录路径；如果没有自动进入相应状态，则手动选择其他登录方式并粘贴之前创建的 DeepSeek API Key。进入 Codex 主界面后，可以新建对话来验证模型是否能够回复。整个流程体现了一个重要的排障原则：修改模型代理或路由配置之后，需要确认代理正在运行，并让客户端重新加载相关配置。

### 8. Codex 返回的模型身份信息可能与真正调用的模型不一致
作者在测试 Codex 时，输入了“在吗？您使用的是什么模型？”，模型随后回复称自己是 Codex 模型，具体模型为 GPT-5（文字稿识别为“GVT5”）。作者指出，这个回答不代表实际模型身份，因为他在 CC Switch 中配置的服务商是 DeepSeek，因此认为当前真正处理请求的是 DeepSeek。这个现象说明，大模型在对话中自称的身份信息并不能作为验证真实调用链路的可靠证据，它可能受到系统提示词、接口返回方式或模型自身生成行为的影响。要判断真实使用的模型，应该检查 CC Switch 请求日志、实际目标接口、模型平台调用记录及 API 消耗，而不是只根据模型的自述做判断。视频演示了可以正常收到回复，但没有提供独立的请求日志或后台账单证据，因此只能将模型身份判断视为作者依据其路由配置作出的说明。

### 9. 这套方法的价值在于工具与模型解耦，但不意味着所有功能都可以无差别替换
作者在演示完成后表示，除 DeepSeek 外，智谱、MiniMax、小米等能够提供 API Key 的模型服务也可以尝试接入 Codex，并鼓励用户探索更多使用场景。其背后的通用思路是将 AI 编程工具的操作界面、任务组织能力，与具体提供推理服务的大模型相分离，让用户按照成本、可访问性或模型特点选择后端。对希望使用国内模型的开发者来说，这种模式有机会减少账号和网络限制，也方便在多个模型提供商之间进行切换。不过，拥有 API Key 只是接入的必要条件之一，并不是充分条件，不同模型在工具调用、上下文长度、流式输出、代码编辑及协议支持上可能存在差异。因而，这套方法更适合作为第三方兼容接入思路，而不是官方保证的通用替换方案。
