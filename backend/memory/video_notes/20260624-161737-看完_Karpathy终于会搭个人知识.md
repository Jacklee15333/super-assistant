## 一句话概括

视频系统讲解了 Karpathy 提出的 **LLM Wiki（由大模型持续编译、维护的 Markdown 知识库）**：它不再依赖传统RAG每次临时检索零散片段，而是让Agent预先把原始资料整理成可读、可修改、可链接、可持续进化的“个人维基百科”。

## 背景与主题

2026年4月，OpenAI早期团队成员、特斯拉前AI总监 Andrej Karpathy 在X平台公开了自己搭建个人知识库的方法，引发广泛讨论。与需要向量数据库、切片、Embedding和检索链路的传统RAG知识库相比，Karpathy的方法主要由文件夹、Markdown文档、索引和双向链接组成，技术结构明显更简单。

视频作者此前搭建过多个RAG知识库，却长期受困于检索不准、答案不稳定、无法持续维护等问题，因此对LLM Wiki产生了强烈兴趣。视频不仅比较了RAG、知识图谱、GraphRAG和LLM Wiki之间的差异，还使用Obsidian、Claude Code、Web Clipper和Git等工具，演示了一个普通人也能完成的本地知识库流程。作者最终强调，真正有价值的知识库不是“把几百份PDF堆进去”，而是围绕具体任务和决策场景，持续把数据整理成可复用的知识体系。

## 核心观点

### 1. 传统RAG最大的缺陷，是“检索到相似内容”不等于“找到解决问题所需的知识”

作者此前曾把几百份PDF一次性灌入RAG知识库，希望大模型能够基于全部材料进行分析。但当他询问“这个项目的核心风险是什么”时，系统往往只检索出包含“风险”一词或语义相近的段落，而这些段落可能只是顺带提到风险，并没有真正分析项目的核心问题。大模型随后会把这些并不完整、甚至不相关的片段拼接成一个表面通顺的答案，使人误以为系统完成了深入分析。

其根本原因在于，传统RAG通常依赖向量相似度召回材料，而向量模型判断的是语言层面的“像不像”，不一定能够判断某段材料在当前任务中的逻辑价值。用户问的是“最关键的风险及其影响”，检索器却可能只理解成“帮我找一些写着风险的段落”。因此，RAG虽然能够降低大模型完全脱离资料胡编的概率，却无法保证召回内容真正覆盖问题的核心。

### 2. RAG的答案容易波动，因为它每次都在重新抽取一组临时上下文

作者遇到的第二个问题是：同一个问题，只要稍微调整一下措辞，回答就可能从正确变成错误。原因是RAG每次提问时都会重新检索，问题表达发生变化，向量相似度排序也会变化，最终送入大模型的知识片段就不再相同。

这意味着答案质量不仅由大模型决定，还高度依赖检索器在当次请求中“碰巧找到了什么”。即使知识库内确实存在正确答案，只要相关片段没有进入本轮上下文，大模型仍可能得出错误或片面的结论。对用户而言，这种波动很难排查，因为他通常看不到完整的检索路径，也不知道究竟是问题写得不好、切片不合理、向量召回失败，还是模型理解错误。

### 3. 传统RAG缺乏清晰的“知识改进接口”，好答案和坏答案都难以沉淀

当RAG回答不理想时，普通用户往往不知道应该修改哪里。问题可能来自原始文档、文档切片、Embedding模型、召回数量、排序规则、提示词或生成模型，但系统通常不会明确指出故障发生在哪一层。即使某次回答非常好，用户也很难把这次分析直接沉淀为知识库的一部分，因为传统RAG仍然主要依赖原始文档，而不是主动积累已经形成的结论。

因此，传统RAG更像一个“每次临时查资料的问答机器”，而不是一个会随着使用逐渐完善的知识系统。用户不断提问，却没有形成稳定的目录、总结、主题文章和交叉引用。时间久了，原始资料越来越多，但知识库本身并没有获得与资料数量相匹配的结构化成长。

### 4. 知识图谱和GraphRAG改善了关联问题，但仍没有彻底解决可读性和维护问题

为了解决向量检索缺乏逻辑关系的问题，人们引入了知识图谱，把文档中的实体和关系抽取出来。例如，“关羽—效力于—刘备”“刘备—建立—蜀汉”等关系可以形成跨文档连接。但传统知识图谱偏向关键词和实体匹配，假如图谱记录的是“关羽”，用户却用“关云长”提问，系统未必能稳定命中相应关系。

微软在2024年提出的GraphRAG，将向量检索与知识图谱结合起来，可以通过语义相似度识别别名和相关概念，还会把图谱划分为多个关联区域，并为每个区域生成摘要。这种方法比纯RAG和纯知识图谱更有能力处理跨文档关系与全局性问题。然而，随着知识规模不断增大，图谱会出现大量节点和边，普通人很难直接阅读、审核和修改；如果完全交由大模型维护，人又难以确认图谱是否准确。它更适合作为机器内部结构，却不一定适合作为人类日常浏览和长期共同维护的知识界面。

### 5. 知识图谱擅长表示离散事实，却难以完整保留人类知识中的连续体验

知识图谱可以很好地表示“谁与谁有关”“某个事件发生于何时”“某个概念属于哪一类”等事实关系，但它难以表达一篇文章的完整论证、一首诗的节奏、一段文字带来的顿悟，或者一个人在长期阅读中形成的审美感受。人类理解世界并不只是把对象拆成实体、属性和关系，还依赖连续语境、叙事过程、语言风格和情感体验。

视频用一个反向例子说明：如果知识图谱真能完整代替文本，那么教材、小说、诗歌和歌词都可以直接写成节点与边，但显然这无法还原原作的意义。因此，一个真正适合个人使用的知识库，既要能够跨文档建立关系，也要尽可能保留完整的自然语言表达。LLM Wiki的优势就在于，它仍然以文章和段落为基本单位，而不是把所有内容彻底拆碎。

### 6. LLM Wiki的核心，是先把原始资料“编译”为一套可持续维护的维基百科

视频用“图书馆”作类比：传统RAG像是用户每次提问，大模型才临时去图书馆翻书，找出几页相关内容后拼成答案；GraphRAG像是大模型事先读过资料，并把实体关系整理成知识图谱；LLM Wiki则像是大模型先把资料读完，再整理成一部有目录、有主题词条、有交叉链接的维基百科。用户提问时，Agent不需要重新在大量原始文件中盲目搜索，而可以先沿着目录和链接进入已经整理好的知识体系。

Karpathy把从原始资料提炼出Wiki文章的过程称为“知识编译”。其产物并不是复杂的数据库，而是一批普通Markdown文件：每个主题对应一个文件，文件之间通过 `[[双向链接]]` 或其他内部链接互相引用，并由 `index.md` 维护整体目录。由于内容仍然是自然语言，人可以直接打开阅读、修改和审核，任何能够读写文件的Agent也都可以参与维护。

### 7. LLM Wiki的结构简单，本质上由原始材料、知识正文、索引规则和输出结果组成

视频对其概念结构的描述包括三个关键部分：第一是 **Raw**，用于存放未经整理的原始材料；第二是 **Wiki**，用于保存大模型编译后的主题文章；第三是 **Schema或配置规则**，用于告诉Agent这个知识库关注什么、应该如何整理和维护。在实际演示中，作者创建了 `Raw`、`Wiki`、`Outputs` 三个文件夹，并增加一个 `CLAUDE.md` 规则文件。

`Raw`中可以放PDF、网页、个人笔记、截图、聊天记录和视频文字稿，不要求用户预先精细分类。`Wiki`保存主题化、结构化的Markdown知识页面；`Outputs`用于存放根据知识库生成的报告、PPT、文章或其他成果；`CLAUDE.md`则相当于知识库的维护说明书。整个架构不强制使用向量数据库，也不依赖复杂服务，最基础的形式就是本地文件夹和Markdown。

### 8. Karpathy的实践表明，中等规模知识库不一定需要立即加入RAG

视频提到，Karpathy曾围绕一个研究主题搭建约 **100篇文章、40万字**规模的知识库。在这一规模下，他认为暂时没有必要使用RAG，Agent可以先读取 `index.md`，再沿着文件之间的交叉链接寻找相关内容。这种方式速度可能不如向量检索，但找到的内容更有结构，也更容易理解其上下文。

这并不等于RAG永远没有价值，而是说明不应把向量数据库视为搭建知识库的必选起点。只有当Wiki增长到数百篇甚至更大规模、目录查找明显变慢时，才有必要考虑在现有结构之上增加RAG。换言之，RAG应该是对成熟知识体系的检索加速层，而不是在缺乏知识组织时用来掩盖混乱的第一步。

### 9. “Farza个人百科”案例说明，LLM Wiki真正的价值是形成高度个性化的决策支持

视频介绍了一位名为 **Farza** 的实践者。他把自己的约 **2500条日记、笔记和聊天消息**交给大模型整理，最终生成约 **400篇文章**的个人维基百科，内容覆盖朋友、创业公司、研究方向、兴趣爱好和喜欢的动漫等信息。这个知识库不是普通意义上的“资料收藏夹”，而是对他长期经历、判断和审美偏好的结构化表达。

当Farza设计新产品落地页时，他可以让Agent参考自己最近喜欢的电影、过去保存的竞品截图及审美资料，给出文案和视觉风格建议。Agent会从个人Wiki中找到他关于吉卜力工作室纪录片的笔记、曾经保存的竞品文章，以及多年前收藏的一支20世纪70年代乐队的照片，从而形成真正贴近其个人品位的方案。这个案例甚至被Karpathy引用，因为它展示了LLM Wiki的核心意义：让Agent不仅“知道公共知识”，还能够持续使用一个人的历史、偏好和经验。

### 10. Wiki比RAG更适合作为“人机共同写作和维护知识”的界面

作者认为，LLM Wiki更有效的根本原因，不只是检索方法不同，而是它提供了一个人和大模型都能理解的知识界面。Markdown文件可以直接阅读，Obsidian可以展示链接与图谱，Git可以记录每一次修改，大模型做了什么变化都能够被检查。发现某篇文章有误时，用户既可以直接编辑，也可以要求Agent按指定意见修订。

相反，传统RAG中的向量、切片、Embedding和召回分数对普通人并不透明，人很难直接参与。LLM Wiki把知识从机器内部的索引结构，重新变成了人类熟悉的目录、文章和引用。它由Agent承担大量整理工作，但知识的最终控制权仍留在人手中，因此更容易做到“可读、可改、可审核、可回退、可持续进化”。

## 值得记住的点 / 行动建议

### 11. 先确定一个明确的使用场景，不要先收集几百份资料

搭知识库之前，首先要回答的不是“我手里有多少PDF”，而是“我准备用这些知识解决什么问题”。例如，产品经理可能需要在做产品决策时综合竞品分析、用户反馈、行业规律和历史项目经验；研究人员可能需要追踪某个学术主题的主要观点、研究方法和争议；内容创作者可能需要管理选题、案例、表达方式和受众反馈。

场景越明确，Agent越容易判断应该提炼什么、舍弃什么、建立哪些链接。若只是把大量文件全部倒入同一个目录，大模型很难形成稳定的组织原则，最后只会得到一堆泛泛的摘要。因此，建议先选一个近期正在研究、并且确实会反复使用的主题作为第一个Wiki。

### 12. 从5—10份高相关材料开始，而不是等待“资料足够多”

视频作者只收集了7—8篇相关文章就开始构建，说明知识库不必以数百份材料为起点。哪怕只有一篇重要文章，也可以先让Agent提炼主题、概念、关键结论和相关问题，建立第一批Wiki页面。随后每增加一篇材料，再让Agent更新已有页面或创建新页面。

这种小步迭代比一次导入几百份资料更容易检查错误，也更容易逐渐形成适合自己的知识结构。第一个目标不是建立“世界上最完整的资料库”，而是验证这种知识组织方式能否帮助自己完成具体任务。

### 13. 按照Raw、Wiki、Outputs和规则文件建立最小目录

可以在电脑上新建一个主题文件夹，例如：

My-LLM-Wiki/
├── Raw/
├── Wiki/
│ └── index.md
├── Outputs/
└── CLAUDE.md

`Raw`存放原始文章、论文、网页、笔记和文字稿；`Wiki`存放Agent生成的主题知识页面；`Outputs`保存最终生成的报告、PPT、方案和其他任务结果；`CLAUDE.md`用于说明知识库的主题、整理标准、文件命名方式、引用规则和更新原则。开始时不必设计非常复杂的Schema，先写清楚“这个知识库研究什么”“希望Agent如何组织内容”“哪些内容不能凭空补充”即可。

### 14. 使用Obsidian和Web Clipper降低资料进入知识库的摩擦

安装Obsidian后，直接把上述文件夹作为Vault打开，就可以浏览全部Markdown文件。再安装Obsidian Web Clipper，遇到有价值的网页时，一键保存到 `Raw` 目录，不需要先花大量时间重命名、分类和排版。对于PDF、聊天记录、会议纪要和视频文字稿，也可以直接放入Raw，之后统一交由Agent处理。

这一步的关键是让“收藏资料”和“进入知识系统”之间尽量顺畅。很多传统收藏工具的问题是资料虽然保存了，却长期没有被重新阅读；而在LLM Wiki中，新增资料可以触发一次Agent更新，使它迅速进入已有知识体系。

### 15. 给Agent一套明确的“知识编译”规则

不要只告诉Agent“总结这些文件”，而应要求它完成更具体的任务，例如：读取Raw中的全部资料，识别核心主题，创建或更新Wiki页面，保留重要事实和来源信息，消除重复表述，标记存在争议的观点，并在相关主题之间建立双向链接。还应要求它更新 `index.md`，保证新页面能够从目录中被找到。

可以进一步规定：不得在缺乏材料支持时自行补充事实；遇到矛盾内容时不要强行合并，而应明确记录不同说法；新增内容应优先写入已有主题页面，只有确实出现新主题时才创建新文件。这些规则越清晰，知识库越不容易无限膨胀成大量重复页面。

### 16. 把每一次有价值的提问和思考重新写回Wiki

LLM Wiki不应只是“导入资料后用来查询”，还应把用户与Agent共同形成的新理解沉淀回去。当一次讨论得出了清晰的框架、判断或行动原则，可以直接告诉Agent：“把刚才的结论整理后更新到相关Wiki页面，并说明它与哪些旧知识有关。”这样，知识库会同时吸收外部资料和个人思考。

例如，你阅读了多篇产品案例后形成了一个新的定价判断，不应让这一判断只停留在聊天记录中。可以让Agent把它写入“产品定价原则”页面，添加适用条件、反例和相关项目链接。长期坚持后，Wiki就不再只是资料摘要，而会逐渐记录你的经验、判断方式和认知变化。

### 17. 定期做知识库健康检查，而不是只增加新内容

知识库长期增长后，常见问题包括同一主题出现多个重复页面、旧观点没有更新、链接指向不存在的文件、页面之间相互矛盾，以及某些文章完全没有与其他内容建立联系。可以定期让Agent检查错误链接、孤立页面、重复主题、矛盾结论、过时内容和缺失关联，并生成一份修复报告。

在自动修复前，最好要求Agent先列出拟修改内容，由用户确认后再执行。这样既能发挥Agent批量维护的优势，也能防止它擅自删除重要信息。健康检查的目的不是追求形式上的整洁，而是保证知识仍然可找到、可理解和可复用。

### 18. 在知识库逐渐重要后加入Git或GitHub Desktop

由于Agent可能一次修改多个文件，版本控制能够帮助用户判断它改了什么，并在出现错误时恢复旧版本。熟悉Git命令行的人可以直接使用Git管理整个知识库；不熟悉命令行的人可以使用GitHub Desktop完成提交、查看差异和回退。视频作者并不推荐完全依赖Obsidian Git插件，因为其个人体验中部分操作不够直观。

不过，在知识库只有少量文件时，不必因为版本控制而延迟开始。可以先定期复制整个文件夹进行简单备份，等页面数量和重要性提高后，再加入规范的Git流程。重要的是确保Agent的修改不是不可追踪、不可恢复的。

### 19. 知识库扩大后，优先采用分层索引，再考虑加入RAG

当Wiki从几十篇增长到几百篇时，可以把一个总目录拆成多个分层索引。例如，总 `index.md` 先列出“技术”“产品”“个人经验”“人物”等一级主题，每个一级主题再链接到自己的二级目录。Agent可以从第一层目录逐步缩小范围，而不是每次读取所有文件。

这种方式可能比向量检索慢，但路径清楚、上下文完整，也方便人类检查。只有当分层目录仍无法满足速度需求时，再考虑为Wiki增加RAG。此时RAG检索的已经不是杂乱原始材料，而是经过整理的高质量Wiki页面，召回结果通常会更稳定、更容易解释。

### 20. 始终保留人工审核权，不要把知识治理完全交给Agent

Karpathy的思路并不是让人彻底退出，而是把机械整理工作交给大模型，让人负责阅读、提问、判断和纠错。Wiki采用Markdown的价值之一，就是人随时可以打开文件检查，而不是面对看不懂的向量索引或巨大知识图谱。用户应定期阅读核心页面，检查Agent是否遗漏条件、错误合并观点或把推测写成事实。

对高风险主题，还应保留来源链接、出处和不确定性说明。一个完全无法由人审核和修改的知识库，即使技术结构复杂，也很难建立真正的信任。LLM Wiki的理想状态是“Agent负责维护，人负责治理”。

## 我的点评

视频对传统RAG局限的概括具有现实意义，尤其是“相似度召回不等于逻辑相关”“答案难以沉淀”“用户难以参与维护”等问题，确实是很多个人知识库体验不佳的重要原因。LLM Wiki的突出价值不在于彻底取代RAG，而在于先把原始资料加工成可读、可链接、可审计的知识层，再决定是否需要增加检索技术。

不过，视频对“Wiki比RAG效果更好”的表述仍需结合任务类型理解：对于几十万字到中等规模、主题相对集中的个人知识库，目录与链接可能足够；对于数百万文档、实时更新或需要精确召回的企业系统，RAG、全文搜索和数据库仍然有必要。LLM自动编译Wiki同样可能出现遗漏、误归类和虚假关联，因此Markdown可读并不意味着内容天然准确。

普通人最值得采用的不是某个固定软件组合，而是这套方法论：**从具体场景出发，小规模收集材料，把资料编译成主题知识，持续把新理解写回系统，并始终保留人工审核和版本回退能力。**
