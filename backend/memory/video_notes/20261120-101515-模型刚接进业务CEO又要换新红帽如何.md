## 🤖 AI 分析

## 一句话概括
文章以红帽（Red Hat）近期在企业 AI 基础设施领域的产品布局为切入点，揭示企业 AI 从试点走向规模化生产面临的核心矛盾：模型迭代越来越快、Token 总成本持续承压、Agent 自主执行带来安全风险，而企业需要在不反复重建底层系统的前提下，实现技术灵活、成本可控、权限可管、安全可靠且能够证明投资回报的 AI 应用。

## 背景与主题
随着大模型、推理模型和 AI Agent 快速发展，企业开始将 AI 接入实际业务流程，但模型更换成本高、GPU 利用率不足、Token 消耗增长、Agent 权限失控等问题逐渐暴露。红帽全球副总裁兼大中华区总裁曹衡康（Victor Tsao）和红帽大中华区方案架构部总经理王慧慧（Aella Wang），从企业基础设施和生产环境治理的角度，解释了红帽正在采取的技术路线。红帽通过 OpenShift、vLLM、llm-d、Red Hat AI 3.5、Lightwell 等平台与项目，尝试将自身在开源操作系统、容器平台和企业软件管理方面的能力扩展至 AI 推理、智能体治理、安全修复和工业机器人。文章不仅介绍了红帽的产品和技术进展，也提出一个更重要的问题：企业 AI 的价值不能只看模型能力和算力规模，还必须看实际运营成本、系统稳定性、风险控制以及最终的商业回报。

## 核心观点

### 1. 企业 AI 最大的基础设施矛盾：模型更新很快，但业务系统不能跟着反复重建
曹衡康用一个典型场景说明企业 CIO 的困境：企业刚选定模型，完成平台搭建，并且把模型接入业务流程，几天之后市场上又出现性能更好的模型，CEO 就希望 CIO 立即尝试新方案。对于个人用户，更换 AI 工具可能只需要打开另一个应用，但企业模型已经与 GPU、推理引擎、数据接口、内部系统及业务流程深度绑定，替换模型可能牵动整套技术架构。企业如果选择长期绑定某个模型，就可能错过新模型在性能、价格或能力上的改进；如果频繁跟进新模型，又会产生迁移、测试、适配和维护成本。因此，CIO 真正需要解决的不是如何永远选中最好的模型，而是如何建立能够持续吸收新模型的基础设施。这意味着企业 AI 架构必须在应用层、模型层、推理层和硬件层之间建立相对清晰的边界，降低技术迭代对现有业务的冲击。

### 2. 红帽的“四个 Any”：把技术选择权留给企业，而不是绑定某一家厂商
红帽将其开放平台战略概括为“四个 Any”，即 Any Accelerator（任意加速器）、Any Cloud（任意云）、Any Model（任意模型）、Any Agent（任意智能体），目标是在底层技术持续变化时，尽量保持企业运行环境的稳定。红帽希望延续 Linux 和 OpenShift 的商业化路径，将不断演进的开源技术整合为企业能够长期维护、部署和管理的平台，而不是让企业每次采用新技术都从零开始。按照红帽提供的数据，目前其平台支持 20 多个开源模型、合计 700 多个模型版本，硬件加速器除 NVIDIA、Intel、AMD 外，还支持中国 GPU 厂商沐曦，并正在推进其他国产算力产品适配。这种开放性对于需要混合云部署、使用多品牌 GPU、兼顾国际与国产技术生态的企业尤其重要，因为它有助于降低单一供应商依赖和未来迁移成本。不过，支持多种模型和硬件不等于完全没有适配成本，企业仍然需要验证具体模型、GPU、驱动、推理框架和业务接口之间的兼容性。

### 3. 企业 AI 正从“购买 GPU 算力”走向“生产 Token、提供模型服务”
王慧慧介绍，红帽观察到的企业 AI 基础设施需求正在经历三个层次的演进：GPU as a Service（GPU 即服务）、Token 工厂和 Model as a Service（模型即服务）。最初，企业主要希望通过统一平台管理 NVIDIA、AMD 等不同品牌的 GPU，让部门按需获得计算资源，而不必分别采购和管理硬件。随着推理业务增多，企业开始希望把 GPU 集中管理，通过模型和推理引擎持续生产 Token，再将推理能力作为内部服务提供给不同部门。在更高层次的 Model as a Service 模式下，IT 部门统一负责模型部署、运行和管理，业务团队根据任务选择适合的模型，而不必各自搭建完整的 AI 环境。这反映出企业 IT 部门角色正在从算力资源提供者转向 AI 能力服务提供者，其管理重点也从 GPU 数量逐步延伸到 Token 产能、服务质量、模型选择、资源分配和业务成本。

### 4. Token 越来越便宜，不代表企业 AI 的总成本越来越低
曹衡康指出，过去一年单位 Token 价格持续下降，但企业在 AI 上的总账单并不一定下降，根本原因在于实际 Token 消耗量也在快速增长。传统模型调用可能只需要一问一答，而思考模型和 Agent 为了完成复杂任务，可能经历多轮推理、工具调用、任务分解、结果验证和失败重试，从而显著增加 Token 使用量。企业必须区分单个 Token 的价格、每次模型请求的成本和每项有效业务任务的综合成本，因为这三个指标可能呈现完全不同的变化趋势。红帽因此提出，对于已经投入大量 GPU 的企业，不应只考虑持续购买外部模型 API，还可以评估建立自己的 Token 工厂，通过自建推理服务改善资源利用率并降低长期依赖。不过，自建平台需要承担 GPU 折旧、电力、运维人员、模型优化及容量管理等成本，如果业务负载不稳定或 GPU 长期闲置，自建方案反而可能比商业 API 更昂贵，因此不能简单认定“自建一定省钱”。

### 5. vLLM 与 llm-d：企业推理优化的重点正从单模型性能延伸到整个集群的服务能力
红帽深度参与开源推理项目 vLLM，同时推动分布式推理项目 llm-d，试图解决企业在大规模 GPU 集群中面临的推理效率、资源调度和生产运行问题。文章介绍，llm-d 于 10 月 20 日发布 1.0 版本，新增或强化了多租户资源管理、请求优先级调度、高可用、滚动升级和面向 Agent 工作流的会话感知路由能力，其中会话感知路由能够让多轮请求尽可能复用已有上下文缓存，从而减少重复计算。IBM Research 的一项基准测试使用 llm-d 部署了约 7530 亿参数的模型，在并行 Agent 工作负载下最多支持 3000 个并发编码 Agent，峰值输出吞吐超过每分钟 660 万 Token。按照该测试所采用的云资源租赁价格估算，单位 Token 成本比同等商业 API 低 5 至 10 倍，展示了规模化自建推理在特定条件下的潜在经济优势。这一结果说明，企业推理平台的竞争力不仅来自模型本身，更来自请求调度、缓存复用、GPU 利用率和集群管理效率；但这些数字属于特定测试场景，不能直接视为所有企业部署后的普遍效果。

### 6. Agent 的开发门槛正在降低，真正难的是企业是否敢让它执行操作
王慧慧认为，开发一个能够处理特定任务的 Agent 已经不再特别困难，开发人员经过几个小时培训，就可能搭建基本可用的智能体。真正困难的是，当 Agent 接入企业生产环境之后，如何确定它能访问什么数据、调用什么工具、执行什么命令，以及哪些操作必须由人工确认。例如在 Agent AIOps（智能体驱动的 IT 运维）场景中，Agent 可能修改服务器配置、关闭机器、执行脚本，甚至删除数据库，一次错误操作可能直接造成业务中断，而不只是生成错误答案。类似风险也存在于 AI 辅助软件开发流程：AI 可以生成代码并参与自动化开发，但代码进入最终合并流程之前，仍然必须经过必要的检查与审核。因此，Agent 的价值越接近真实业务执行，企业对权限边界、操作审计、人工审批和责任追踪的要求就越高，单纯依靠提示词要求 Agent 不要越权并不足以形成可靠防护。

### 7. Agent 应用速度远超治理成熟度，企业需要从模型安全走向执行安全
红帽与 CIO 时代联合发布的《2026 中国企业级 AI 实践调研分析年度报告》指出，接近 70% 的受访企业正在推进 Agent 应用，但正式治理框架覆盖率还不到 15%，说明企业正在快速部署智能体，却尚未普遍建立与之匹配的管理制度。红帽在 Red Hat AI 3.5 中引入或强化模型安全评估、Agent 开发模板、工具调用防护、可观测性和按用户统计 Token 消耗等能力，尝试同时解决安全与资源管理问题。其中，EvalHub 用于模型和 Agent 的安全评估，NeMo Guardrails 用于约束模型及智能体行为，而按用户统计 Token 消耗的功能则有助于企业识别不同团队的资源使用情况。文章强调，真正的 Agent 治理应当由身份认证、工具访问控制、操作审计和人工审批等多层机制共同组成，而不是仅仅限制模型输出什么内容。企业必须从“回答是否安全”进一步转向“系统是否授权、操作是否安全、结果是否可追溯”，尤其是涉及生产数据库和核心业务系统的操作，需要明确自主执行权限以及人工控制边界。

### 8. AI 加快漏洞发现，也暴露出企业软件安全的真正瓶颈：修复和部署
AI 工具能够提升漏洞发现效率，同时也可能让攻击者把多个看似无关的低危漏洞组合起来，形成更复杂的攻击路径，使企业安全防护面临新的时间压力。很多企业运行着依赖 Java、Python 等开源组件的复杂生产系统，当上游项目发现漏洞时，维护人员往往只在最新版本中提供修复，但企业直接升级整个软件版本可能造成接口失效、依赖冲突或业务中断。红帽与 IBM 联合推进的 Lightwell 试图通过 AI 辅助发现漏洞，再由工程师参与验证和修复，将安全补丁回移到企业实际使用的软件版本，避免为了修复个别漏洞而被迫整体升级。10 月 6 日披露的信息显示，Lightwell 已在广泛使用的 Java 库中发现并修复 400 多个此前未知的漏洞，Lightwell Clearinghouse 也进入全面可用阶段，允许企业提交具体软件依赖以申请优先审查和修复。王慧慧还提到，传统情况下企业完成相关补丁部署可能需要 40 多天，通过自动化流程可缩短到 7 至 14 天，说明企业软件安全竞争的关键不仅是谁先发现漏洞，还在于谁能更快完成验证、修复和安全上线。

### 9. 红帽把基础设施延伸到工业机器人，本质上仍是在管理分布式计算环境
在工业自主运营领域，红帽联合 Intel、紫金星宇、西湖机器人和施耐德电气推出解决方案，将企业 AI 基础设施从传统数据中心进一步扩展到工业现场与具身智能系统。联合方案中，西湖机器人负责机器人本体，Intel 提供计算平台，施耐德电气提供工业场景能力，紫金星宇负责通信技术，红帽提供底层软件平台。王慧慧把人形机器人比作一座移动的数据中心，因为它需要在端侧同时处理感知、计算、实时动作和肢体控制，而更复杂的推理和决策可以根据需求放在云端或数据中心。红帽希望借助统一软件环境实现软件在不同运行位置之间迁移，并通过 OpenShift AI 管理多台机器人、模型及计算资源，集中分发算法更新和控制指令。从服务器、虚拟机和容器到工业机器人，红帽希望复用的核心能力始终是统一软件运行环境、集中资源管理和远程运维，但机器人场景还涉及实时性、网络通信和物理安全等问题，最终效果仍需实际工业生产验证。

### 10. 企业 AI 最终要跨越的门槛不是技术演示，而是可验证的投资回报
曹衡康承认，国内外企业在 AI 落地中遇到的问题大体类似：投入往往不小，但真正能够证明投资获得回报的案例仍然有限。对于中小企业，目前更现实的应用主要集中在邮件处理、文档管理和客服等风险较低、流程相对标准化的场景，而自主决策、自动化运维等更复杂的应用，即使在技术领先的企业中也受到成本、安全和可控性的制约。红帽近期从 GPU 调度、分布式推理、Agent 权限治理、软件漏洞修复一路延伸到工业机器人，看似布局广泛，实际上都是在解决 AI 能否可靠进入企业现有生产系统的问题。模型性能提升和基础设施成本下降只代表技术条件正在改善，不等于企业已经创造了可量化的业务价值。红帽开放平台战略是否真正成功，最终仍要通过企业在真实生产环境中的任务完成率、成本变化、风险水平、业务效率和投资回报来检验。

### 三、llm-d 1.0 的生产环境能力

| 功能 | 主要解决的问题 | 对企业的价值 |
| --- | --- | --- |
| 多租户资源管理 | 多部门、多团队共享 GPU 集群 | 降低资源冲突，实现统一管理 |
| 请求优先级调度 | 不同业务任务的重要性和紧急程度不同 | 让关键请求获得更合理的资源分配 |

| 会话感知路由 | Agent 多轮请求可能重复处理已有上下文 | 提高缓存复用机会，减少重复计算 |

文章特别强调会话感知路由的重要性：Agent 工作流往往包含多次连续请求，如果请求能够尽可能复用已有上下文缓存，就有机会减少重复计算，进而降低推理延迟和 GPU 资源消耗。

“对红帽而言，开放平台的价值正在从提供技术选择，进一步延伸到帮助企业管理 AI 运行的成本、权限和风险。”

价值： 凝练了文章的核心主题，也解释了为什么红帽会同时布局推理效率、安全治理、漏洞修复和边缘计算。

## 值得记住的点 / 行动建议
以下建议综合文章中的实际做法与技术逻辑，进一步整理为企业可以执行的措施；其中具体的评估指标和实施步骤属于基于原文的延伸建议，并不全部是红帽受访者的直接原话。

### 1. 选型时不要只比较模型排行榜，要先评估未来更换模型的成本
企业在引入模型之前，应当把模型表现、业务适配、硬件兼容、迁移能力和运行成本放在一起评估，而不是只看基准测试排名。
可以建立一张模型选型表，至少记录：模型名称与版本、适用业务、所需算力、推理引擎、上下文需求、API 兼容性、安全要求、单任务成本以及替换难度。
尤其要提前验证三个问题：如果后续出现更好的模型，现有业务接口是否可以继续使用；如果更换 GPU 厂商，底层推理环境是否需要大幅改造；如果业务需要从云端迁移到本地，数据和服务架构能否延续。
核心原则是把模型当成可替换组件，而不是整个企业 AI 系统不可改变的中心。

### 2. 建立统一 AI 服务平台，避免各部门重复采购和部署
如果一个企业存在多个 AI 应用团队，可以考虑逐步把 GPU 资源、模型部署和推理能力统一管理，形成内部 AI 服务平台。
一种可参考的演进路径是：
第一层：GPU as a Service
集中管理硬件资源，按需分配 GPU

第二层：Token 工厂
统一部署模型与推理引擎，提供 Token 产能

第三层：Model as a Service
提供可选择、可管理、可计量的模型服务

最终：面向具体业务的 AI 应用
客服、文档、研发、运维、Agent 工作流

这种方式的主要价值在于降低重复建设、提高 GPU 共享效率，并让企业能从统一入口监控各业务部门使用的模型、Token 以及相应成本。
但对于 AI 需求很少的小企业，直接采购商业 API 可能仍然是更经济的起点，没有必要为了追求平台化而过早建设复杂基础设施。

### 3. 用“每项有效任务成本”衡量 AI，而不是只看每百万 Token 的报价
企业在评估商业 API 与自建推理平台时，建议至少建立以下成本框架：
单位有效任务成本=AI 系统总成本成功完成且符合质量要求的任务数量\text{单位有效任务成本}
=
\frac{\text{AI 系统总成本}}{\text{成功完成且符合质量要求的任务数量}}单位有效任务成本=成功完成且符合质量要求的任务数量AI 系统总成本​
总成本可以按部署方式纳入 API 调用费、GPU 折旧或租赁费、电力、网络、存储、人工运维、系统维护以及任务失败后的重试成本。
例如，一个 AI Agent 即使使用更便宜的模型，如果每项任务需要反复调用 10 次模型，而另一方案只需要调用 3 次，那么最终任务成本不一定更低。
企业应同时观察任务完成率、平均响应时间、人工返工成本和业务成果；在质量不同的情况下，单纯比较 Token 价格没有太大意义。
真正值得优化的不是 Token 消耗绝对值，而是在达到要求的结果质量时，完成一项业务任务需要支付多少总成本。

### 4. 是否自建 Token 工厂，先检查业务负载与 GPU 利用率
不能因为某项大规模推理基准测试显示自建方案成本低于商业 API，就认定所有企业都应该购买 GPU、部署大模型。
在决策前，建议重点检查四类条件：业务调用量是否足够大且相对稳定、GPU 是否具有合理的预期利用率、企业是否具有模型部署和运维人才、模型及业务需求是否需要长期更新。
同时开展商业 API、自建推理和混合方案的对比，评估不同并发需求以及不同调用量下的成本变化。
如果推理需求持续且稳定，自建可能具备优势；如果任务量较小、波动很大或模型更新频繁，商业 API 的弹性可能更有价值。
自建与外购不是身份选择，而是一道资源利用率和长期现金成本的计算题。

### 5. 对高并发 Agent，优先优化缓存复用和任务调度
Agent 与普通问答最大的运行差异之一，是前者常常需要持续执行多轮任务，其中可能反复使用相同的上下文信息。
企业部署并发 Agent 时，可以重点测试会话感知路由、KV Cache 复用、请求优先级、多租户隔离和资源利用率，并结合 llm-d 等基础设施能力进行验证。
例如，同一个编码 Agent 在多轮操作中可能重复涉及项目代码和任务上下文，如果平台能够合理复用缓存，就可以减少部分重复处理。
但缓存优化也必须与会话隔离、数据访问控制和缓存失效管理结合，不能为了性能牺牲不同用户、部门之间的数据边界。
建议同时监控缓存命中率、GPU 利用率、峰值吞吐、首 Token 延迟、任务完成时间以及失败重试次数，而不只追求一个漂亮的 Token 吞吐数字。

### 6. Agent 上生产环境前，建立明确的操作权限分级
企业不应将所有工具和系统权限一次性授予 Agent，而应根据操作风险划分权限等级。
下面是一种可供参考的分级设计：

| 风险级别 | 典型操作 | 建议控制方式 |
| --- | --- | --- |
| 低风险 | 查询公开资料、读取经授权的非敏感文档 | 可在授权范围内自主执行并记录日志 |
| 中风险 | 修改内部草稿、整理文档、生成代码 | 限定可修改资源，保留版本与审核机制 |
| 高风险 | 修改生产服务器配置、执行关键脚本、变更核心业务数据 | 强身份认证、细粒度授权、必要时人工审批 |
| 极高风险 | 删除生产数据库、批量删除核心数据、关闭关键生产系统 | 默认禁止 Agent 自主执行，采用严格人工控制和额外验证 |

这些分级属于基于原文风险描述形成的实施建议，不是红帽在文章中发布的正式分级标准。
企业尤其要避免通过提示词代替系统权限管理，应优先落实最小权限原则、工具访问控制、完整操作日志、可追溯审批以及故障回滚机制。
判断 Agent 能否安全上线，不仅要看它能不能完成任务，更要看它做错事时，企业能否阻止、发现和恢复。

### 7. AI 生成代码必须进入原有研发质量管理体系
企业采用 AI 编程工具后，可以提高代码生成效率，但不应因此降低代码合并和发布要求。
比较稳妥的做法是：AI 生成代码先进入独立开发分支，自动完成基本测试、静态检查、安全扫描和依赖检查，再按照变更风险进行代码审核，最后进入合并与部署流程。
对于涉及身份认证、支付、数据库操作、网络安全和生产系统配置的代码，尤其要提高审核强度。
这里需要坚持一个基本原则：无论代码由人编写还是 AI 生成，都应当符合相同的生产质量和安全标准，而且 AI 生成速度越快，越应重视验证和审核能力是否跟得上。

### 8. 建立“发现漏洞—验证风险—修复补丁—上线部署”的安全闭环
企业安全工作不能停留在漏洞扫描报告层面，而应关注漏洞从发现到完成修复的整个周期。
对于使用大量历史版本 Java、Python 组件的企业，建议建立软件依赖清单和版本清单，明确关键系统所使用的第三方开源软件及其风险。
当上游只修复最新版本而企业无法直接升级时，可以评估补丁回移方案，并要求相关补丁经过兼容性测试、功能回归和必要的人工验证。
同时通过自动化流程缩短测试、审批和部署时间，把“漏洞发现后的等待期”纳入安全治理指标。
文章中从 40 多天缩短至 7—14 天的案例说明，安全能力提升不仅来自 AI 发现更多漏洞，也来自企业把修复流程真正工程化、自动化。

### 9. 先从风险可控的业务场景证明 ROI，再扩大 Agent 自主权限
中小企业不必一开始就追求全自动办公、无人化 IT 运维或具有复杂自主决策能力的 Agent。
文章提到的邮件处理、文档管理和客服是更现实的起点，因为这些任务通常具有一定标准化程度，也更容易量化处理时间、人工成本、错误率和业务效率。
建议在试点开始时就确定基线指标，例如处理一份文档原本需要多少分钟，AI 介入后需要多少分钟，错误率是否上升，员工还需要进行多少人工检查。
在证明任务质量、成本和实际收益之后，再逐步增加工具调用、自主执行范围和业务系统接入深度。
先证明 AI 对业务有价值，再决定要不要扩大算力投入、增加智能体权限或建设更复杂的平台。

### 10. 机器人等边缘 AI 场景，要把统一运维与物理安全同时考虑
对于计划部署大量工业机器人或边缘智能设备的企业，值得借鉴红帽把机器人视为“移动数据中心”的管理思路。
部署前应明确哪些任务必须在端侧完成，哪些任务可以交给云端或数据中心处理，并评估网络延迟、通信中断、算力限制及实时控制要求。
运维体系中可以逐步统一机器人软件环境、模型版本、算法更新流程和运行状态监控，减少大量设备独立维护的难度。
不过，工业机器人还直接与物理环境交互，因此系统治理不仅关系到数据和软件，也关系到设备动作、现场人员以及生产安全，不能照搬纯软件 Agent 的全部管理方法。

## 我的点评
这篇文章最值得认同的地方，是它没有把企业 AI 落地简单理解为部署更强的模型，而是把问题推进到了系统兼容、运行成本、权限治理和生产可靠性这些真正影响企业长期采用的环节。尤其是“Token 单价下降但总账单未必下降”和“Agent 开发容易但治理困难”两点，揭示了 AI 从演示应用转向实际生产时经常被低估的成本与风险。红帽围绕开放平台、分布式推理、安全治理、漏洞修复和机器人管理的布局具有相对清晰的商业逻辑，但文章引用的高并发推理与成本优势主要来自特定基准测试，不能直接等同于一般企业的实际收益。另一个需要保留判断的地方是，文章主要依据红帽高管的解释及相关产品和合作案例，缺少独立客户长期使用数据，例如真实生产负载下的故障率、完整拥有成本、实施周期及可核算 ROI。对于普通企业和技术决策者，最有用的启示不是立即采用某一套平台，而是先明确业务目标和成功标准，再用合理成本部署 AI，并逐步建立模型可替换、资源可计量、操作可审计、故障可恢复的技术体系。

## 📝 完整文字稿

“刚选定模型、完成平台搭建，业务流程也已经接入。但没过几天，市场上又出现一个表现更好的模型，CEO 转头就问 CIO：能不能也试试？”红帽全球副总裁兼大中华区总裁曹衡康（Victor Tsao）提到了企业落地 AI 时经常遇到的一个困境。

对企业来说，换模型并不像个人更换一个聊天工具那么简单。模型背后还连接着 GPU 适配、推理服务、数据接口和业务流程，前一套系统刚刚跑顺，新模型就来了，企业既不想错过技术进步，也不愿意为此重新搭建整套环境。

Agent 的出现又带来了另一层压力。当智能体开始接入企业内部系统，能够访问什么数据、执行哪些操作，就成了必须明确的问题。如果缺乏有效的权限约束，Agent 为了完成任务，甚至可能直接删除生产数据库。

模型迭代越来越快，企业需要保持技术选择的灵活性；Agent 能力越来越强，企业又必须确保其行为可控。这些变化正在推动企业 AI 基础设施从模型部署和算力供给，进一步走向推理效率、资源管理和运行治理。

红帽近几个月的产品布局也围绕这些问题展开：从 GPU 调度和 Token 生产，到 Agent 权限管理，再到软件漏洞发现与修复，试图解决 AI 从试点走向生产环境时遇到的实际困难。

##### 底座不能频繁重建，总账单需要控制

模型厂商之间的竞争，正在让企业 IT 部门面临新的选择难题。

企业如果把业务流程深度绑定在某个模型和运行环境上，就很难及时享受到新技术带来的收益。模型换代还会牵动底层硬件、推理框架和应用接口，之前的投入也未必能够直接复用。

曹衡康认为，企业 CIO 真正关心的不只是哪个模型最好，而是当前选择的平台能否适应持续变化的技术环境。过去，红帽将这一思路概括为“四个 Any”：任意加速器、任意云、任意模型和任意智能体。

红帽希望延续 Linux 和 OpenShift 的路径，将开源技术转化为企业可以长期使用的商业化平台。底层硬件和模型可以变化，但企业不必每次都重新建设整个运行环境。据红帽介绍，目前其平台支持 20 多个开源模型、合计 700 多个版本。在加速器方面，除了 NVIDIA、Intel 和 AMD，也已经支持国产 GPU 厂商沐曦，并继续推进其他国产算力产品的适配。

随着企业对算力的管理需求增加，这种开放性也开始从硬件层向推理服务延伸。

红帽大中华区方案架构部总经理王慧慧（Aella Wang）提到，红帽早期将相关场景称为 GPU as a Service，即通过统一平台管理不同品牌的 GPU，让企业按需使用。随着推理需求增长，客户开始更多地谈 Token 工厂：将 GPU 资源集中起来，通过模型和推理引擎生产 Token，再将其作为服务提供给不同业务部门。再往上一层，则是 Model as a Service，由企业 IT 部门统一提供模型服务，业务部门根据自身需求选择模型，而不必分别搭建运行环境。

这背后是企业 AI 成本结构的一次变化。

曹衡康指出，过去一年，单位 Token 价格虽然持续下降，但企业的总账单不一定减少。随着思考模型和 Agent 普及，一项任务可能需要多轮推理、工具调用和结果验证，Token 消耗量也随之增加。单价下降，并不意味着总支出同步下降。

这也是红帽提出企业不能只做 Token 消费者，还应该考虑成为 Token 生产者的原因。对于已经投入大量 GPU 资源的企业，可以通过自建推理平台提高算力利用率，减少对外部 API 的长期依赖。

不过，自建 Token 工厂并非天然更便宜。它需要相对稳定的业务负载、合理的 GPU 利用率、专业的运维团队，以及持续的模型优化能力。如果算力长期闲置，折旧、电力和维护成本反而可能高于直接调用商业 API。企业真正需要比较的，不是单个 Token 的价格，而是完成一项有效任务的综合成本。

红帽在推理基础设施上的布局，正是围绕这一问题展开。其深度参与的 vLLM 已经成为开源模型推理领域的重要项目。与此同时，红帽还推动分布式推理项目 llm-d，希望进一步解决大规模 GPU 集群中的资源调度和推理效率问题。

10 月 20 日，llm-d 发布 1.0 版本。相比此前主要关注推理性能和集群调度，这次更新进一步补齐了生产环境所需要的多租户资源管理、请求优先级调度、高可用和滚动升级能力，并增加了面向 Agent 工作流的会话感知路由，让多轮请求尽可能复用已有上下文缓存，减少重复计算。

IBM Research 的一项基准测试展示了其规模化能力：通过 llm-d 部署约 7530 亿参数的模型，在并行 Agent 工作负载下，最多支持 3000 个并发编码 Agent，峰值输出吞吐超过每分钟 660 万 Token。按照测试采用的云资源租赁价格估算，单位 Token 成本比同等商业 API 低 5 至 10 倍。

这类优化的价值不仅在于提高吞吐量，也在于让 GPU 资源能够承载更多并发任务，降低高负载下的推理成本。

在中国市场，红帽还与趋境科技共建推理 AI 创新实验室 AI 推理技术联合创新实验室。双方的分工是，红帽提供 vLLM 推理框架和标准化平台，趋境科技负责不同模型、加速卡和平台环境下的具体优化，包括 KV Cache 处理等技术实现。双方希望将成熟成果进一步回馈开源社区。

##### Agent 真正难的不是开发，而是权限

推理效率解决的是 AI 能否以合理成本运行，Agent 进入企业工作流后，另一个问题随之出现：企业敢不敢让它真正执行操作？

王慧慧认为，当前智能体开发本身已经不是很高的门槛，开发人员经过几个小时培训，就可能搭建一个能够完成特定任务的 Agent。真正复杂的是权限管理和治理。

当 Agent 开始承担 IT 运维工作，它可能修改服务器配置、关闭机器、执行脚本，甚至删除数据库。一旦操作超出预期，影响的就不再是一段错误回答，而可能是企业真实运行的业务系统。红帽将这一方向称为 Agent AIOps，即通过智能体承担企业内部的 IT 运维工作。

类似的风险也出现在 AI 辅助软件开发中。AI 生成代码之后，可以进入自动化开发流程，但并不意味着可以跳过审核。无论代码由人还是 AI 生成，都需要经过相应检查，尤其是 AI 生成的代码，仍需要必要的审核环节，才能进入最终合并流程。

这意味着，企业需要管理的不只是模型本身，还包括 Agent 的实际执行行为：它能调用哪些工具、访问哪些数据，哪些操作可以自主完成，哪些必须经过人工确认。

Red Hat AI 3.5 进一步加入模型安全评估、Agent 开发模板、工具调用防护和可观测性能力。其中，EvalHub 可以帮助企业对模型和 Agent 开展安全评估，NeMo Guardrails 则用于约束模型和 Agent 的行为。平台还增加了按用户统计 Token 消耗的能力，帮助企业追踪不同团队的资源使用情况。

红帽与 CIO 时代联合发布的《2026 中国企业级 AI 实践调研分析年度报告》也反映了应用速度与治理能力之间的落差：接近 70%的受访企业正在推进 Agent 应用，但正式治理框架覆盖率还不到 15%。

对于企业来说，Agent 的权限不能只靠一条提示词约束，还需要身份认证、工具访问控制、操作审计和人工审批等机制共同发挥作用。尤其涉及生产数据库、核心业务系统等高风险资源时，企业必须明确自主执行的范围，并保留必要的人工控制。

##### AI 发现漏洞更快，企业修复跟得上吗？

Agent 治理之外，AI 还在改变软件安全的攻防节奏。AI 工具加快了漏洞发现，也可能帮助攻击者将多个看似无关的低危漏洞组合起来，形成更复杂的攻击路径。

对于企业而言，发现漏洞只是第一步，真正麻烦的是修复。很多生产系统依赖大量 Java、Python 开源组件，当漏洞出现时，上游社区维护人员通常只会在软件的最新版本中进行漏洞修复。对于拥有高度自定义、互连生产环境的企业来说，直接升级到新版本可能引发兼容性问题。企业往往需要在安全风险和系统稳定性之间作出取舍。

红帽与 IBM 联合推进的 Lightwell，试图解决的正是漏洞发现之后的修复问题。其方式是利用 AI 辅助漏洞识别，再由工程师参与验证和修复，将补丁回移到企业实际使用的软件版本中，尽量避免为了修复漏洞而整体升级。

10 月 6 日，IBM 与红帽披露，Lightwell 已经在广泛使用的 Java 库中发现并修复 400 多个此前未知的漏洞，Lightwell Clearinghouse 也正式进入全面可用阶段，企业可以提交具体的软件依赖，申请优先审查和修复。

企业还需要将补丁快速应用到生产环境中。王慧慧还给出了一组时间对比：传统情况下，企业完成相关补丁部署可能需要 40 多天，通过自动化流程可以缩短到 7 至 14 天。

从漏洞发现到补丁部署，Lightwell 希望缩短的是企业安全响应中间的这段时间。对于仍然运行大量旧系统的企业，这种方式也能减少因整体升级带来的业务中断和兼容性风险。

#### 红帽的平台边界也在变化

红帽的基础设施能力还在从数据中心向工业现场延伸。

在具身智能领域，红帽联合 Intel、紫金星宇、西湖机器人和施耐德电气，推出面向工业自主运营的联合解决方案。这套方案中，西湖机器人提供机器人本体，Intel 提供计算平台，施耐德电气提供工业场景能力，紫金星宇提供通信技术，红帽则负责底层软件平台。

王慧慧将人形机器人比作一座移动的数据中心，。机器人端侧负责集成感知、计算、实时动作和肢体控制等多种能力，。随着应用场景要求的提高，更复杂的推理和决策则可以放在云端或数据中心。在红帽平台支持下，软件无需重新编译即可实现位置迁移。此外，通过红帽 OpenShift AI，企业可以统一管理多台机器人、模型和相关计算资源，集中下发算法更新和控制指令。

这实际上是红帽原有平台能力向边缘计算场景的延伸。过去管理的是数据中心里的服务器、虚拟机和容器，现在则可能增加工厂里的机器人。对于需要部署和管理大量设备的企业，统一的软件环境和远程运维能力也会变得重要。

回到企业 AI 落地本身，曹衡康坦言，国内外企业面临的问题大体相同：投入不小，但真正能够证明投资获得回报的案例还不多。中小企业目前仍主要集中在邮件处理、文档管理和客服等相对轻量的场景，更复杂的自主决策和自动化运维，即使在领先企业中，也受到安全、成本和可控性的限制。

从 GPU 调度、分布式推理，到 Agent 治理、漏洞修复，再到工业机器人，红帽近几个月的产品布局看似分散，实际都指向同一个问题：如何让不断变化的 AI 技术进入企业现有系统，并在生产环境中稳定运行。

模型和算力仍在快速迭代，企业却不能跟着每一次技术变化重建基础设施。对红帽而言，开放平台的价值正在从提供技术选择，进一步延伸到帮助企业管理 AI 运行的成本、权限和风险。至于这些能力能否转化为可量化的业务回报，还需要更多真实生产场景来验证。
