# ## 一句话概括

这期视频介绍了一个名为 **Loop Engineering（循环工程）** 的 AI Agent 工作方式：不再靠人工反复写提示词，而是设计一个能够“自主发现任务→执行任务→记录结果→生成下一轮任务”的循环系统，并以一个“GitHub Trending 项目监控雷达”为例，展示如何利用免费大模型 Agnes 2.0 Flash 搭建长期自动运行的 AI 工作流。

# ## 背景与主题

近期，Cloud Code 负责人 Boris 提出了一个新概念——**Loop Engineering（循环工程）**。乍看像是 AI 圈的新术语，但作者研究后发现，其本质并不复杂：让 Agent 不再被动等待人类输入提示词，而是主动进入一个持续运行的工作循环。

为了验证这一思路，作者搭建了一个自动化 GitHub 热门项目监控系统。这个系统每天自动抓取 GitHub Trending 项目、去重、打分、下载、安装测试、分析价值，最后通过微信推送最值得关注的项目。

整个案例同时展示了一个关键问题：**长期运行的 Agent 系统非常消耗 Token，因此需要一个成本低、上下文长、能够长期运行的模型。** 作者最终选择了 Agnes AI 的免费模型 Agnes 2.0 Flash，并以此完成整个项目。

本视频既是在讲 Loop Engineering 的设计思想，也是在讲如何利用免费大模型搭建一个真正可长期运行的 AI Agent 系统。

# ## 核心观点

### 1. Loop Engineering 的核心不是提示词，而是“循环机制”

传统 Prompt Engineering（提示词工程）强调如何写出更好的提示词，而 Boris 提出的 Loop Engineering 则更进一步：不要让人类不断给 Agent 下指令，而是让 Agent 自己产生下一轮任务。作者总结其本质为：Agent 自动发现任务、执行任务、记录结果、生成下一轮提示词，然后继续运行。这样一来，AI 不再是一次性工具，而更像一个持续工作的数字员工。作者认为，这并不是什么高深的新理论，而是把 AI 从“对话模式”升级到“自动化工作模式”。

### 2. AI Agent 最适合承担长期重复性的信息筛选工作

作者选择 GitHub Trending 监控作为实验对象，原因是这类任务具有明显特点：

- 每天都会出现新项目；
- 信息量巨大；
- 大量重复劳动；
- 人工筛选成本高。

系统每天自动：

**1. 抓取 Trending；**
**2. 去重；**
**3. 项目评分；**
**4. 下载项目；**
**5. 尝试安装运行；**
**6. 输出分析报告；**
**7. 微信推送。**

作者将其形容为：

“一个不会休息的 GitHub 项目雷达。”

这种任务不需要创造力，但需要长期坚持，因此特别适合 Agent 自动化执行。

### 3. 稳定规则交给代码，判断和分析交给 Agent

这是整套系统最重要的设计思想之一。

作者强调：

“代码做稳定工具，Markdown 保存状态，Agent 负责判断和执行。”

例如：

GitHub Trending 去重本质上是集合运算。

如果让 Agent 去判断：

- 成本高；
- 容易出错；
- 不稳定。

因此作者直接写脚本读取 `sync.txt` 完成去重。

类似的：

- 抓取 Trending → 脚本
- 去重 → 脚本
- 微信发送 → 脚本

而：

- 项目价值判断
- 技术分析
- 是否值得关注

则交给 Agent。

这种设计实际上是在利用：

**程序 = 确定性能力**

**Agent = 非确定性判断能力**

二者分工明确。

### 4. 状态管理必须轻量化，否则上下文会无限膨胀

长期运行 Agent 的最大问题之一是上下文越来越长。

作者采用两层状态存储设计：

#### sync.txt

只保存：

- 项目名
- 仓库名
- 日期
- 分数
- 是否通知

属于轻量索引。

#### history.md

保存：

- 详细分析
- 跳过原因
- 测试结果
- 运行状态

这样设计的好处是：

Agent 每次运行不需要重新读取所有历史记录。

避免：

- Token 消耗爆炸；
- 上下文窗口被占满；
- 运行速度下降。

这是长期运行 Agent 系统非常重要的工程经验。

### 5. Agent 应该先做轻量筛选，再做深度分析

作者没有让 Agent 对所有 Trending 项目都深入研究。

而是采用两级筛选机制。

第一阶段：

快速评分。

评分维度包括：

- 是否与 AI 相关；
- 是否属于开发工具；
- 是否有创新点；
- Data 增长是否异常；
- README 是否清晰；
- 是否适合作为短视频选题。

低分项目：

直接记录原因并跳过。

高分项目：

交给子 Agent 深度分析。

这样做的原因是：

GitHub Trending 每天项目很多。

如果全部深度分析：

- Token 成本巨大；
- 时间浪费严重。

先筛选再深挖是典型的信息漏斗设计。

### 6. 子 Agent 架构能有效隔离脏上下文

作者特别强调了子 Agent 的价值。

高分项目进入分析阶段后：

子 Agent 会：

- Clone 仓库；
- 阅读 README；
- 分析依赖；
- 查看配置；
- 阅读 Release；
- 查看 Issue；
- 安装项目；
- 尝试运行；
- 执行测试。

过程中会产生大量垃圾信息：

- 安装日志
- 报错堆栈
- 测试输出
- 编译信息

如果这些内容进入主 Agent：

上下文会迅速污染。

因此作者采用：

主 Agent → 调度

子 Agent → 执行

最终主 Agent 只接收：

- 项目分析结论
- 测试结果摘要

保持上下文干净。

这实际上是多 Agent 系统中非常经典的上下文隔离策略。

### 7. 长上下文能力是 Agent 系统的重要基础设施

作者指出：

整个流程中 Agent 需要不断读取：

- README
- Issue
- 日志
- 历史 Markdown

因此极度依赖上下文窗口。

视频中特别提到：

Agnes 2.0 Flash 正在灰度测试 100 万上下文窗口。

对于这种长期任务来说：

上下文长度的重要性甚至超过模型智商。

因为 Agent 需要持续记住：

- 过去分析过什么；
- 为什么跳过；
- 项目是否重复；
- 曾经运行结果如何。

长上下文决定了 Agent 的持续工作能力。

### 8. 免费模型正在成为自动化 Agent 的最佳选择

作者最初一直在寻找适合长期运行的模型。

因为：

每天执行任务意味着持续消耗 Token。

最终选择 Agnes 2.0 Flash 的原因包括：

- 免费；
- 无需绑定信用卡；
- 长上下文；
- API 可用；
- 多模态支持。

作者认为：

对于后台自动化任务而言：

成本比性能更重要。

即使模型略弱一些，但只要免费且稳定，就更适合作为长期运行 Agent 的基础模型。

### 9. Agnes AI 的开放策略吸引了大量开发者

作者引用了 Agnes 的公开数据。

截至视频录制时：

Agnes 全模态模型累计调用量：

免费模型对于开发生态具有极强吸引力。

### 10. Loop Engineering 的应用远不止 GitHub 项目监控

视频最后作者强调：

GitHub Trending 雷达只是一个示范案例。

同样架构可以扩展到：

- 论文雷达
- 竞品监控
- Issue Triage

本质都是：

发现信息 → 筛选信息 → 分析信息 → 输出结论 → 进入下一轮循环

这正是 Loop Engineering 的通用模式。

# ## 值得记住的点 / 行动建议

### 1. 不要把所有事情都交给 Agent

判断一件事时先问：

这是确定性问题还是非确定性问题？

如果是：

- 去重
- 排序
- 过滤
- 数据处理

直接写脚本。

如果是：

- 分析
- 判断
- 总结
- 评价

再交给 Agent。

这样效率最高、成本最低。

### 2. 长期任务必须设计状态管理机制

不要每次都让 Agent 重新学习全部历史。

建立：

- 轻量索引文件
- 详细历史文件

分层存储。

这样能大幅降低：

- Token 消耗
- 响应时间
- 上下文污染

### 3. 用筛选漏斗降低成本

不要对所有数据做深度分析。

先：

- 快速评分

再：

- 深度分析

最后：

- 输出结果

这是任何 Agent 工作流都适用的原则。

### 4. 用子 Agent 隔离复杂任务

安装软件、运行项目、测试代码等任务会产生大量日志。

最佳实践是：

主 Agent 不直接执行。

创建：

- Research Agent
- Testing Agent
- Coding Agent

分别处理。

最后只汇总结果。

### 5. 优先寻找可长期运行的低成本模型

很多 Agent 项目不是做一次，而是每天运行。

选择模型时要考虑：

- Token 成本
- 调用限制
- 上下文长度
- 稳定性

而不仅仅是排行榜性能。

长期总成本往往比单次效果更重要。

### 6. 把 Loop Engineering 用到自己的信息工作流中

可以模仿作者的方法搭建：

- AI 新闻雷达
- 学术论文雷达
- 行业监控系统
- 竞品分析系统
- 客户反馈监控系统

让 Agent 自动发现变化并主动通知自己，而不是每天手动检查。

### 7. 先让 Agent 搭框架，再逐步完善

作者开发过程并非一次完成。

顺序是：

**1. 先搭项目结构；**
**2. 开发抓取脚本；**
**3. 测试去重；**
**4. 开发通知系统；**
**5. 最后整体联调。**

这种渐进式开发方式比一次性构建复杂 Agent 更可靠。

# ## 我的点评

这期视频最大的价值不在于 Agnes AI 本身，而在于展示了一个非常实用的 Agent 工程思维：**不要把 AI 当聊天机器人，而要把它当长期运行的自动化系统。** Loop Engineering 本质上是把 Agent 从“单轮问答”升级为“持续工作流”。

作者提出的“代码负责确定性、Agent 负责判断性”的原则尤其值得借鉴，这是目前很多 Agent 项目失败的根源——把本该由程序完成的事情硬塞给大模型，导致成本高、结果不稳定。子 Agent 隔离上下文污染的设计也体现出比较成熟的工程经验。

不过视频中的案例规模还比较小，真正部署到生产环境时，还会遇到权限管理、异常恢复、监控告警、任务调度、成本控制等更复杂的问题。因此 Loop Engineering 更像是一种设计思想，而不是完整解决方案。

对于普通开发者或内容创作者来说，最值得学习的并不是具体工具，而是这个思路：找到那些每天重复发生的信息收集和筛选工作，把它们改造成“发现→分析→记录→通知”的循环系统，让 AI 持续替你工作。这样才能真正发挥 Agent 的长期价值。
