## 核心观点

### 1. 四款 Flash 模型代表了不同的取舍：不能只比较总参数量
四款模型虽然都属于主打推理效率的 Flash 系列，但其参数规模和架构设计差异很大，不能简单地认为参数越多就越值得本地部署。Qwen3.8-Flash-Next 的主干为 125B（1250 亿参数），每个 Token 仅激活 6B；GLM-5.3-Flash 总参数为 320B、激活 18B；Hy4 flash 总参数约 224B、激活 12B；DeepSeek-V4.1-Flash-1017 则拥有高达 552B 的主干和 196B 的 Engram 记忆参数，输出阶段激活 16B。四者的原生上下文长度也不一致，Qwen 为 256K，其余三款均支持约 1M Token，因此 GLM、Hy4 和 DeepSeek 在理论上更适合处理超长文档或大规模上下文任务。作者认为，对本地部署而言，总参数决定了很大一部分权重存储负担，激活参数影响每步计算开销，而注意力机制、缓存设计和推理框架共同决定实际运行效率，必须综合判断。

### 2. MoE 混合专家架构，是这些大型模型能够进入个人部署市场的重要原因
四款模型都采用了 **MoE（Mixture of Experts，混合专家）**架构，这也是作者认为它们受到本地部署用户关注的共同原因。传统稠密模型在每次生成 Token 时，需要使用大部分模型参数参与计算，而 MoE 通过路由机制，只选择部分相关专家参与当前计算，使模型能够在拥有庞大知识与能力容量的同时，控制单次推理的计算量。比如 Qwen 主干具有 125B 参数，却只激活 6B；DeepSeek 主干达到 552B，但输出阶段仅激活 16B，说明其庞大的模型容量并没有等比例转化为每步计算量。这样的设计能够降低计算成本，为较小规模的本地硬件运行高能力模型创造条件，但并不意味着全部参数可以从内存中消失，因为没有被激活的专家权重仍可能需要保存在内存、显存或其他存储介质中。MoE 主要降低的是活跃计算负担，而不是自动消除模型权重的存储成本，这也是为什么一些 Flash 模型虽然推理效率高，实际部署时仍然需要上百 GB 的存储空间。
进一步理解，MoE 带来的收益可以拆成三个层面：
- 模型容量： 可以容纳更多专家，在不同类型任务中调用不同的专业能力。
- 计算效率： 每次只计算一部分参数，减少相对同规模稠密模型的计算负担。
- 部署门槛： 需要同时考虑权重存储、内存带宽、专家路由、KV Cache（键值缓存）和 CPU/GPU 数据传输成本。

因此，MoE 的优势是否能在个人电脑上充分发挥，仍然依赖具体硬件和推理实现。

### 3. 四款模型虽然都采用 MoE，但技术创新的重点并不相同
Qwen3.8-Flash-Next 和 Hy4 flash 都引入了 N-gram embedding / Engram（N 元语法嵌入与条件记忆），可以理解为为模型增加一个通过 Token 组合进行索引的外部记忆结构，用较低的计算成本增强参数容量。其基本逻辑是根据输入中的 Token 组合进行哈希查找，读取对应的嵌入信息，而不需要像普通神经网络参数那样，对整个巨大词表进行密集矩阵运算，因此能够以相对较小的计算增量扩展模型的知识表达能力。GLM-5.3-Flash 则没有采用同样的独立 Engram 词表，而是将重点放在 **KDA（线性注意力）与稀疏 MLA（多头潜在注意力）**的混合设计上，试图减少长上下文场景中的注意力计算和 KV Cache 开销。DeepSeek 的设计更特别，采用 **CED（Causal Encoder-Decoder，因果编码器—解码器）**架构，使输入处理和输出生成采用不同的计算配置，在输入阶段激活 8B 参数、输出阶段激活 16B。由此可见，四款模型都在尝试解决大型模型推理成本问题，但分别从知识存储、注意力效率和推理阶段计算分配等不同角度寻找突破。
GitHub

这几种技术方案的实际含义值得进一步区分：

| 技术 | 主要解决的问题 | 对本地部署的意义 |
| --- | --- | --- |
| MoE 混合专家 | 总参数过大导致计算昂贵 | 每 Token 只激活部分专家 |
| Engram / N-gram 记忆 | 增加知识容量需要更多神经网络计算 | 通过查表增强模型，计算增量较低 |
| KDA 线性注意力 | 长上下文注意力计算成本较高 | 有机会降低长序列处理开销 |
| 稀疏 MLA | 注意力与 KV Cache 资源占用 | 减少需要处理和缓存的信息 |
| Causal Encoder-Decoder | 输入理解与输出生成的计算需求不同 | 对 Prefill 和 Decode 分别优化 |

需要注意： Engram 更准确地说是利用 N-gram 特征构建的嵌入记忆，并非任意查询的通用知识数据库；它可以降低计算需求，但实际使用中仍然需要加载或读取相关数据，也可能带来存储 I/O 成本。

### 4. DeepSeek-V4.1-Flash-1017 综合能力领先，但强大性能伴随着巨大的部署代价
在作者的基准能力测试中，DeepSeek-V4.1-Flash-1017 凭借庞大的模型容量，在绝大多数测试项目上取得领先，显示出较强的基础推理与知识处理能力。在随后进行的常见办公任务测试中，DeepSeek 仍然保持总体优势，说明其能力并不只体现在标准测试题上，也能够在实际任务执行中发挥作用。作者因此认为，DeepSeek 的基础模型能力和复杂任务执行能力都非常扎实，尤其适合更加重视输出质量的用户。不过，视频也指出它在所测多模态任务中的表现存在明显短板，即便总参数量远超其他三款，也并非所有应用场景都能够取得优势。更重要的是，它的模型主干达到 552B，另有接近 200B 的 Engram 参数，即使采用极低比特量化，也仍然需要巨大的存储容量，导致其能力优势很难轻松转化为普通个人用户的本地部署优势。
DeepSeek 还采用了一个特别值得注意的设计：
- Prefill（预填充阶段）： 对输入 Prompt 和上下文进行处理，激活参数约 8B，重点在于提高大量输入内容的处理效率。
- Decode（解码阶段）： 逐步生成输出 Token，激活参数约 16B，为生成过程提供更多计算能力。
- 设计逻辑： 输入阶段通常要快速处理大量已有信息，输出阶段则需要反复生成下一个 Token，因此两个阶段并不一定需要完全相同的模型计算量。
- 实际意义： 可以针对不同推理阶段分别优化资源分配，而不是始终使用同样的计算配置。

这种不对称设计有利于提高特定工作负载的推理效率，但并不能消除巨大权重带来的存储和读取开销。
另外，DeepSeek 官方将该模型定义为具有多模态能力的模型，因此视频中所谓“多模态短板”，应理解为在作者测试项目中的相对表现不足，而不是模型本身不支持多模态输入。

### 5. Qwen3.8-Flash-Next 证明：较小的激活参数与较低的部署成本，可以带来更好的综合性价比
Qwen3.8-Flash-Next 是四款模型中每 Token 激活参数最少的，仅有 6B，同时其 125B 主干也明显小于 GLM 和 DeepSeek，因此具备较好的本地部署基础。视频提到，在基准测试中，Qwen 与同期发布的 GLM-5.3-Flash 表现相当，尽管 GLM 的总参数为 320B、激活参数为 18B，也没有在作者测试中建立明显优势。这意味着，如果两款模型能够完成相似的任务，用户就没有必要为了更高的参数量而承担更大的内存及存储负担。在量化部署方面，Qwen 的极低精度版本约为 66GB，通常的 4-bit 版本约为 110—120GB，在四款模型中成本相对较低。当模型能力差距不大时，更小的文件、更低的激活计算量以及更成熟的部署环境，可能比理论上的参数优势更有价值。
作者对 Qwen 的肯定，本质上是肯定它在“够用的能力”和“可承担的部署成本”之间取得了较好的平衡。
但也要看到它的限制：Qwen 原生上下文仅为 256K，而其他三款均达到约 1M，这可能影响极长文本任务的上限。
因此，它比较适合追求日常办公、代码辅助、知识问答和个人 AI 助手能力，同时对硬件投入较敏感的用户。

### 6. GLM-5.3-Flash 是视频中最令人失望的模型：参数规模较大，却没有转化为对应的成绩
GLM-5.3-Flash 的总参数达到 320B，激活参数为 18B，在四款模型中属于较大规格，并且拥有 KDA 与稀疏 MLA 混合注意力带来的技术优势。但作者测试发现，GLM 的基准能力与参数规模明显更小的 Qwen 相差不大，在实际办公场景中也没有展现出突出的竞争力，整体表现被评价为“毫无亮点”。尤其令人意外的是，GLM 系列旗舰模型原本以编程能力见长，但 GLM-5.3-Flash 在作者的编程测试中仅拿到 13 分，与作者对该系列的预期存在较大落差。与此同时，它的低比特量化文件体积并不小，1-bit 版本约为 95GB，4-bit 版本约为 200GB，激活参数量也比 Qwen 更高。由此形成一个对本地部署用户不太有利的组合：硬件成本更高，作者测试中的任务表现却没有明显更好，因此很难成为四者中优先考虑的性价比选择。
这里需要保留一个重要边界：视频中的“编程 13 分”没有给出完整评分标准、题目数量、满分、推理模式及测试配置。
GLM-5.3-Flash 官方资料将编程与智能体任务列为其重点能力之一，也报告了与作者测试不同的基准结果，因此不能根据这一项分数断言它的通用编程能力必然最差。

### 7. Hy4 flash 的突出价值，是用中等参数规模取得较好的实际能力，并兼顾量化部署空间
Hy4 flash 是这次比较中最新发布的模型，与 8 月底发布的 Qwen 和 GLM 相比，有约三个月的发布时间差，因此在训练方案与架构优化方面可能具备后发优势。它的总参数约为 224B，包含 64B Engram 参数，单 Token 激活约 12B，从规模上看位于 Qwen 与 GLM 之间，明显小于 DeepSeek。作者发现，Hy4 flash 的综合测试表现略好于 Qwen 和 GLM，说明它并没有因为更加重视推理效率而明显牺牲模型能力。相比 GLM，Hy4 不仅拥有较小的激活参数，还通过 Engram 词表将一部分容量放在可查找的记忆结构中，为本地部署创造了更灵活的存储和读取方式。在作者看来，Hy4 flash 既有比较强的实际任务能力，又没有 DeepSeek 那样庞大的模型主干，因此有机会成为新的本地部署性价比选择。
更有价值的是，Hy4 并不是只停留在理论架构设计层面，而是已经出现了有针对性的量化版本。
视频重点提到 `AngelSlim` 提供的 `IQ2_AH` 和 `Q4_K_M` 版本，说明开发者正在通过混合精度量化与独立 Engram 数据存储，进一步降低其实际运行门槛。
不过，作者仍然对 Hy4 保持一定审慎态度：它刚开放权重不久，推理框架和量化方案尚需持续完善，真正的部署体验仍有提升空间。

### 8. 量化精度与文件布局，比单纯的“模型有多少 B”更能影响本地部署结果
视频后半部分将重点转向量化部署，因为对于大多数个人用户而言，真正需要付出的成本不是模型名称里的参数数字，而是模型文件有多大、内存和显存是否足够，以及能否在可接受的速度下完成推理。量化（Quantization）是将模型权重从原本的较高精度表示压缩为较低比特表示的方法，常见的低比特方案包括 1-bit、2-bit、4-bit 等，而 `BPW（Bits Per Weight，每个权重的平均比特数）` 是用于衡量整体存储精度的重要指标。通常来说，更低的 BPW 有利于减小文件体积，但也可能损失模型能力；较高的 BPW 往往能够保留更多数值信息，但会增加存储与运行负担。作者对比发现，Qwen 的 4-bit 文件一般为 110—120GB，GLM 接近 200GB，而 DeepSeek 即使使用极低精度量化，其主干加 Engram 文件也非常庞大。Hy4 比较特殊，其量化方案在缩小主干权重的同时保留了高精度 Engram 数据，因此不能仅看量化名称中的“2-bit”或“4-bit”，还必须了解真实文件体积和混合精度布局。

由此可见：量化模型的名称只是一个粗略的精度标签，最终必须综合比较实际文件体积、精度保持情况和运行所需资源。

### 9. 把 Engram 词表放在 SSD 上，是降低部分模型内存占用的重要思路
视频最值得本地部署爱好者关注的细节，是 Hy4 flash 可以将约 60GB 的 Engram 词表保存在 SSD 中，让主干权重占用较少的高性能内存资源。按照视频的思路，`IQ2_AH` 含 Engram 总体积约为 135GB，其中词表约占 60 多 GB，如果词表使用磁盘映射或按需读取，主干模型需要常驻内存或显存的权重就会显著减少。与始终将所有模型数据完整加载到高成本显存相比，这种布局可以让部分用户以较低的硬件成本尝试更大规模的模型。其背后的关键原因是，Engram 使用查表方式访问相关记忆，理论上不需要在每一次生成时读取整个词表，所以有机会将一部分大容量数据放到相对便宜的 SSD 中。作者由此判断，如果未来有更完善的推理框架与量化版本配合，Hy4 flash 可能在不牺牲太多模型能力的前提下，降低个人用户尝试中大型模型的门槛。
不过，这一点不能直接理解为“有不到 100GB 内存，就一定能流畅运行整个 Hy4”。
原因在于：
- 模型主干仍然需要计算和存储资源。 即使 Engram 不常驻显存，主干权重、运行缓冲区及 KV Cache 也会占据内存或显存。
- SSD 并不等于内存。 按需读取可以降低常驻内存要求，但性能取决于 SSD 延迟、随机读取能力、缓存机制等因素。
- 推理框架必须支持相应的数据布局。 是否允许独立映射 Engram、是否能准确识别模型架构，会直接影响运行可行性。
- 上下文越长，运行资源需求可能越高。 支持 1M Token 只是模型的能力上限，并不表示普通硬件能以同样速度处理百万 Token。

这一思路也不完全是 Hy4 独有。DeepSeek 的相关 GGUF 部署方案同样支持将 Engram 数据映射在磁盘上，根据需要读取，而不强制将整个词表加载至显存。
Hugging Face

因此，真正值得记住的是：当模型采用可独立查找的记忆结构时，存储层次优化可能与模型量化本身一样重要。

## 值得记住的点 / 行动建议

### 1. 选本地模型时，优先比较实际任务表现与部署成本，而不是参数排名
选择模型前，应该先确定自己究竟需要解决什么问题：是日常聊天、知识检索、编程辅助、长文档分析，还是多模态处理。
不同任务对模型能力和硬件资源的要求差别很大。例如，普通文件总结可能并不需要 DeepSeek 这样庞大的模型，但复杂代码生成和多步骤任务规划可能更容易体现高能力模型的优势。
可以按照下面的顺序进行判断：
**1. 明确主要使用任务和可接受的最低输出质量。**
**2. 筛选能够完成这些任务的候选模型。**
**3. 比较模型的原始能力和量化后的能力。**
**4. 根据硬件条件比较运行速度、内存占用和部署难度。**
**5. 在满足需求的模型中，选择综合成本最低的方案。**

关键原则：选择满足需求的最低成本模型，而不是单纯追求跑分最高的模型。

### 2. 硬件资源有限时，优先考虑 Qwen3.8-Flash-Next 这样的低激活模型
对于普通个人用户，Qwen 是视频中值得优先尝试的方向，因为它既有较强的基础能力，又在激活参数和权重规模上保持较低水平。
作者给出的参考体积为：极低比特版本约 66GB，4-bit 版本约 110—120GB。
但部署之前不能只比较文件大小，还需要估算：
- 权重需要占用的显存或内存。
- 推理框架和运行缓冲区的额外开销。
- KV Cache 随上下文长度增长产生的占用。
- CPU 与 GPU 之间的数据传输负担。
- 模型没有完全放入显存时，可能出现的性能下降。

例如，模型文件是 110GB，不代表总共拥有 110GB 内存就一定能够无障碍运行。
最好先通过较短上下文测试稳定性，再逐步提高上下文长度，并观察内存峰值、生成速度及首 Token 延迟。

### 3. DeepSeek 更适合愿意为输出质量付出较高部署成本的用户
如果任务是复杂推理、较难的知识问答或多步骤工作流，DeepSeek 可以作为重点测试对象。
不过，在 GSQ `IQ2_XXS` 方案下，仅主干文件就约 138GB，再加上 110GB 左右的 Engram 文件，磁盘空间合计约 249GB。
这意味着用户至少需要提前考虑几个问题：
第一，是否有足够的高速 SSD 容量存放模型。
第二，是否有足够的显存和系统内存承载主干权重。
第三，是否接受通过 SSD 映射、CPU 内存或部分 GPU 卸载等方式部署，以及相应的性能取舍。
第四，实际运行速度是否能够满足使用需求。
因此，DeepSeek 可以作为个人部署的高能力候选，但未必适合作为所有用户的第一款本地模型。
如果只是偶尔需要其高性能能力，而本地硬件明显不足，也应该将在线 API 的使用成本纳入比较。

### 4. 关注 Hy4 flash 的量化版本与推理框架，尤其是独立 Engram 存储方案
Hy4 flash 是视频最值得后续观察的新模型。
它的 `IQ2_AH` 文件约 135GB，其中 Engram 数据占了很大比例；`Q4_K_M` 版本总体积约为 168GB，视频采用的平均位宽约为 6.05 BPW。
如果打算部署，建议重点关注以下四项：
- 量化质量： 相同任务中，`IQ2_AH` 与 `Q4_K_M` 的表现差多少。
- 词表存储： 能否让 Engram 数据保持在 SSD 上，利用按需读取降低常驻内存。
- 推理框架： 当前版本的 vLLM、SGLang、llama.cpp 或其他框架是否支持目标量化格式。
- 实际吞吐： 在目标硬件上，首 Token 延迟、输出速度和长文本处理速度是否可以接受。

视频发布时，Hy4 的低比特部署生态仍然比较新，因此要特别注意 模型文件、量化方法、推理引擎和引擎版本必须相互兼容。
可以先查阅模型仓库中的 README、运行示例及已验证硬件配置，再决定是否下载上百 GB 的权重文件，以免下载后发现无法直接运行。

### 5. 不要忽视量化带来的能力损失，更不能只看“几 bit”
量化并不是越低越划算。
例如，某个版本虽然能够将文件体积缩小到原来的很小一部分，但如果复杂推理、编程、数学或工具调用能力明显下降，节省的存储成本就可能被更差的任务完成率抵消。
对个人开发者而言，可以建立一个小型量化对照测试：

| 测试维度 | 建议测试方式 | 重点观察 |
| --- | --- | --- |
| 事实问答 | 10 道熟悉领域的问题 | 错误率、事实准确度 |
| 推理能力 | 10 道多步骤题目 | 推导是否完整、结论是否正确 |
| 编程能力 | 5—10 个实际代码问题 | 可执行性、修复成功率 |
| 长文本 | 一份较长 PDF 或知识文档 | 信息遗漏、定位与总结能力 |
| 结构化输出 | JSON、表格、字段提取 | 格式正确率 |
| 工具调用 | 简单多步骤 Agent 工作流 | 调用准确率、任务完成率 |

建议尽可能使用相同 Prompt、推理预算、上下文设置和测试样本，减少其他变量对结果的干扰。
如果低比特版本只是在少数任务上略有退化，但部署资源显著下降，就可能具有实际价值。
反过来，如果模型体积缩小很多，却导致关键任务成功率明显下降，就不一定值得采用。

### 6. 将本地部署成本拆分为四个独立问题来评估
真正的本地部署成本至少包括：
① 磁盘存储成本
决定需要多少 SSD 空间保存模型主干、Engram 文件及其他辅助文件。
② 常驻内存与显存成本
决定模型能否以理想方式运行，以及是否需要将部分权重放到 CPU 内存中。
③ 计算与带宽成本
决定每秒能够生成多少 Token，以及读取权重、切换专家和传输数据时是否存在性能瓶颈。
④ 软件与维护成本
包括推理框架兼容性、模型转换、量化方案适配、依赖安装、版本更新和故障排查。
这四种成本之间并不能简单互相替代。
例如，把 Engram 放到 SSD 上，可能有利于节省内存，却不能直接提高 GPU 的计算能力；采用更低比特量化，可能节省内存，但也可能让输出质量下降。
最终应该优化的是完成一次实际任务的总体成本，而不是单独优化某一个硬件指标。

### 7. 把官方模型评测与本地实测分开，不要混为一谈
视频中 DeepSeek 综合领先、Hy4 表现较好、GLM 编程只有 13 分，都是特定测试环境下得到的比较结果。
需要区分三类数据：
- 官方原始模型成绩： 通常用于评估模型本身的上限或相对能力。
- 第三方统一测试成绩： 可以在相同题目和评分规则下进行横向比较。
- 本地量化实测成绩： 最接近真实部署体验，但会受到量化精度、硬件和软件版本的显著影响。

例如，GLM 在作者测试中的编程成绩并不理想，但不能直接推论它在其他编程基准、其他提示词配置或完整 Agent 工作流中同样表现不佳。
同样，DeepSeek 原始模型能力领先，也不保证低比特量化后在所有任务上仍保持同样的优势。
因此，最可靠的做法是：先用统一测试判断模型能力，再用目标硬件测试量化版本，最后根据自己的任务评价实际价值。

### 8. 建立一套自己的本地模型选型记录表，避免反复试错
建议每次尝试新的开源模型时，都记录下面这些项目：

| 记录项目 | 应填写的内容 |
| --- | --- |
| 模型名称 | 完整模型 ID 和具体版本 |
| 模型主干规模 | 例如 125B、320B、552B |
| 激活参数 | 6B、12B、16B 等 |
| 量化方案 | IQ2_AH、Q4_K_M 等 |
| 权重文件大小 | 区分 GB 与 GiB |
| Engram 大小 | 是否存在独立记忆文件 |
| 实际内存峰值 | 运行时测得 |
| 实际显存峰值 | 运行时测得 |
| 首 Token 延迟 | 从请求到开始输出的时间 |
| 生成速度 | Token/s |
| 上下文长度 | 实际测试的上下文规模 |
| 常用任务成绩 | 根据自己的测试集打分 |
| 框架与版本 | vLLM、llama.cpp、SGLang 等 |
| 已知问题 | 不兼容、崩溃、输出异常等 |

随着模型不断更新，这套表格能够帮助判断新版本是否真正值得替换现有模型。
比如，当某个新模型比当前使用的模型多占用 40GB 内存，却只在少量任务中有所提升，就可以更理性地决定是否升级，而不是只根据热度和宣传内容行动。

### 9. 本次横评的选型结论：根据硬件与需求，而不是盲目确定唯一赢家

资源有限、注重性价比：Qwen3.8-Flash-Next
激活参数最少，低比特文件相对较小。适合优先关注部署成本、日常能力和使用效率的个人用户。

追求综合能力、硬件资源充足：DeepSeek-V4.1-Flash-1017
作者测试中的总体能力最强，但主干规模和 Engram 文件巨大，更适合愿意承担较高部署成本的用户。

关注新模型、愿意尝试新量化方案：Hy4 flash
能力与资源需求处于较好的折中位置，独立 Engram 读取也提供了新的优化空间，值得持续测试。

特定 GLM 生态或任务需求：GLM-5.3-Flash
虽然作者这次测试的评价较低，但对于已经使用 GLM 生态、重视其特定能力的用户，仍可通过实际任务测试决定是否采用。

最终结论：不存在脱离硬件、量化版本和任务需求的绝对性价比冠军。

## 📝 完整文字稿

千问4Flash还是没等来,但是等来了还原4Flash的开放权重。很多朋友都在等新一的量化版本跟推理框架出现之后再来尝试本地部署。在这个等待期间,我们就来把目前市面上几个主流的开源模型的Flash版放在一起,来比较一下看一看。我选择了4款用户使用最广泛的Flash模型。先来看一下技术参数。千问3.8 Flash Next,今年8月底发布的。125B的主干,加上51B的Ngram。激活参数最小,只有6B。原生上下文也是最短的,是256K。和它同时期的JRM5.3 Flash,总参数量是320B。激活参数有18B。原生支持1兆的上下文。

回原4Flash,11月16号发布,11月18号开放权重。总参数量是224B,其中还包含了64B的Ngram。激活参数是12B,刚好介于千问3.8 Flash Next跟JRM5.3 Flash之间。同样原生也支持1兆的上下文。以上三款都是各自体系内的次细节模型。而体量最大的DeepSync V4 Flash 1017,却是DeepSync体系当中目前10G以上的旗舰。552B的主干,近200B的Ngram字表。激活参数16B。总参数巨大,但是激活的比例却是最小的。

为什么这四款体量不小的模型能受到本地部署的青睐呢?主要还是因为它们都采用了MOE混合专家架构。但是虽然架构相同,它们各自实现的方式还是有区别的。千问3.8跟回原4都引入了Ngram字表,作为外部记忆。由于只是通过哈希查找字表来增强模型的知识容量,所以几乎不增加推理算力的成本。而JRM没有可分类的字表。它的特色是在于KDA线性注意力和稀疏的MLA的混合注意力机制,可以直接降低注意力计算跟KB缓存的开销。而DeepSync的架构最为特殊,它采用了因果编解码器。并且,它的激活参数在输入和输出阶段是不对称的。

这种设计就是为了能够在Perfume阶段保持更高的效率,并且在Decode阶段分配更多功能。那我们来看看实测中它们的表现怎么样。在机制测试里面,DeepSync的大参数量给它带来了明显的优势,在绝大部分测试项上都是领先的。而千问3.8跟JRM5.3这一对同级的伙伴表现也是相差无几,但是JRM的参数优势并没有转化成更好的成绩。反而,还原4Flash由于和刚刚两位比起来有近三个月的代差,所以整体的表现还略好一点。我们再来看看在常用办公场景的实际任务测试,DeepSync依然是总体领先。

说明它在模型基础能力跟任务执行上的硬实力还是非常强的,但是也暴露出了它在多模态领域的明显短板。反而JRM作为四款当中参数体量第二大的存在,它的表现可以说是毫无亮点。甚至在它的同族旗舰老大的优势项目编程领域上,它只拿了13分,这个实在是让人大跌眼镜。既然这四个模型的定位是可以本地部署,那观看参数跟测评数据是不够的,部署成本也是重要的考量因素之一。在不考虑全重硬盘放置读取的情况下,天问3.8 FLASH NEXT的部署成本是最低的。低精度的1比特版大概只有66G,简直量化版体积更小。

而精度保持良好的4比特版,一般来说它的大小都在110G到120G左右。而JRM 5.3 FLASH的1比特版基本上都在95G左右,而4比特的精度则有200G左右的大小。再加上它比较大的激活参数,实际部署的效果明显不如天问3.8。再来看一下DeepSync V4.1 FLASH 1017。GSQ新出的IQ1M版本,1.75的BPW,120G的大小。而官方推荐的IQ2 XXS全重是138G,再加上110G的磁表,BPW也只能达到2。所以对于大部分个人本地用户使用者来说,DeepSync的本地部署基本上是属于吃力不堂好。

再来看一下还原4 FLASH。目前腾讯官方的Android Slim的量化方案里面,IQ2 AH含磁表的大小是135G左右,而整体的BPW可以达到4.85。157G Q4KM版本的BPW更是做到了6.05。再把60G的磁表留住在SSD的话,不到100G的全重,对于本地部署来说可以说是相当友好。如果后期能够有更好的推理框架来进行配合的话,或许又多出了一个不错的本地部署选择。好了,我是老林,关注我,评论区聊聊吧。
