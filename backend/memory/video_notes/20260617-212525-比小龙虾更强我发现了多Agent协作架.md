## 一句话概括

这个视频主要讲：作者认为 Anthropic 的 **Managed Agents 多 Agent 协作架构**，代表了当前 Agent 系统从“个人工具”走向“企业级基础设施”的关键方向，其核心是把“大脑、双手、会话、记忆、调度”层层解耦。

## 背景与主题

这期视频的主题，是作者基于自己本地复刻 Anthropic Managed Agents 架构的实践，分析多 Agent 协作系统未来可能的标准形态。作者之前做过一个“养了五只小龙虾协同开发”的视频，展示多个 Claude/Agent 协作开发的效果，但当时他认为自己的实现方式比较别扭，没有分享教程。后来他看到 Anthropic 4 月 8 日发布的一篇关于扩大 Agent 规模的博客，认为其中提出的“脑和手解耦”正好解释了多 Agent 协作的正确方向。作者站在实践者和架构拆解者的角度，试图说明：未来的主线不是单个 Agent 变强，而是如何编排一群 Agent，让它们在云端沙盒中分工协作。

需要说明的是，文字稿里有不少语音识别误差，例如“unthorpec / unthorpeak / Sorpreet”按上下文应理解为 **Anthropic**，“Cloud Code”大概率指 **Claude Code**；个别英文名如“Token / Cube Sandbox / Open A Fontier”可能需要回看原视频确认。

## 核心观点

### 1. 多 Agent 协作的关键，不是“养很多个 Agent”，而是要有一套可扩展的架构

作者开头就说自己“找到了 agent 风群的标准答案”，意思是他认为 Managed Agents 这套架构解决了多 Agent 协作的核心问题。过去很多人想象的是：在本地电脑上养一群随时待命的 Agent，只要用户提出需求，它们就能昼夜不停地协作完成任务。作者此前“养五只小龙虾协同开发”的视频之所以爆火，也正是因为击中了大家对“私人 Agent 团队”的想象。但他后来没有分享教程，是因为他知道那套本地架构“太别脚”，也就是能跑，但不够优雅、不够稳定、不够标准化。真正的问题不是开几个窗口、跑几个 Agent，而是如何让它们可靠分工、并发协作、失败可恢复、上下文可管理。

### 2. Anthropic 的核心启发是“脑和手解耦”：规划决策和执行环境必须分开

作者提到 Anthropic 4 月 8 日的博客，认为里面最重要的观点是：要扩大 Agent 的规模，就要把“大脑”和“双手”拆开。这里的“大脑”指大模型负责规划、推理、拆任务、决策；“双手”指执行代码、运行命令、操作文件的沙盒环境。作者认为，过去很多 Agent 系统把模型记忆和本地环境死死绑定在一起，因此一个配置出错、环境污染、记忆膨胀，都可能导致整个系统越来越难用。解耦之后，模型只负责发指令，底层执行环境变成一个个无状态、可销毁、可重建的沙盒。这样即便某个沙盒跑崩、配置冲突，也可以直接杀掉重启，不会把整个 Agent 系统拖死。

### 3. “宠物与牛马”是理解 Agent 架构转变的关键比喻

视频里用了一个很有意思的比喻：以前大家把 Agent 当“宠物”养，现在应该把 Agent 当“牛马”用。所谓“宠物”，指的是一个长期运行、状态复杂、记忆越来越多、环境越来越脏的 Agent 实例；它一旦出问题，修起来很麻烦，甚至要重装。所谓“牛马”，指的是无状态、工具化、可替换的执行单元，需要的时候拉起来干活，坏了就扔掉再起一个。这个思路非常接近现代云计算里的容器化思想：不要迷信某个长期存在的实例，而是让每个执行节点都可以快速创建、快速销毁、快速替换。作者认为，这样才能避免“一个配置导致全盘崩溃”的问题。

### 4. Managed Agents 的 Coordinator，本质上是一个“不干活的指挥官”

作者在 Anthropic SDK 的 Beta 目录里发现了 Managed Agents 相关模块，并特别注意到 Agents 类型定义中有一个关键字段叫 **Coordinator**。他把 Coordinator 理解成“一个不干活的指挥官”，它的职责不是亲自执行任务，而是拆任务、派活、协调不同 Agent。文字稿中提到，这个指挥官的“花名册里最多有 20 个 Agents”，每个 Agent 都可以拥有独立的 Prompt、工具和 MCP 服务器。作者由此联想到自己过去做长程任务时，经常开多个窗口，一个负责编码，一个负责准备资料，一个负责测试，自己在中间复制信息、协调流程。在 Managed Agents 架构里，过去由人扮演的协调者，被一个专门的 Coordinator Agent 替代了。

### 5. Agent 和 Session 必须分开：Agent 是模板，Session 才是运行中的状态

作者对 Session 的解释很关键：**Agent 和 Session 是两个完全不同的实体**。Agent 是静态的，可以定义它用什么模型、什么工具、什么系统提示词，本质上像一个角色模板。Session 是动态的，是 Agent 被拉起来执行任务后产生的对话、线程、记忆、挂载文件和运行状态。同一个 Agent 可以同时跑 10 个不同 Session，每个 Session 彼此独立，互不污染。作者把这种关系总结为：“Agent 负责我是谁，Session 负责我在干什么。”这句话非常精准地表达了架构解耦的意义。

### 6. Session 不只是聊天记录，而可能成为可复制、可回滚、可调度的“记忆树”

作者进一步提出一个想象：如果某个 Agent 刚刚搜完代码库，此时它对项目理解最深、状态最聪明，但继续执行 A、B、C、D 任务后，上下文被压缩、记忆被丢弃，它会越来越“不聪明”。如果存在一个聪明的编排者，能知道 Agent 在哪个时刻状态最好，并且可以随时回滚、复制、派生这个状态，就能让不同任务从最合适的上下文起点开始。作者把 Session 理解成一种“记忆树”，可以 fork、回滚、克隆，成为 Coordinator 调度 Agent 的工具。这个思路的价值在于，它不是简单延长上下文，而是把上下文变成可管理的资源。也就是说，未来 Agent 系统要管理的不只是任务，还包括“哪个上下文状态最适合执行哪个任务”。

### 7. Session Store 让 Agent 进一步无状态化，记忆从本地搬到云端

作者提到，他在 4 月中下旬看到 Claude Agents SDK 的 Python 代码库里有一条关键 PR：一个叫 **Session Store** 的东西在 4 月 19 日正式合并。按照他的理解，从此记忆可以从本地搬到云端，Claude Code 可以从 Redis 缓存中恢复上下文。这个变化让他“后背发凉”，因为它意味着 Agent 本身可以变得更彻底地无状态。只要上下文、记忆、会话状态可以外部存储，Agent 实例本身就不再重要，可以随时销毁、随时重建。结合前面的沙盒解耦、Coordinator 编排、Session 状态管理，整个系统就越来越像一个面向 Agent 的云端操作系统。

### 8. 作者把 Anthropic 路线抽象为“四层解耦”

视频中作者自己总结了一个“四层解耦”框架。第一层是 Agent 和沙盒解耦，也就是“大脑”和“双手”分开，执行环境崩了可以换。第二层是 Coordinator 编排，一个指挥官带着最多 20 个专业 Agent，负责拆任务和派活。第三层是 Session 作为记忆树，可以 fork、回滚、克隆，成为调度工具。第四层是 Session Store，把记忆搬到云端，让 Agent 完全无状态化，随时销毁和重建。作者也承认这个分层是他自己的抽象，未必完全严谨，但他认为这已经非常接近“Agent 操作系统”的形态。

### 9. 作者本地复刻后的体验：多模型、多容器、多任务图协作，带来很强的 Token Efficiency

作者说自己用了大约一周时间，几乎完整复刻了这套四层解耦架构，包括 Agent 沙盒、Session Store、静态编排器等，只是结果评估模块还没完成。他的实现中，每个 Docker Agent 都可以是 Claude Code、Codex 或其他 Harness，也可以在创建时决定模型、技能、Session 恢复位置、SSH Key 和工作目录。主控服务器通过预定义任务图，让不同 Worker 按规则交互，比如编码、Review、测试，或者 Deep Research 中的并发搜索、并发写作、最后汇总成 PPT 或报告。因为每个节点任务独立，所以可以从全新上下文开始，也可以使用不同模型，做到大模型处理复杂环节、小模型处理简单环节。作者认为这能显著提升 Token Efficiency，也就是用更合理的模型组合和上下文分配，降低浪费、提高效率。

### 10. Agent 正在从个人玩具变成企业基础设施，国内外差距可能不只在模型能力上

视频最后上升到了行业判断。作者提到 Palantir 的 AIP、Anthropic 的 Managed Agents、OpenAI 的某些 Frontier 方向，以及一个新兴职业 FDE，认为它们都在做同一件事：把 Agent 从个人工具变成企业基础设施。相比之下，国内很多讨论还停留在“本地养多只小龙虾”“用 OpenClaw 还是 Hermes”这类工具选择上。作者认为，国产模型这几年进步很快，表面上与海外距离不断缩小，但如果海外厂商已经在思考如何把 Agent 系统产品化、平台化、基础设施化，而很多国内厂商仍主要围绕“卖 Token”优化商业模式，那么真正的差距可能在架构理解和落地层面。这个判断带有明显的警醒意味：未来竞争不只是模型参数和 benchmark，而是 Agent 系统工程能力。

## 值得记住的点 / 行动建议

### 1. 做 Agent 系统时，不要把精力都花在“补丁式 harness”上

作者强调，模型能力变化太快，今天为模型缺陷写的大量补丁，明天可能因为新模型发布而全部失效。因此，如果要做长期可维护的 Agent 系统，不应该把核心竞争力押在复杂的提示词补丁、上下文修补、异常 workaround 上。更稳的方向是做解耦架构：让模型、工具、执行环境、记忆系统、调度系统分离。这样模型升级时，只需要替换“大脑”，而不是重写整套系统。普通开发者也可以借鉴这个思路，尽量把代码执行、文件读写、上下文管理、任务分发做成独立模块。

### 2. 不要把 Agent 当长期宠物养，而要设计成可替换的 Worker

如果一个 Agent 长期运行、状态越来越复杂、环境越来越脏，那么它迟早会变得难以维护。更好的做法是把 Agent 看成一个 Worker：需要时创建，完成任务后销毁，失败后重启。这样可以避免单个实例积累太多不可控状态，也能降低环境污染带来的风险。对于本地 Agent 实践者来说，可以优先考虑 Docker、沙盒、虚拟环境、临时工作目录等方式，把执行环境隔离开。真正重要的不是某个 Worker 活多久，而是任务结果、会话状态和可恢复能力。

### 3. 多 Agent 协作一定需要 Coordinator，否则人会变成调度瓶颈

作者过去开多个窗口协作时，自己就是事实上的 Coordinator：把测试结果复制给编码 Agent，把需求拆给不同窗口，再人工汇总结果。这种方式短期可用，但任务一复杂，人就会成为瓶颈。Managed Agents 的思路是让一个专门的 Coordinator Agent 来拆任务、派活、汇总结果。普通人做多 Agent 工作流时，也应该先设计“谁负责协调”，而不是只堆更多 Agent。没有协调者的多 Agent 系统，很容易变成多个聊天窗口同时胡说，最后还是需要人来收拾。

### 4. 要把 Agent、Session、Memory 分开设计

视频里最值得记住的架构原则之一，是 Agent、Session、Memory Store 三者分离。Agent 是角色模板，决定它是谁、能用什么工具、采用什么模型；Session 是一次具体任务运行过程，记录它正在做什么；Memory Store 则是长期或外部化记忆，不应该直接长在某个 Agent 实例里。这样设计之后，同一个 Agent 可以同时处理多个任务，每个任务互相隔离，也可以把某个状态复制给新的执行节点。对于开发者来说，这能显著提高系统的可控性和复用性。

### 5. 长程任务不能只靠“不断压缩上下文”，要学会保存关键状态

作者指出，单个 Agent 做长程任务时，经常会因为上下文不足而不断压缩，而每一次压缩都会丢失一部分记忆。这会导致 Agent 越做越不聪明，前面刚理解过的代码库、需求背景、约束条件，后面可能又忘掉。更好的做法是把某些关键 Session 状态保存下来，当它处于“最聪明”的时刻，可以复制、回滚或分叉。比如在 Agent 刚完成代码库扫描、刚建立全局理解时，把这个状态作为后续编码、Review、测试任务的共同起点。这样比每个节点重新理解一遍项目更高效，也更稳定。

### 6. 任务图是多 Agent 协作落地的关键工具

作者的本地复刻不是简单让多个 Agent 自由聊天，而是通过预定义任务图安排它们协作。比如编码任务可以拆成多个编码节点、多个 Review 节点、测试节点和汇总节点；研究任务可以拆成并发搜索、并发整理、最终报告生成。任务图的好处是流程清晰、依赖明确、并发可控。每个 Worker 只需要完成自己的局部任务，不需要知道整个系统所有细节。普通人做复杂 AI 工作流时，也可以先把任务拆成图：哪些能并行，哪些必须串行，哪些节点负责验证，哪些节点负责汇总。

### 7. 不同任务阶段应该使用不同模型，而不是全程都用最贵的大模型

作者提到，因为每个 Worker 的任务独立，所以可以让不同节点使用不同模型。复杂推理、架构设计、最终判断可以交给强模型；简单搜索、格式整理、批量改写可以交给小模型。这样可以提高 Token Efficiency，避免所有任务都用最贵模型硬跑。对于企业或个人来说，这一点很实用：多 Agent 系统的成本控制，不只是减少调用次数，而是让合适的模型做合适的事。未来 Agent 编排能力，很大一部分可能就是模型选择和资源调度能力。

### 8. 关注 Agent 基础设施，而不是只关注单个工具哪个好用

作者最后提醒，海外厂商正在把 Agent 做成企业基础设施，而不是停留在“个人桌面助手”或“本地多开工具”。这意味着真正值得关注的是：Agent 如何接入企业数据、如何权限管理、如何审计、如何调度、如何回滚、如何与业务流程结合。普通开发者如果只讨论 OpenClaw、Hermes、Claude Code 哪个更顺手，可能会错过更大的方向。工具选择当然重要，但更重要的是理解背后的系统架构。谁能把 Agent 嵌入企业流程，谁才可能真正产生商业价值。
