## 🤖 AI 分析

## 一句话概括
扩散智能（DiffuSpace）通过分块扩散、双向建模和 Agent 执行框架协同优化，让扩散语言模型 Clover 在复杂编程、工具调用和联合决策任务中展现出速度与能力优势，并试图证明：扩散模型有机会在未来一到两年内，凭借更高的推理效率、更低的长期成本和特定场景下的性能优势，部分替代主流自回归模型。

## 背景与主题
当前主流大语言模型普遍采用自回归（Autoregressive）生成方式，即按照从左到右的顺序逐个生成 Token，而扩散语言模型（Diffusion Language Model）尝试通过并行生成、反复修正和双向信息交互，突破这一生成范式的效率限制。2026 年 11 月，扩散智能发布并开源了拥有 350 亿总参数、约 30 亿激活参数的 Clover-35B-A3B-Preview，并公布技术报告，展示其在 Agent 编程、工具使用以及生成吞吐量方面的竞争力。
文章通过对扩散智能联合创始人、首席科学家龚珊三的专访，梳理了扩散语言模型从 2022 年早期研究到进入复杂 Agent 任务竞争的技术演进，重点讨论分块扩散架构、端到端执行效率、联合决策、基础模型商业战略以及软硬件生态挑战。文章整体采取技术分析与行业观察相结合的视角，既呈现扩散智能的性能成绩和未来预期，也强调 Token 生成速度不等于实际任务完成速度，以及扩散模型尚未解决的全局规划和基础设施问题。

## 核心观点

### 1. 扩散语言模型正在从追求生成速度，转向争夺 Agent 复杂任务执行能力
传统自回归模型（Autoregressive Model）遵循从左到右、逐个 Token 生成的方式，后一个 Token 的生成依赖此前已经生成的内容；扩散语言模型则可以同时处理多个 Token，并在生成过程中反复调整结果，因此具有并行计算和双向信息交互的潜力。过去，扩散模型最重要的卖点是 Token 生成速度，但随着 AI Agent 开始承担写代码、操作软件、调用工具以及执行工作流等任务，单纯生成得快已经不足以建立竞争优势。扩散智能发布的 Clover-35B-A3B-Preview 总参数量为 350 亿、激活参数约为 30 亿，在其技术报告列出的七项 Agent 指标中取得最高分，其中 SWE-bench Verified 达到 73.6，Terminal-Bench 2.1 达到 51.7，部分配置下 Token 生成速度为同级别自回归模型的 5—10 倍。这表明扩散模型正在尝试证明自己不仅能快速生成文本，也能胜任实际编程、终端操作和复杂工具调用。技术路线竞争的核心正在从“谁生成 Token 更快”，升级为“谁能以更低成本、更短时间、更高成功率完成真实任务”。 不过，这些结果仍受评测模型、任务环境和运行配置限制，不能直接推导出扩散模型在所有 Agent 应用中全面领先。

### 2. 分块扩散是 Clover 兼顾并行生成能力和长上下文效率的关键技术
扩散模型虽然能够并行生成 Token，但早期方案需要在生成过程中反复处理较大范围的文本序列，当上下文不断增长时，重复计算会迅速增加，反而削弱并行生成带来的性能优势。为解决这一问题，Clover 引入分块扩散（Block Diffusion），将生成过程拆分为多个 Block：每个块内部并行生成和迭代修正 Token，已经完成的历史内容则通过 KV Cache（键值缓存）复用，避免每轮重新计算全部上下文。这种设计实际上在全局采用分块顺序推进、局部采用并行扩散，试图在计算效率与双向建模能力之间建立平衡。为了同时利用历史状态和当前块内的信息，团队进一步改造 Gated DeltaNet（GDN，门控 DeltaNet），形成支持块内双向信息交互的 BD-GDN，并结合 Full Attention（全注意力）与 dMoE（混合专家架构）构建混合模型。技术报告显示，Clover 每四层包含三层 BD-GDN–dMoE 和一层 Full Attention–dMoE，共重复十组，同时引入共享 Softmax 处理、可学习块大小校准机制以及右侧上下文卷积分支。这项架构的核心价值，是让扩散模型不必在“长上下文计算成本”和“局部并行生成能力”之间完全二选一。

### 3. Clover 已经具备局部双向建模能力，但真正的全局规划仍未实现
扩散语言模型在理论上的重要吸引力，是生成过程中不仅能参考之前的信息，还能够同时考虑后续位置，从而有机会改善内容一致性、约束满足和全局规划能力。Clover 当前已经能够在同一个 Block 内实现双向信息交互，但不同 Block 仍然按照顺序向后生成，因此模型并不能随时重新审视和联合修改整个长序列。龚珊三明确指出：“真正的全局规划，就是从头到尾的全局规划，现在其实没有完全实现。” 这一限制意味着，当前 Clover 的优势主要体现为块内双向建模，而非整个任务执行计划或完整输出序列的全局联合优化。扩散智能正在探索扩大生成块的大小，技术报告中针对完整的 64 条 Agent 历史轨迹前缀进行回放测试时，将块大小从 8 增至 16，观察到每轮提交的 Token 数量以及实际吞吐量均有所提升。未来的关键研究问题，是能否在扩大双向建模范围的同时，控制计算成本，并真正改善推理质量、长期规划和任务完成率，而不只是提高吞吐量。

### 4. Token 生成速度不等于 Agent 任务完成速度，模型与 Harness 的协同决定实际效率
一个真实 Agent 任务通常包含生成操作指令、调用工具、等待执行反馈、判断结果、处理异常以及继续行动等多个阶段，因此模型生成速度仅影响整个执行流程的一部分。现有 Agent Harness（智能体执行框架）大多为自回归模型设计，工作方式是生成内容、调用工具、等待反馈，再继续生成，但扩散模型的并行生成能力可能允许系统同时安排不存在依赖关系的工具调用。Clover 在使用相同 Harness 的公开评测中表现出竞争力，而扩散智能还在研发专门适配扩散模型的 Harness，希望通过模型与执行框架的协同设计进一步缩短端到端任务耗时。文章给出了两个案例：在浏览器创建私有项目并邀请成员的测试中，Clover 用 13 步、169.9 秒完成任务，而 Qwen3.6 Flash 用了 21 步、392.3 秒；在覆盖 49 项任务的 WindTunnel 测试中，Clover 执行耗时中位数为 1.52 秒，Jev 与 Mercury 2.5 组合则为 3.21 秒。这说明效率优势不一定只来自 Token 生成速度，也可能来自行动步骤减少、工具调用策略改善和执行框架优化。但龚珊三也承认，团队尚未完成严格的端到端系统性对比，她提出的生成提速与任务效率提升大致呈 1:1 关系，目前仍属于经验性判断，不能视为已经验证的普遍规律。

### 5. 扩散模型的双向信息交互，为代码一致性和关联问题的联合决策提供了新的可能性
代码、JSON 及其他结构化内容往往存在大量跨位置约束，例如同一个变量的前后引用必须一致，JSON 的字段结构、括号和数据类型必须满足特定规则。自回归生成通常从前向后逐步决定内容，而扩散模型能够在同一生成块内部同时参考前后位置，理论上有利于减少局部不一致和互相矛盾的生成结果。扩散智能进一步将这一特点应用于联合决策（Joint Decision-Making），让模型一次输出多个存在逻辑关联的判断，而不是分别、独立地回答问题。文章中的合同判断案例要求模型回答通知是否及时、保证金能否保留等五个相互制约的问题，联合决策模型五题全部答对，独立模式答对四题，Jev 只答对两题。在规模更大的验证集中，500 组、共 2,420 道关联问题的测试显示，联合预测的单题准确率达到 93.88%，整组全对率达到 77.0%，分别高于独立预测的 90.37% 和 65.4%。这一结果提示，扩散模型的优势不一定只体现在生成更多内容，而可能体现在同时协调多个判断、减少局部正确但整体矛盾的情况。

### 6. AI 正在重新重视 System 1 快速直觉决策，而非一味延长思维链
过去几年，大模型行业持续强化 Thinking（深度思考）能力，通过更长的 Chain of Thought（思维链）和更多测试时计算提升复杂问题的准确率，但这种方法也可能带来更高的推理成本和更长的响应延迟。Jev 等决策模型引发了行业对 System 1（系统一，快速直觉式判断）的重新关注，与需要多步骤分析的 System 2（系统二，慢速审慎式推理）形成对照。龚珊三用羽毛球运动员接球作比喻：运动员不能等到完整计算轨迹和所有可能动作后再挥拍，而必须依靠经验在极短时间内作出决策。机器人行走、道路安全判断、物体抓取和方向选择等任务也具有类似特征，如果每一步都依赖漫长的 Thinking 过程，就可能错过最佳行动时机。扩散模型具有并行生成和短输出双向建模的潜力，因此可能适合需要低延迟、多个判断相互约束的场景。但文章真正强调的不是让 AI 完全放弃深度思考，而是按照任务特点选择不同的决策机制：简单实时判断追求快速响应，复杂高风险问题仍然需要充分推理和校验。

### 7. 扩散智能选择坚持基础模型战略，而非直接进入 AI 应用产品竞争
随着 Clover 开始面向 Agent 编程和工具使用，扩散智能也在开发 Agent Harness 和编程客户端，看起来似乎正在从底层模型公司向应用产品公司转型，但龚珊三明确表示公司的核心定位仍然是基础模型研发。她认为：“纯做产品的公司，其实很容易被基模吞噬。” 这一判断背后的逻辑是，AI 编程助手、个人助手等应用虽然能够凭借交互体验和特定功能形成差异，但基础模型能力持续增强后，一部分应用层功能可能逐渐被模型厂商直接吸收。扩散智能开发自己的 Harness 和客户端，主要目的是验证扩散模型的并行生成优势，并构建与底层架构相适配的使用方式，而不是直接与成熟 AI Coding 产品争夺消费者市场。公司希望将有限资源优先投入模型架构、训练、推理基础设施和开发者生态，以形成更难被复制的技术差异。这体现了一种以基础模型为核心、以应用工具验证能力和建设生态的商业战略，但同时也意味着公司需要承担较高的持续研发投入以及模型商业化的不确定性。

### 8. 复用自回归模型能力，再进行扩散适配，是降低研发门槛的重要路径
扩散语言模型的探索从一开始就面临较大技术不确定性：2022 年龚珊三参与 DiffuSeq 研究，尝试把扩散机制应用于文本条件生成；2023 年团队开始探索扩大模型规模，但缺少可借鉴的成熟技术经验。早期团队尝试在连续空间中进行扩散建模，发现学习复杂度较高、训练难度较大，后来逐渐转向离散空间，经过多轮实验才找到更可行的路线。Clover-35B-A3B-Preview 没有选择完全从零开始训练，而是基于已有的 Qwen3.6-35B-A3B 自回归模型，复用其预训练阶段积累的知识与能力，再进行扩散适配，从而降低前期训练投入。扩散模型使用的训练数据与自回归模型基本相同，主要差异在于训练过程中随机遮蔽部分 Token，并要求模型恢复被遮蔽的内容，这使得相同的数据能够通过不同学习机制形成不同的生成能力。龚珊三认为，即使扩散模型需要更多训练轮次，只要部署后的推理效率足够高，就有可能通过长期、重复调用摊薄额外训练成本。这种路线的关键经济逻辑，是用训练阶段的前期投入换取推理阶段的长期收益，但是否划算仍取决于调用规模、实际吞吐量、硬件利用率及模型维护成本。

### 9. 扩散模型真正的商业机会，可能首先出现在端侧部署和高频、成本敏感的细分场景
龚珊三坚持认为，未来一到两年，扩散模型有机会在部分具体场景中替代相同规模的自回归模型，但这并不意味着短期内全面取代 OpenAI、Anthropic 等公司的前沿模型。相比直接参与最大参数规模和最高算力投入的竞争，扩散智能更希望发挥同级别模型在速度、成本和特定任务能力上的优势，优先探索 AI PC、车载设备等端侧场景。文章披露，团队使用 16GB 显存的 RTX 5070 Ti、AMD Ryzen 7 9700X CPU 和 64GB 主机内存，通过 SGLang 与 KTransformers 实现 GPU–CPU 混合专家推理，并将路由专家权重量化至 INT4、主要非专家模块保留 BF16。在完整 MATH-500 测试中，优化专家放置后，top-8 验证配置达到 97.52 Tokens/s、人工复核准确率 97.6%；使用 top-6 验证时，吞吐量提高到 106.25 Tokens/s，而准确率下降至 96.0%。这一案例说明，扩散模型可以在相对有限的消费级 GPU 显存条件下通过量化、混合推理和配置调整争取较高吞吐量，但速度与准确率之间仍存在需要权衡的关系。扩散智能押注的并非“所有场景都全面领先”，而是先在成本敏感、响应要求高、硬件资源有限且任务适配度较好的应用中建立局部优势，再逐步扩大应用范围。

### 10. 扩散模型能否成为主流路线，最终取决于算法、工程生态和真实应用价值能否形成闭环
一项新模型架构即使在算法层面取得突破，也未必能够迅速形成市场竞争力，因为今天的模型 Serving（推理服务）、算子实现、GPU 计算能力和显存配置，绝大部分都是围绕自回归架构逐渐发展起来的。扩散模型对计算调度、并行生成、历史缓存和双向信息处理的需求可能不同，因此许多现有基础设施未必能直接发挥其优势，团队需要自行开发和优化相关工程组件。扩散智能已经开放 Clover 模型权重、相关代码和 SFT（监督微调）实现，并支持 SGLang、llama.cpp 等推理框架，希望通过开源吸引开发者参与部署、优化算子和探索实际应用。与此同时，Clover 在 Humanity's Last Exam（HLE，人类终极考试）等高难度测试中表现相对薄弱，部分传统任务成绩也略低于 Qwen，说明其通用能力仍存在短板，龚珊三主要将这一现象归因于相关训练数据不足。面向 2027 年，扩散智能计划继续将绝大部分资源用于基础模型训练，把 Scaling（规模扩展）和多模态作为主要方向，并探索具身智能、机器人部署和联合决策等场景。真正的竞争门槛不是单独证明扩散生成可行，而是让模型性能、运行成本、开发工具、软硬件适配和用户需求共同形成可持续的优势。

### 三、Clover 的技术架构与训练机制

| 技术 | 具体设计 | 解决的问题 |
| --- | --- | --- |
| Block Diffusion | 将长序列生成划分为多个 Block | 减少反复处理长序列带来的计算开销 |
| KV Cache | 缓存已生成历史内容的中间状态 | 避免重复计算历史上下文 |
| BD-GDN | 双向改造 Gated DeltaNet | 同时利用历史信息和块内双向信息 |
| Full Attention | 与 BD-GDN 混合使用 | 补充注意力建模能力 |
| dMoE | 混合专家架构 | 通过专家机制组织模型计算 |
| 混合层结构 | 3 层 BD-GDN–dMoE + 1 层 Full Attention–dMoE，重复 10 次 | 在不同建模机制之间取得平衡 |
| 共享 Softmax | 将历史状态读取信息和当前块内信息放在同一个 Softmax 中处理 | 协调不同来源的信息 |
| 块大小校准 | 引入可学习的校准机制 | 适应块大小带来的建模差异 |
| 右侧上下文卷积分支 | 利用当前块后续位置的信息 | 增强块内双向建模 |
| Mask 训练 | 随机遮蔽部分 Token，再学习恢复 | 训练非严格从左到右的生成能力 |
| 自回归模型适配 | 基于 Qwen3.6-35B-A3B 进行扩散适配 | 减少从零预训练的成本 |

需要特别区分：分块扩散并不意味着整篇输出可以同时完成并任意修改。 Clover 的当前设计仍然按照 Block 顺序推进，双向建模主要发生在块内部。

### 八、当前仍未解决的问题与限制
**1. 全局建模受限： 当前 Clover 的双向信息交互主要发生在 Block 内，尚未实现完整长序列的全局联合规划。**
**2. 端到端提速证据不充分： 团队尚未完成严格系统性的任务总耗时比较，Token 速度优势能否稳定转化为实际生产力仍需验证。**
**3. 高难度通用能力存在短板： HLE 等测试相对薄弱，部分传统任务成绩略低于 Qwen。**
**4. 训练成本存在额外投入： 扩散适配虽然复用了预训练能力，但扩散训练仍可能需要更多轮次。**
**5. 软硬件基础设施尚不成熟： Serving 框架、GPU 调度、推理算子、内存管理等需要继续优化。**
**6. 真正的生态竞争尚未完成： 扩散模型需要证明自己能在实际应用中稳定部署，并获得开发者和客户认可。**

## 值得记住的点 / 行动建议

### 1. 评价 AI 模型时，先区分生成吞吐量、任务效率和任务成功率
不要只根据 Tokens/s、单项 Benchmark 分数或模型宣传中的提速倍数判断 AI 是否真正好用。至少应分别观察模型生成速度、工具调用耗时、完成整个工作流的总时间、任务成功率、错误修复次数以及单次成功任务的成本。例如，Clover 在某些配置下生成速度达到自回归模型的 5—10 倍，但浏览器任务中表现出的端到端耗时差异约为 2.31 倍，两者属于不同维度。对企业采购或开发者选型来说，最有意义的指标通常是“在可接受质量下，完成一次实际任务需要多少时间和成本”。

### 2. 开发 Agent 时，要把执行框架视为性能的一部分，而不是只依赖模型升级
Agent 的效率不仅取决于模型参数和推理能力，还取决于 Harness 如何组织任务、调度工具、管理上下文、处理失败和安排重试。在具体开发中，可以先分析任务的依赖关系，将相互独立的操作识别出来，再评估是否能够安全并行执行；对必须等待结果才能继续的步骤，则保留必要的顺序控制。同时，应记录每次工具调用、等待反馈和模型推理的耗时，识别真正的瓶颈。这样即使不更换基础模型，也可能通过工作流设计改善效率。

### 3. 对多问题、多约束任务，优先考虑统一判断和一致性校验
合同审查、审批流程、风控规则、财务核对和结构化信息分析中，经常会出现多个结论必须同时满足逻辑约束的情况。对于这样的任务，不宜简单地把问题拆散后彼此独立处理，而应该明确共享条件、前置约束和相互依赖关系，再集中生成或统一校验答案。例如，一份合同中如果约定“只有按时通知才能保留保证金”，系统就不能一方面认定通知超期，另一方面却允许保留保证金。可以通过联合生成、规则校验或结果交叉检查提高一致性。需要注意的是，联合决策并不是自动保证正确，在法律、财务等重要场景中仍然需要依据原始文件和适用规则进行复核。

### 4. 根据任务复杂度选择推理深度，不要把 Thinking 越长等同于效果越好
如果任务是简单分类、常规状态判断、固定格式输出或实时环境响应，可以优先评估短推理、低延迟模型是否足够准确。如果任务涉及复杂数学证明、多步骤软件工程、重大财务决策或相互依赖的长期规划，则可能需要更深入的推理、工具验证与多轮检查。更合理的设计是按照任务风险和难度分配计算资源，而不是让每个请求都采用最高成本的推理模式。对于机器人和实时控制系统，还需要设置超时、异常处理和安全机制，不能只追求快速生成结果。

### 5. 对端侧 AI 项目，要以完整硬件与部署配置评估经济可行性
文章中的 Clover 实验说明，通过 INT4 量化、BF16 模块保留、GPU–CPU 混合专家推理及专家放置优化，可以在 16GB GPU 显存等条件下实现一定吞吐量。但实际部署前，应同时测试模型加载时间、内存使用、长上下文性能、功耗、设备温度、准确率以及多任务并发稳定性。还需要区分本地部署的固定硬件成本与云端 API 的持续调用成本，计算预期调用量对应的总成本。对于 AI PC、车载和本地办公助手，这种评估尤其重要，因为设备可用算力、延迟要求和隐私需求都可能明显影响部署决策。

### 6. 研究新架构时，可以借鉴“复用已有能力，再进行范式适配”的思路
Clover 选择复用 Qwen3.6-35B-A3B 的预训练能力，说明探索新的模型生成范式不一定要从最昂贵的零基础预训练开始。对于科研团队或算力有限的创业公司，可以优先研究如何借助已有模型权重、公开训练数据、成熟推理框架和开源社区，减少重复投入。真正需要集中资源解决的，是新技术相对于既有方案的核心差异和性能瓶颈。同时，必须开展消融实验和同条件对比，区分哪些能力继承自原始模型，哪些能力真正来自新的训练方式或架构改造。

### 7. 判断 AI 技术创业机会时，寻找有真实需求且优势可验证的细分场景
扩散智能没有把“全面超越最强前沿模型”作为短期目标，而是优先探索速度敏感、成本敏感和硬件受限的应用，这是值得借鉴的技术商业化路径。创业团队可以先寻找愿意为低延迟、低推理成本、本地运行或高频任务自动化付费的客户，再围绕具体任务验证性能优势。比如，一个本地 AI 编程助手或车载决策系统，只要能在客户关心的任务上稳定提供更合适的性能、成本和响应体验，就未必需要在所有综合排行榜中排名第一。但要形成可持续业务，还必须解决部署、支持、可靠性、维护和客户迁移成本等问题。

### 8. 关注扩散模型未来的发展，应重点跟踪可验证的技术与商业里程碑
对于希望长期跟踪 DiffuSpace、Clover 或扩散语言模型路线的人，可以建立一个观察清单，重点关注以下变化：
- 架构能力： Block 是否继续扩大，是否出现真正跨块乃至全序列的双向规划与修改能力。
- Agent 性能： 是否发布更严格、可复现的端到端任务效率对比，并同时报告成功率和总体成本。
- 推理生态： SGLang、llama.cpp 等框架是否进一步优化扩散模型推理，相关算子和硬件利用率是否提高。
- 通用能力： HLE、数学、代码与其他非 Agent 任务的性能短板是否缩小。
- 应用落地： AI PC、车载、机器人和联合决策是否出现可重复验证的真实部署案例。
- 商业化： 是否有客户因为成本、延迟或任务表现优势，实际从自回归模型迁移到扩散模型。

其中最有说服力的证据不是某次发布会展示了新的吞吐量纪录，而是在相同任务、相同硬件预算和可接受的准确率约束下，扩散模型能够长期、稳定地提供更优的使用价值。

## 我的点评
这篇文章最值得关注的地方，是它将扩散语言模型的讨论从单纯的 Token 生成加速，推进到了 Agent 执行效率、关联决策和商业可行性三个更实际的层面，技术逻辑比较完整。Clover 在软件工程评测、工具调用和联合决策中的表现，说明扩散生成范式确实具有值得继续研究的潜力，特别是在多个输出相互约束以及低延迟要求较高的任务中。不过，需要对性能结论保留适当谨慎：文章的大部分实验来自团队公布的技术报告，不同模型的训练基础、硬件、评测环境和执行框架都可能影响结果，尤其不能把部分配置下 5—10 倍的 Token 生成优势理解为实际生产力必然提高同样倍数。受访者所提出的“未来一到两年部分替代自回归模型”，更适合被理解为一种具有条件的行业预测，而不是已经能够确定实现的技术趋势。对普通开发者、研究者或企业来说，最有价值的启发是：不要只关注模型采用什么架构，而要关注这种架构能否在具体任务中以更低成本、更高可靠性和更短时间创造实际价值。

## 📝 完整文字稿

AI 已经开始替人写代码、操作软件、执行复杂任务，但支撑它们的主流大语言模型，仍然在一个 Token 接一个 Token 地生成答案。

扩散语言模型正在尝试另一种路径。它可以并行生成多个 Token，在生成过程中反复调整内容，而不必严格遵循从左到右的顺序。过去，这条路线最大的吸引力是速度；如今，随着 Agent 成为大模型竞争的重点，扩散模型也开始尝试证明自己能够完成更复杂的任务。

前不久，扩散智能（DiffuSpace）开源了 Clover-35B-A3B-Preview（下文简称 Clover），总参数量 350 亿，激活参数约 30 亿。11 月 19 日，团队正式发布技术报告，并同步开放 SFT 代码，进一步披露模型的架构设计、训练方法与评测结果。

技术报告链接：https://arxiv.org/abs/2611.24636

开放代码链接：https://github.com/DiffuSpace/Clover-35B-A3B-Preview/tree/main/sft

在统一评测协议下，Clover 在技术报告所列对比模型中的七项 Agent 指标上均取得最高分，覆盖工具使用、专业工作和智能体编程。其中，SWE-bench Verified 达到 73.6，Terminal-Bench 2.1 达到 51.7。速度方面，在部分测试配置下，Clover 的 Token 生成速度达到同级别自回归模型的 5—10 倍。

但从生成 Token 到完成任务，还涉及工具调用、环境反馈、测试与代码修复等环节。更快的生成能够缩短其中一部分等待时间，而最终能够转化为多少实际生产力，还取决于任务本身和执行流程等多个方面。

“从生成提速到完整任务效率提高，团队还在持续验证。”扩散智能联合创始人、首席科学家龚珊三在接受 InfoQ 专访时坦言。为了让扩散模型能够高效处理长上下文和复杂任务，团队对底层架构进行了较大调整，采用分块扩散来减少重复计算，在当前生成块内实现双向信息交互。在此基础上如何进一步拓展双向建模的范围、发挥扩散模型的全局规划潜力，仍是团队接下来研究的重点。

龚珊三对这条技术路线保持着坚定的信心。她仍然坚持此前的判断：未来一到两年，扩散语言模型有机会在部分具体场景中替代同规模的自回归模型。从 2022 年少数研究者的早期探索，到如今进入 Agent 编程和工具使用的竞争，扩散模型究竟已经跨过了哪些门槛，又有哪些方向值得继续探索？

### 扩散模型想跑得更快，为什么反而要把文本切成小块？

2022 年，龚珊三开始探索扩散语言模型时，自回归生成已经是大语言模型领域热门技术路线。她参与的 DiffuSeq 是较早将扩散机制用于文本条件生成的研究之一。团队当时就意识到，这种生成方式可能带来更高的并行效率，也有望通过双向信息交互改善推理与全局规划能力。四年后回头看，龚珊三觉得，这条技术路线后来的发展，大部分都超出了最初的预期。

首先是 Scaling。2023 年，团队开始尝试扩大模型规模，但当时几乎没有成熟经验可以借鉴。可以探索的技术路径太多了，究竟哪一种有效、哪一种行不通，只能一个个试。团队最初尝试在连续空间中进行扩散建模，却发现学习复杂度很高，模型很难训练成功；后来转向离散空间，经过多轮实验才逐渐找到可行的路线。

比试错更难熬的，是不知道这条路究竟能不能走通。当时研究扩散语言模型的人很少，既不知道其他人是否也在做类似研究，也不知道这个方向究竟能走多远，这种未知对于研究人员来说本身就是一种挑战。从最初只有几个人探索，到后来形成研究小组，再到如今 Google、Inception、蚂蚁等越来越多团队加入，原本只有少数人探索的冷门方向，逐渐有了更多同行者，这让龚珊三更加确信，扩散语言模型有值得长期投入的发展潜力。

模型规模扩大后，一个问题变得越来越突出：如何让扩散模型在处理长上下文时，仍然保持高效生成？早期方案需要反复处理较大范围的序列，随着上下文增长，重复计算的成本也随之增加。

Clover 选择用分块扩散（Block Diffusion）缓解这一矛盾。模型将生成过程划分为多个 Block，每个块内部仍然通过扩散方式并行生成 Token，而已经完成的内容则可以通过 KV Cache 复用，避免反复计算历史上下文。这样既保留了块内并行生成的优势，也降低了长序列生成的开销。

但分块之后，模型必须同时处理两类信息：此前已经生成的历史内容，以及当前 Block 内需要相互参照的 Token。为此，Clover 对 Gated DeltaNet（GDN）进行了双向改造，形成 BD-GDN。相比主要面向从左到右生成的原有设计，BD-GDN 既要高效保存和读取历史信息，也要支持当前块内部的双向信息交互。

根据扩散智能的技术报告，Clover 采用混合架构，每四层为一组，包括三层 BD-GDN–dMoE 和一层 Full Attention–dMoE，重复十次。在具体实现上，团队将历史状态读取的信息与当前块内部的信息放在同一个 Softmax 中处理，并引入可学习的块大小校准机制；同时增加独立的右侧上下文卷积分支，让模型在处理当前位置时，也能够利用当前块内后续位置的信息。这些改造都是为了兼顾历史信息复用与块内双向建模。

Clover 采用分块扩散，在降低长序列生成开销的同时，利用块内双向信息交互，在 Agent 编程和工具使用等任务中取得了有竞争力的表现。而这还不是扩散模型双向建模能力的全部：当前模型仍按 Block 逐步向后生成，双向生成与修改主要发生在块内。

“真正的全局规划，就是从头到尾的全局规划，现在其实没有完全实现。”在龚珊三看来，尚未充分释放全局建模潜力的 Clover，已经展现出有竞争力的任务表现，也让团队更有信心继续探索。

扩大生成块是其中一个方向。技术报告显示，在完整的 64 条 Agent 历史轨迹前缀回放测试中，Clover 将块大小从 8 增至 16 后，每轮提交的 Token 数与实际吞吐量均有所提高。在此基础上，团队还将进一步研究更大的生成块对推理质量和任务表现的影响。

### 模型跑得快，Agent 完成任务也能同比提速吗？

对于希望进入实际应用的扩散语言模型来说，生成速度只是第一道门槛。如今，Agent 需要直接读取文件、调用工具、运行程序，并根据执行结果不断调整行动。模型能否完成这些复杂任务，已经和生成效率一样重要。Clover 35B 因此将 Agent 编程和工具使用作为重点方向。

在扩散智能公布的评测中，Clover 35B 在 SWE-bench Verified、Terminal-Bench 2.1 和 τ³ Overall 上分别取得 73.6、51.7 和 65.3 的成绩，在所列同规模自回归模型及其他扩散模型中领先。其中，SWE-bench Verified 包含 500 个经过人工核验的真实 GitHub 软件工程问题，要求模型理解代码仓库并完成修复；Terminal-Bench 2.1 则需要模型在终端环境中实际执行任务。

不过，Agent 的最终表现不仅取决于模型，还受到任务执行框架（Harness）、工具配置和上下文管理等因素影响。Clover 在公开评测中采用了与对照模型相同的 Harness，以尽可能排除执行系统差异带来的影响。但在实际应用中，扩散智能也在开发专门适配扩散模型的 Harness，希望进一步发挥并行生成的优势。

现有 Agent 框架大多围绕自回归模型设计，通常按照“生成内容—调用工具—等待反馈—继续生成”的方式工作。扩散模型一次可以生成多个 Token，为模型生成与工具执行的协同提供了新的空间。例如，对于没有依赖关系的工具调用，系统可以尝试并行执行，而不必完全按照顺序等待。龚珊三认为，通过模型与 Harness 的协同设计，还有机会进一步提升 Agent 的整体执行效率。

部分实际任务已经展现出这种潜力。在一项通过浏览器创建私有项目并邀请成员的测试中，Clover 用 13 个步骤、169.9 秒完成任务，对照的 Qwen3.6 Flash 用了 21 个步骤、392.3 秒。另一组 WindTunnel 测试覆盖 49 项任务，Clover 的执行耗时中位数为 1.52 秒，而 Jev 与 Mercury 2.5 组合为 3.21 秒。除了模型响应速度，任务执行步骤和工具调用过程中的时间开销，也开始成为扩散模型展示效率优势的地方。

但在更复杂的 AI 编程任务中，生成代码只是整个工作流的一部分。模型还需要运行测试、处理报错、修改代码，有时甚至需要多轮尝试。如果一次生成虽然很快，却需要反复修复错误，最终任务耗时未必会同比例缩短。

模型生成 Token 的速度快了几倍，Agent 完成整项任务究竟能快多少？龚珊三认为，这是一个复杂的工程问题。团队尚未对端到端任务耗时进行严格的系统性比较，但按照目前的使用体验，她估计模型速度的提升大致可以以 1:1 的比例转化为任务效率的提升。未来如果让模型生成与 Harness 中的工具调用等环节更好地协同工作，还有机会实现“1+1 大于 2”的效果，这也是团队正在探索的方向。

除了速度，扩散模型在代码和结构化数据生成中的一致性也具有潜在优势。例如，代码中前后引用的变量需要保持一致，JSON 的括号和字段必须符合严格的格式约束。扩散模型能够在一个生成块内部同时利用前后位置的信息，龚珊三认为，这有助于提高生成内容的前后一致性。

不过，Clover 也并非在所有评测中领先。在 Humanity's Last Exam（HLE）等高难度测试中，Clover 的表现相对较弱，部分传统任务成绩也略低于 Qwen。龚珊三将其主要归因于相关训练数据不足。

值得注意的是，扩散模型并不需要一套完全不同的训练数据。团队目前使用的数据与自回归模型基本相同，区别主要在于数据处理和学习方式：训练时随机遮蔽（Mask）部分 Token，再让模型学习恢复这些内容。相同的数据经过不同的处理与学习过程，模型最终掌握的能力也可能有所不同。

### AI 为什么开始重新学习“凭直觉做决定”

过去几年，大模型行业不断追求更强的推理能力，试图用更长的思维链、更多测试时计算换取更准确的答案。但最近，另一种思路开始受到关注：AI 是否真的需要每次都思考那么久？

Jev 等决策模型的出现，让行业重新关注类似人类直觉的 System 1 快速决策能力。在龚珊三看来，尽管 Jev 本身存在一些技术争议，但它重新唤起了人们对快速决策价值的重视。对于以并行生成为重要优势的扩散语言模型来说，这同样是一个利好方向。扩散智能也在推出 Clover 时，同步展示了联合决策模型的研究进展，这个场景能够进一步发挥扩散模型在速度和双向信息交互方面的优势。

龚珊三用打羽毛球作比喻：运动员接球时，不会先计算球的轨迹、分析所有可能的动作，再决定如何挥拍。很多判断依靠经验形成的快速反应，在极短时间内完成。AI 进入真实环境后也会遇到类似情况，例如机器人判断道路是否安全、物体能否抓取，或者下一步应该往哪个方向移动。如果每次都要经过漫长的 Thinking 过程，可能根本来不及作出反应。

不过，快速作出单个判断只是第一步。当多个决策之间存在关联，模型能否在保证响应速度的同时，兼顾不同判断之间的约束关系？

扩散智能在官方技术博客中展示了一项合同判断任务：模型需要根据同一份合同，回答通知是否及时、保证金是否应该保留等五个相互关联的问题。这些问题之间存在逻辑约束，例如，只有通知及时才允许保留保证金。如果逐题独立判断，模型就可能一边认定通知已经超时，另一边却认为保证金可以保留，导致结论自相矛盾。扩散智能的联合决策模型则利用双向生成机制，让多个答案在同一次生成过程中相互参照。在这项测试中，联合模式五题全部答对，独立模式答对四题，而 Jev 只答对两题。

类似的联合决策方式也适用于棋类、数独等任务：不同位置的选择相互制约，模型需要同时考虑多个判断之间的约束关系，而不能只关注单步决策是否正确。

更大范围的内部测试也呈现出类似差异。根据最新技术报告，在包含 500 组、共 2,420 道关联问题的验证集中，同一决策模型采用联合预测时，单题准确率为 93.88%，整组全对率为 77.0%；独立逐题预测时，两项成绩分别为 90.37% 和 65.4%。联合预测使整组全对率提高了 11.6 个百分点，支持了这种方式在关联判断任务中的应用价值。

相比需要生成很长文本的 Agent 任务，这类决策通常具有较短、相对固定的输出范围，扩散模型可以利用双向信息交互，在一次生成中统筹考虑多个判断之间的关系。这也与 Clover 当前面临的全局规划限制形成了对照：长序列生成仍然受到 Block Diffusion 的限制，而联合决策模型能够在较短的输出范围内进行完整的双向建模。

快速决策之外，扩散智能也在探索更高效的推理方式，希望进一步发挥扩散架构的并行优势，在提升响应速度的同时保持推理质量。对用户而言，模型内部采用怎样的推理机制并不重要，真正重要的是能否在保证结果质量的同时，更快地完成思考与任务。

对于扩散智能来说，这种探索也开始延伸到具身智能等更广泛的场景。龚珊三透露，团队已经开始尝试机器人部署，并开展相关研究，多模态也将成为下一阶段的重要方向。从 Agent 编程到联合决策，再到需要实时感知和行动的机器人，扩散智能正在寻找扩散生成范式更多的应用空间。

### 坚持做基础模型公司，但扩散智能还要跨过几道坎

随着 Clover 开始面向 Agent 编程和工具使用，扩散智能也在开发自己的 Agent Harness 和编程客户端。这似乎意味着，一家专注扩散语言模型研究的公司，正在向应用层延伸。但龚珊三的态度很明确：扩散智能仍然是一家基础模型公司。

“纯做产品的公司，其实很容易被基模吞噬。”在她看来，个人助手、编程助手等 AI 产品可以通过交互体验和特定功能形成差异，但随着基础模型能力不断增强，这些功能也可能逐渐被模型厂商吸收。相比直接与成熟的 AI Coding 产品争夺用户，扩散智能更希望把资源投入底层模型。开发 Harness 和客户端，主要是为了适配扩散模型的并行生成特性，展示其不同于自回归模型的使用体验，而非转向 C 端产品竞争。

在基础模型研发中，如何更有效地利用训练算力，同样是重要课题。Clover-35B-A3B-Preview 选择从已有自回归模型出发，复用 Qwen3.6-35B-A3B 在预训练阶段积累的能力，再进行扩散适配。这条路线减少了从零训练的投入，让团队能够更集中力量探索扩散架构与并行生成能力。

这种方式已经大幅降低了训练成本，但扩散模型仍可能需要更多训练轮次。龚珊三认为，以训练阶段的额外投入换取推理阶段更高的效率，是一笔值得考虑的账：模型训练完成后会被反复调用，推理端节省的时间和计算成本可能在长期使用中不断累积。

更现实的挑战是，今天的大模型软硬件生态主要围绕自回归架构发展，现有推理算子、Serving 框架乃至 GPU 的计算能力与显存配置，都未必最适合扩散模型。许多基础设施仍需要团队自己开发和优化。对于一家计划继续扩大模型规模的创业公司来说，算法突破之外，还有大量基础设施工作需要补齐。

这也是扩散智能持续投入开源生态的原因。Clover 已开放模型权重和相关代码，并支持 SGLang、llama.cpp 等推理框架。团队希望吸引更多开发者参与模型部署、算子优化和应用探索，逐渐完善扩散语言模型尚不成熟的工程生态。

尽管面临的挑战不少，龚珊三仍然坚持此前一个颇为大胆的判断：未来一到两年，扩散模型有机会替代自回归模型。不过，她所说的“替代”首先发生在部分具体应用场景，而非短期内全面取代 OpenAI、Anthropic 等公司的前沿模型。后者在模型规模、算力和工程生态上的优势，仍然需要时间追赶。

更现实的机会，可能出现在端侧部署等对速度和成本敏感的场景。扩散智能正在探索 AI PC、车载等应用，与持续调用云端 API 相比，当设备已经具备相应计算能力时，本地部署可以减少长期调用费用，并提供更及时的响应。在技术报告中，团队使用配备 16GB 显存的 RTX 5070 Ti、AMD Ryzen 7 9700X CPU 和 64GB 主机内存，通过 SGLang 与 KTransformers 进行 GPU–CPU 混合专家推理。Clover 的路由专家权重采用 INT4 量化，主要非专家模块保留 BF16。在完整 MATH-500 测试中，优化专家放置后，top-8 验证配置达到 97.52 Tokens/s 的解码吞吐量，人工复核准确率为 97.6%；进一步采用 top-6 验证时，吞吐量提升至 106.25 Tokens/s，准确率为 96.0%。

对于扩散智能而言，这意味着不必一开始就与参数规模最大、算力投入最高的前沿模型正面竞争，而是可以在具体场景中，以同等规模下的能力、速度和成本优势争取替代机会。

2027 年，扩散智能仍计划将绝大部分资源投入基础模型训练，Scaling 和多模态是两个主要方向，Agent 产品与开发者生态则继续围绕模型能力展开。四年前，扩散语言模型还是少数研究者探索的冷门路线；如今，Clover 已经开始在复杂 Agent 任务中与自回归模型竞争。但算法上的突破还需要算力、工程生态与实际应用共同支撑，才能真正形成市场竞争力。

对于扩散模型来说，真正重要的突破，或许不是证明它能够以不同的方式生成 Token，而是让这种不同，最终成为用户愿意选择它的理由。
