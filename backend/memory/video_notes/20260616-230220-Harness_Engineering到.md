## 🤖 AI 分析

## 一句话概括

这个视频在解释 AI Agent 领域的新概念 **Harness Engineering**：未来 Agent 的竞争不只是模型本身有多强，而是谁更能通过外部系统设计，把一个聪明但不稳定的大模型“驾驭”成可靠、可控、能持续交付结果的 Agent。

## 背景与主题

最近 AI Agent 圈里出现了一个新热词：**Harness Engineering**。很多人第一次听到它，会误以为这只是给 Agent 增加规则、限制、提示词或安全边界，但作者认为这种理解太浅。视频通过一个 coding agent 在 **Terminal-Bench 排行榜**中从 **30 名开外提升到前 5** 的案例说明：真正决定 Agent 表现的，越来越不是底层模型是否更强，而是模型外层的系统设计是否成熟。作者站在 AI Agent 系统设计和技术转型的角度，解释 Harness Engineering 与 Context Engineering 的区别，以及优秀 Agent 背后的系统层次。

## 核心观点

### 1. Agent 的竞争正在从“谁的模型更强”转向“谁更会驾驭模型”

作者开头就提出一个重要判断：过去一年表现最好的 Agent 系统，真正拉开差距的地方，越来越不只是底层模型本身，而是模型外面的那层系统。也就是说，模型当然重要，但模型只是提供能力的基础，能不能把能力稳定转化成结果，取决于外部系统如何组织信息、约束行为、验证结果和管理运行过程。作者用一句话概括为：**“Agent 的竞争正在从谁的模型更强，逐渐转向谁更会驾驭模型。”**这意味着未来做 Agent，不只是会调 API、写 prompt、接工具，而是要像工程系统一样设计一整套控制、反馈、验证和演进机制。Harness Engineering 正是在这个背景下出现的概念，它研究的是如何把模型从“聪明但不稳定”变成“可靠、可控、能交付”的 Agent。

### 2. 一个 coding agent 的案例说明：不换模型，也能带来接近跨代级的性能提升

视频中最关键的案例是：有团队开发的一个 **coding agent**，在 **Terminal-Bench 排行榜**上的名次从 **30 名开外一路提升到前 5**。最值得注意的是，这个提升并不是因为他们升级了模型，也不是因为更换了底层模型；整个优化过程中，**底层模型始终保持不变**。真正发生变化的是模型外部的系统设计，例如 **prompt 设计、动态 tool 调用策略、middleware 中间件机制** 等。作者认为，这种结果相当于带来了“接近跨代级的性能提升”，说明 Agent 的能力不只是由模型参数决定，还高度依赖外部工程结构。这个案例背后的逻辑是：模型能力只是一个潜在上限，而 Harness 决定 Agent 能不能接近这个上限。

### 3. Harness Engineering 的核心问题：如何让模型能力稳定转化为结果

作者强调，Harness 的作用从来不是单纯“限制模型”，而是让模型强大的能力可以稳定落地。英文里的 **Harness** 原意很形象，指的是驾驭马匹时使用的马具系统，包括**缰绳、马鞍以及各种控制装置**。如果映射到 AI 世界，模型就像一匹速度极快、力量巨大的马，它有能力、有冲劲，但它自己并不知道应该去哪里。人类负责设定目标，而 Harness 负责把目标转化为行动路径、工具使用、执行步骤和反馈机制。因此，Harness Engineering 本质上回答的是：怎样把一个强大但不稳定的模型，变成一个能按照目标持续行动并交付结果的系统。

### 4. 模型决定智能上限，系统设计决定 Agent 能否接近上限

视频中有一个非常重要的判断：**“模型能力只是 Agent 的上限，而系统设计决定了 Agent 能否接近这个上限。”**这句话可以理解为，模型越强，理论上 Agent 可以完成的任务越复杂，但如果没有好的外部系统，模型很可能在执行中迷失重点、调用错误工具、陷入循环、遗漏验证，最后结果仍然不稳定。比如同一个模型，在一个简单 prompt 驱动的 Agent 中可能表现平平，但在一个拥有检索、校验、测试、中间件、权限控制和任务审查机制的 Agent 中，表现可能大幅提升。作者用 coding agent 排名跃升的案例证明：外部系统设计的改进，有时可以带来类似“换了一代模型”的效果。这也解释了为什么 Agent 工程越来越像系统工程，而不只是 prompt 工程。

### 5. Harness Engineering 与 Context Engineering 关注点不同：一个管输入，一个管运行

视频专门区分了 **Harness Engineering** 和 **Context Engineering**。很多人熟悉 Context Engineering，它解决的是 Agent 应该获得哪些信息，也就是如何组织上下文、检索材料、筛选知识、控制输入质量。Harness Engineering 解决的是另一个问题：Agent 应该如何行动，以及系统如何保证行动正确。作者用一句很清晰的话总结：**“前者关注输入，后者关注运行过程；一个负责喂养智能，一个负责管理智能。”**这意味着 Context Engineering 更像是在给模型提供高质量信息，而 Harness Engineering 更像是在给 Agent 建立执行规则、反馈机制和质量控制体系，两者共同决定 Agent 的最终表现。

### 6. 优秀 Harness 的第一层：信息组织不是越多越好，而是要按需检索

作者指出，过去很多人的直觉是：给 Agent 的信息越多越好，最好一次性把整个知识库、全部文档、所有背景都塞进上下文。但大量实践发现，事实恰恰相反：当上下文过长时，模型会开始**迷失重点**，注意力被噪声稀释，甚至可能忽略真正关键的信息。因此，先进团队越来越倾向于构建一种 **按需检索机制**。Agent 不需要一次性读完整个知识库，它只需要知道“去哪里找答案”。作者用了一个很形象的比喻：从“给它一本百科全书”变成“给它一张地图”，也就是让 Agent 具备寻找信息的路径，而不是被过量信息淹没。

### 7. 优秀 Harness 的第二层：约束不能只写在 prompt 里，而要迁移到系统层执行

视频指出，prompt 里的规则本质上只是“建议”，不是强制执行。即使你在 prompt 里写上 **20 条注意事项**，模型仍然可能忽略其中一部分，因为大模型不是传统程序，它不会像代码一样严格执行每一条自然语言规则。因此，越来越多团队开始把约束从 prompt 中迁移出来，用系统机制直接执行，比如 **自动测试、Schema 校验、Linter、权限控制** 等。这些规则不依赖模型是否“理解”或“记住”，而是由外部系统强制执行。作者认为，这样获得的稳定性远高于语言层面的约束，因为系统层约束能减少模型偶发失误带来的风险。

### 8. 优秀 Harness 的第三层：验证机制解决 Agent“不知道自己做错了”的问题

作者认为，Agent 最大的问题之一不是不会做，而是**不知道自己做错了**。典型情况包括：陷入无效循环、反复修改同一个文件、过早结束任务、没有验证结果就直接提交。这些问题在 coding agent、自动化办公 Agent、多步骤任务 Agent 中都很常见，因为模型往往会产生“任务已经完成”的错觉。优秀系统通常会在关键节点增加检查器：有些检查器负责发现异常循环，有些负责强制执行测试，还有些会在任务结束前进行二次审查。作者把这称为在 Agent 外面增加一层 **质量控制体系**，让 Agent 不只是会执行，还能被检查、被纠偏、被约束。

### 9. 优秀 Harness 还包括上下文隔离、持续治理和可演进性

视频后半部分继续拆解优秀 Harness 的其他层面。首先是 **上下文隔离**：当多个 Agent 同时工作时，真正有效的方法往往不是简单分成“前端 Agent、后端 Agent、测试 Agent”，而是让每个 Agent 只接触自己需要的信息，看不到其他 Agent 的中间过程，这样能避免上下文膨胀，也能减少噪声传播。其次是 **持续治理**：Agent 长期运行后，系统会逐渐产生“脏数据”或信息腐化，文档会过期，知识库会失真，代码与文档会出现偏差，所以有团队开始用 Agent 维护 Agent，例如自动扫描文档、发现不一致内容、生成修复 PR。最后是 **可演进性**：模型能力进步很快，今天必须依赖的复杂流程，明天可能就不再必要，因此优秀 Harness 不应该是庞大僵化的框架，而应该像乐高积木一样，每个模块都能单独增加、替换或删除。

### 10. 未来 Agent 的胜负，可能取决于谁拥有更成熟的 Harness

作者最后用汽车比喻进一步解释 Harness 的价值：决定一辆车能否到达终点的，不只是发动机马力，还包括方向盘、刹车、导航和整套控制系统。模型就像发动机，它提供动力和智能；但如果没有方向盘，车不知道往哪走；没有刹车，车无法安全停止；没有导航，车可能走错路线；没有控制系统，车无法稳定运行。因此，Harness 才是真正让模型成为“可用 Agent”的关键部分。作者认为，未来 Agent 的竞争未必是谁拥有最强模型，而是谁拥有最成熟的 Harness。这个判断也暗示了一个转行机会：未来懂模型的人很多，但懂得构建 Agent 外部控制系统、验证机制和长期治理体系的人，会越来越重要。

## 值得记住的点 / 行动建议

### 1. 不要只盯着换模型，先检查 Agent 外部系统是否设计得足够好

视频最有价值的提醒是：当 Agent 表现不好时，不要第一反应就是“模型不够强”或“该换更贵的模型”。Terminal-Bench 的案例说明，即使底层模型不变，通过 prompt 设计、工具调用策略、中间件机制等外部系统优化，也可能实现从 30 名开外到前 5 的跃升。实际做 Agent 项目时，应该先拆解问题出在哪里：是信息太杂、工具调用不稳定、缺少验证、权限控制不足，还是任务结束条件设计得不好。模型升级当然有价值，但系统工程优化往往更便宜、更可控，也更能积累长期壁垒。真正成熟的团队，不会只问“用哪个模型”，还会问“怎样驾驭这个模型”。

### 2. 给 Agent 信息时，不要追求“越多越好”，而要设计按需检索

很多人做 Agent 时会把大量文档、规则、背景信息一次性塞进上下文，以为这样模型知道得越多就越聪明。但视频提醒，过长上下文会让模型迷失重点，甚至让真正关键的信息被噪声淹没。因此，更好的做法是建立按需检索机制，让 Agent 知道在哪里找答案，而不是一次性把答案、背景、历史记录全部塞给它。比如在企业知识库场景中，可以让 Agent 先判断任务类型，再检索相关文档、代码片段、接口说明或历史案例。这样相当于给 Agent 一张地图，而不是把一本百科全书砸给它。

### 3. 不要把所有规则都写进 prompt，要把关键约束做成系统机制

Prompt 可以引导模型，但不能保证模型永远遵守。视频提到，即使写上 20 条注意事项，模型依然可能忽略其中一部分，这说明自然语言约束的可靠性有限。真正重要的规则，应该尽量迁移到系统层执行，例如自动测试、Schema 校验、Linter、权限控制、输出格式验证、危险操作拦截等。比如代码 Agent 不应该只在 prompt 里写“提交前请运行测试”，而应该由系统强制执行测试，测试不通过就不允许提交。这样可以把“希望模型自觉遵守”变成“系统强制保证”，稳定性会高很多。

### 4. 给 Agent 增加验证机制，让它在关键节点被检查和纠偏

Agent 常常不是不会做任务，而是不知道自己什么时候做错了。它可能在一个错误方向上反复尝试，也可能修改同一个文件很多次却没有推进，还可能没验证结果就宣布完成。因此，一个可靠的 Harness 应该在关键节点加检查器，比如检测循环、强制测试、检查输出格式、二次审查最终结果。尤其在 coding agent 中，测试、lint、类型检查、单元测试、集成测试都应该成为系统流程的一部分，而不是可有可无的建议。验证机制的目标不是降低模型自由度，而是让模型的自由探索有反馈、有边界、有质量控制。

### 5. 多 Agent 协作时，重点不是起更多角色名，而是控制信息流

很多人做多 Agent 系统时喜欢按岗位命名，比如前端 Agent、后端 Agent、测试 Agent、产品 Agent。但视频指出，真正有效的往往不是角色划分本身，而是信息隔离。每个 Agent 应该只看到自己完成任务所需的信息，而不是共享所有上下文、所有中间过程和所有历史记录。这样可以避免上下文膨胀，也能减少一个 Agent 的错误推理或噪声传播给其他 Agent。可以把每个 Agent 理解成一个独立沙箱：它有自己的任务、输入、工具和输出边界，通过明确接口协作，而不是在一个巨大上下文里互相干扰。

### 6. 把 Agent 系统当成长期运行的工程系统来治理

视频提到，Agent 长期运行后会出现文档过期、知识库失真、代码与文档偏差等问题。这意味着 Agent 不是上线后就一劳永逸，它需要持续治理。可以让 Agent 反过来维护 Agent，例如自动扫描文档，发现不一致内容，生成修复 PR，提示知识库中可能已经过期的部分。对于企业项目来说，这一点尤其重要，因为知识库和代码库每天都在变化，如果不治理，Agent 的依据就会越来越脏。成熟的 Harness 不只是让 Agent 完成一次任务，而是让整个系统在长期运行中保持健康。

### 7. 设计 Harness 时要模块化，避免做成僵化的大框架

作者提醒，模型能力提升速度很快，今天必不可少的复杂流程，明天可能因为模型升级而完全不必要。因此，Harness 不应该被设计成一套庞大、固定、难以拆改的框架。更好的方式是像乐高积木一样模块化：检索模块、工具调用模块、权限模块、验证模块、审查模块、日志模块、回滚模块都可以单独增加、替换或删除。这样当模型变强、任务变化或业务场景变化时，系统可以同步进化，而不是被旧架构拖住。长期看，Harness 的可演进性会成为 Agent 工程能力的重要标志。

### 8. 转行或学习 AI Agent 时，要从“调模型”升级到“建系统”

视频标题里带有“转行”，其实也暗示了一个学习方向：未来只会写 prompt 或简单调用大模型 API，竞争力可能不够。真正有价值的能力是理解 Agent 的完整运行系统，包括上下文管理、工具调用、权限控制、验证机制、多 Agent 协作、持续治理和模块化架构。学习者可以从一个简单 Agent 开始，不只是让它回答问题，而是给它增加检索、工具、测试、错误恢复和结果审查。这样才能理解 Harness Engineering 的本质：不是给模型套枷锁，而是给模型方向盘、刹车、导航和控制系统。对于想转向 AI Agent 工程的人来说，这比单纯追热点模型更有长期价值。

## 我的点评

这段视频的判断很有道理，因为当前 Agent 落地的主要瓶颈确实往往不是“模型完全不会”，而是执行过程不稳定、上下文混乱、工具调用失误和缺少验证闭环。它把 Harness Engineering 解释成“驾驭模型的外部系统”，这个比喻很清晰，也比单纯说 prompt、workflow 或 agent framework 更准确。值得注意的是，视频里的 Terminal-Bench 案例虽然很有启发，但具体团队、方法细节和排行榜数据仍需要结合原始项目或榜单进一步查证，不能只凭短视频就当成完整技术结论。另一个需要保留的地方是：Harness 不是万能的，底层模型能力仍然决定上限，如果模型本身无法理解任务，外部系统只能缓解，不能凭空创造能力。普通人或开发者可以把这段视频当成一个学习路线提醒：不要只追最新模型，而要系统学习如何组织信息、控制行动、验证结果和长期维护 Agent。
